# BUG-13 CDP 端口硬编码 9222:外部消费方无法 attach 非默认端口实例

> 日期:2026-09-23 | 报告方:media-gen-mcp 项目(gemini 渠道调研,2026-09-22 全程实机使用 lasso)
> 级别:**非阻塞**(有兜底通路;但显著抬高外部消费方接入成本,与"CC 全交互抓手"定位相悖)
> 现场实录与证据:media-gen-mcp `doc/Gemini渠道调研-2026-09-22.md` §5 + `doc/evidence-gemini/`

---

## 1. 背景

media-gen-mcp 第 5 生成渠道(gemini 网页,CDP UI 驱动 gemini.google.com)落地调研,完整消费了一次 lasso 的浏览器治理能力:`doctor` / `chrome-status` / `launch-chrome` / `browse_logged_in`。场景特征:

- 用户原生 Chrome 占用 9222(无调试口,不可用);
- 渠道需要**独立 Chrome 实例 @ 9225**(lasso chrome-profile-default profile,持 Google 登录态,`--idle-ms 0` 防回收);
- 该 profile 的既有登录态正是选 lasso 实例的核心动机(调研零次人工重登)。

## 2. 复现时间线(2026-09-22 实录)

| 步骤 | 命令/工具 | 结果 |
|---|---|---|
| 1 | `lasso doctor` | `cdp_9222_logged_in: fail`(HTTP 404——9222 被占,见 §3-b) |
| 2 | `node dist/index.js chrome-status --port 9222` | ✅ 正确判定 `user_asset_suspected`(pid 444 用户原生 Chrome),**拒绝 kill** |
| 3 | `node dist/index.js launch-chrome --port 9225 --mode visible --idle-ms 0` | ✅ 成功(pid 38789;profile 登录态在,零重登) |
| 4 | `browse_logged_in`(navigate → gemini.google.com) | ❌ **失败:attach 目标硬编码 9222**(chrome-devtools-mcp `--browser-url=http://localhost:9222`),连不到 9225 实例 |
| 5 | (兜底)消费方 CDP 裸 WebSocket 直连 9225 | ✅ 全程可用,调研完成(`PUT /json/new` 开页 + `Runtime.evaluate` 页面上下文驱动) |

## 3. 问题清单

### a)【主体】browse 通道 CDP 端口硬编码 9222(消费方不可配)

**现象**:`browse_logged_in` 对 9225 实例完全不可达——通道内部把 attach 目标写死为 `http://localhost:9222`。9222 被用户原生 Chrome 占用(本机常态)时,**browse 通道整体瘫痪**,无论消费方起没起自己的实例。

**影响**:
- 外部消费方(media-gen-mcp 类工具、任何脚本)想用 lasso 管理的**非默认端口**实例 → `browse_logged_in` 系列全不可用;
- 被迫走 CDP 裸连兜底:每次手写 ws 连接 + 消息路由 + evaluate 封装(样样板代码),丢失 lasso 通道的快照/截图/eval 等成熟能力;
- 与 lasso "外部消费方"治理体系(launch-chrome 端口参数化 / chrome-touch 跨消费方契约 / render-chrome 多端口台账)存在**能力断层**:治理面承认多端口,交互面只认 9222。

**建议**:
1. env 通道:`LASSO_CDP_PORT`(或 `LASSO_BROWSER_URL`)——browse_* 系列启动 chrome-devtools-mcp 时注入 `--browser-url=http://127.0.0.1:$LASSO_CDP_PORT`;
2. 或工具参数化:`browse_logged_in` 增加可选 `cdpPort`/`browserUrl` 入参;
3. 通道未显式指定时保持 9222 现行为(零回归)。

### b)【同根】doctor 的 `cdp_9222_logged_in` 检查假设 9222

9222 被用户资产占用时 doctor 报 fail——语义上"检查项失败"没错,但该检查与 browse 通道共享同一个"唯一端口"假设。若 a) 落地端口可配,doctor 检查建议跟随 env(或增加一项"configured browser port"检查)。

### c)【正面记录——防线按设计工作,非问题】

- ✅ `chrome-status --port 9222` 对用户原生 Chrome 的 `user_asset_suspected` 判定与**拒绝 kill** 完全正确(9/8"永不 kill 用户浏览器"红线实机有效);
- ✅ `launch-chrome --port 9225 --mode visible --idle-ms 0` 端口参数化工作正常;**profile 登录态跨会话保持**(调研隔日续用零重登);
- ✅ 台账/收割体系未干扰长驻调研实例(`--idle-ms 0` 生效)。

## 4. 消费方兜底模式(供其他外部消费方参考)

调研期间验证可用的裸 CDP 模式(生产实现见 media-gen-mcp `src/providers/cdp-client.ts`,flow/gemini 两渠道共用):

```
1. GET  http://127.0.0.1:<port>/json/list        → 定位目标 page target
2. PUT  http://127.0.0.1:<port>/json/new?<url>   → 开新页(🔴 url 参数不落地导航,
                                                    须再对返回的 webSocketDebuggerUrl 发 Page.navigate)
3. WSS  <webSocketDebuggerUrl>                   → Runtime.evaluate(awaitPromise+returnByValue)
                                                    / Input.insertText(可信输入)/ Page.navigate
4. 用毕断开 WS(事件循环引用,不断开会挂住进程)
```

该模式即 lasso browse 通道的底层同款;差别仅在 lasso 把端口封死了。若 a) 落地,media-gen-mcp 的 gemini/flow 渠道可评估切回 lasso 通道获得统一治理(现状:自带 CDP 客户端,零阻塞)。

## 5. 一句话结论

**lasso 的浏览器"治理面"(launch/status/stop/touch)已是多端口世界,但"交互面"(browse_*)仍停在 9222 单端口假设——补一个 `LASSO_CDP_PORT` 即可打通,外部消费方从裸连兜底回到正门。**

## 9. lovart 评估追加阻塞（2026-09-23 第二轮，media-gen-mcp `doc/lovart评估-lasso阻塞项-2026-09-23.md`）

**阻塞-1（E-1 姊妹缺陷）**：chrome-devtools-mcp 惰性 attach——spawn 成功、**首次工具调用**才连 CDP；该失败形态（nav_error 前缀）不进 getMcpClient 的 ensureRunning catch → E-1 三层解析结构性失效。**修复**：browse() 包装层（连接失败签名判定 isConnectPhaseError——版本探针 ∧ 失败词顺序无关组合）→ respawnWithConfigOrDiscovery 自救 → 原请求重试恰一次；签名外错误零干预。

**阻塞-2（config 热生效缺失）**：LASSO_CDP_PORT 的 config file 值为启动期装配，长命 server 不重读——运行中消费方无任何运行时切换口。**修复**：respawnWithConfigOrDiscovery 优先热读 config file 键（file 值合法+≠当前口+非 env 显式 → respawnOnPort 换口，retrieval 标注 config_hot_reload_port）→ 台账发现兜底（E-1 原路）。

**换口体收口**：respawnOnDiscoveredPort 的换口段抽 `respawnOnPort(newPort, tag)` 单一真源（两路复用）。守卫不变：env 显式恒赢 / autoDiscoveredOnce 幂等 / 救不回=原错误如实（E-1 第 3 层纪律）。

**回归钉**：`test/unit/bug13-lazy-attach-rescue.spec.ts` 16 测（签名表 8 形态实测来源+实施锚 F2/F3 审查变异补钉+模板守卫）。

## 10. 第三轮（doubao 评估阻塞-3，2026-09-23）

**定性**：非代码缺陷——CC 的 lasso MCP server（11:06 spawn 长命进程）早于 dist 重建（12:40）→ 载旧码，1.30.1 修复不生效；消费方定位正确（保守未 kill server ✓——失联风险取舍对）。恢复=用户 `/mcp` reconnect。

**真缺口=载旧码无一键裁决**（§6 白盒「最可能解释①」的诊断延伸）：本地 dist 开发模式下消费方无法判断当前 server 进程是否载新码——版本号判据弱（同版本号内可多次重建）。

**修复**：doctor #42 `stale_runtime`——进程启动时间（Date.now()-uptime）vs 自身模块 mtime（同批构建产物，dist .js / vitest 源 .ts 双候选）；mtime 晚于启动 +5s 容忍 → warn「carries pre-rebuild code + 重连 MCP 提示」。MCP doctor tool 在 server 进程内跑=暴露真实判据；CLI 形态恒 pass（新进程永载新码——它不是被裁决对象，同样正确）。永不 fail（诊断探针）。配方入 TROUBLESHOOTING §2.24。
