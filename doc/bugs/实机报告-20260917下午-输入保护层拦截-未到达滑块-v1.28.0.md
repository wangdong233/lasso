## P0：tm.aliyun.com 搜索框输入保护层（新发现，滑块之前）

### 现象

搜索框内**任何程序化设置的值都会在毫秒级被清除**。不是"点击后提交被吞"——是**输入本身就不被接受**。

**关键证据**：

```javascript
// evaluate 直接设值 + 派发事件，然后立即读回——值为空
inp.value = '喵虎';
inp.dispatchEvent(new Event('input', {bubbles:true}));
return inp.value;
// → 返回空串 ""（设值瞬间被清除）
```

**这不是 React 问题**（页无 React root/`__reactFiber` 属性零命中——搜索区由阿里 lowcode 引擎 `hmod-lowcode-normal-page` 渲染）。

### 六路攻击全部失败（完整实验记录）

| # | 方法 | 输入值结果 | 提交结果 | 判定 |
|---|------|-----------|---------|------|
| 1 | CDP `fill_form`（chain steps 内） | fill 报 worked；snapshot 确认 `value="喵虎"` 在位；但 chain 的 navigate 步**重载页面**清空输入 → click 落空值 | 🔴 无跳转 | 页面重载与 fill 竞争 |
| 2 | JS `inp.value = 喵虎` + `dispatchEvent('input')` | 设值瞬间 `inp.value` 读回为空 | 🔴 无跳转 | **值被 lowcode 引擎清除** |
| 3 | JS + `_valueTracker` 欺骗（React 手法） | tracker 不存在（非 React 站）| 🔴 同上 | 方法不适用 |
| 4 | **物理鼠标点击**（`landed:true` 回执确认精确落地）| 按钮坐标正确（从 getBoundingClientRect 计算屏幕坐标），物理点击确认落地——但输入值已被清除 | 🔴 无跳转 | 投递链完好；**值在点击前已没了** |
| 5 | JS click（`btn.click()`）| 同上 | 🔴 无跳转 | lowcode 事件绑定不消费合成点击（或值已空） |
| 6 | Enter 键（KeyboardEvent 派发）| `enter-dispatched val=` 空串 | 🔴 无跳转 | **决定性证据：设值→派发→读回，值已没了** |

### 根因分析

tm.aliyun.com 的搜索输入框由 **lowcode 引擎** 管理，有**输入保护机制**：

1. 引擎可能用 `Object.defineProperty` 劫持了 input 的 `value` setter
2. 或用 MutationObserver 监听 value 变化并重置
3. 或引擎内部维护 shadow state，不与 DOM value 同步——设 DOM value 无效果，读回时引擎返回自己的内部值（空）

**关键区分**：这**不是**反爬检测"检测到自动化就拒绝"——是**程序化 DOM 操作根本不被引擎的输入管道接受**。只有**通过 CDP `Input.dispatchKeyEvent` 逐键派发的真实键盘事件**（或用户物理键盘输入）才能进入引擎的输入管道。

### 与滑块的关系

**滑块从未在本轮出现**。上午 v1.27.1 会话中滑块之所以出现，是因为 chain 的 CDP fill 恰好赶在页面重载完成后的窗口内生效了一次——那次是**运气的时序**，不是可复现的通路。即使到今天，如果能到达滑块环节，v1.28.0 的 `landed:true` 物理拖拽应该能解（投递链已证完好）。

**真正的瓶颈是上游的输入保护层**——搜索词都进不去，永远到不了滑块。

## P1：lasso 缺少逐键输入能力（根因在工具侧的映射）

### 现状

lasso 的 `fill` action（fill_form）底层是 chrome-devtools-mcp 的 fill_form，其实现方式是**直接设置 DOM value**（批量赋值）。对于：
- React 受控组件：可以通过 native setter + input event 绕过（上午的 `_valueTracker` 手法）
- **lowcode/自定义引擎**：批量设值被引擎的保护机制拒绝

### 需要的能力

**CDP `Input.dispatchKeyEvent`**——逐字符派发 `keyDown → char → keyUp` 事件序列，模拟真实键盘输入。这是 Playwright 的 `page.type()` / `page.keyboard.type()` 的底层机制，也是唯一能穿透输入保护层的方法。

chrome-devtools-mcp 的工具集里有没有 type/keyboard 相关工具？我检查了 lasso 源码里 `CDP_UPSTREAM_TOOL_NAMES` 的映射，当前映射表未包含 keyboard 类工具（只有 click/fill_form/screenshot/snapshot 等）。

### 修复建议

1. **短期**：evaluate 内手写 CDP 键盘事件模拟：
   ```javascript
   // 在 evaluate 中模拟逐键输入（利用 InputEvent + isTrusted bypass）
   // 注意：这不是真正的 isTrusted:true——CDP evaluate 的合成事件 isTrusted 为 false
   // 但某些 lowcode 引擎只检查事件存在而非 isTrusted
   ```
2. **中期**：lasso 增加 `type` action，底层用 CDP `Input.dispatchKeyEvent` 逐键派发（与 click 同级的原生输入原语）：
   ```typescript
   // 伪代码
   case 'type':
     for (const char of text) {
       await cdp.send('Input.dispatchKeyEvent', { type: 'keyDown', text: char });
       await cdp.send('Input.dispatchKeyEvent', { type: 'keyUp', text: char });
     }
   ```
3. **长期**：在 doctor #22 投递自检中增加「输入保护穿透」检查项（用已知有输入保护的站点做 fixture）

## v1.28.0 新能力验证详情（正面结论）

### landed:true 落地回执

```
desktop act click@(745,324)
→ { ok: true, cursor_after: {x:745, y:324}, landed: true }
→ physical_input: { attribution: "idle", seconds_since_mouse_moved: 325.7 }
```

**精确、可依赖**。配合坐标校准流程（evaluate 取 getBoundingClientRect → 窗口度量换算屏幕坐标），物理点击的坐标管线完全可用。

### evaluate 三形态

```
JSON.stringify({a:1})  → {"a":1}          ✅ 表达式自动包裹
({...})                 → 返回对象           ✅ 对象字面量
function(){...}()       → 返回值             ✅ IIFE
```

不再需要记住 IIFE 形式，大幅降低调用摩擦。

### 物理输入归因

`attribution: "idle"` + `seconds_since_mouse_moved: 325.7` —— 准确反映鼠标空闲状态，上午的"竞争"假设在本次不再成立（确认投递链独立于物理输入状态工作）。

## 对 lasso 的改进建议汇总

| 优先级 | 建议 | 理由 |
|--------|------|------|
| **P1** | 增加 `type` action（CDP Input.dispatchKeyEvent 逐键派发） | 唯一能穿透 lowcode/自定义引擎输入保护层的输入原语；click/fill 已有，type 是同一层缺失的第三原语 |
| P2 | chain `fill` 在 navigate 后的**时序保证**：fill 应在页面完全加载 + JS 引擎初始化完成后执行（当前可能存在竞争——fill 赶在引擎初始化前执行导致值被后续初始化覆盖） | 上午 v1.27.1 滑块出现可能是时序运气的产物 |
| P3 | `no_reload` 选项的语义文档化或修复 | 本次实测 `no_reload:true` 仍然 `did_navigate:true`——语义不清（是"同 URL 不重载"还是"完全跳过导航"？）|
| 观察 | doctor #22 `cgevent_delivery_selftest` opt-in 合理（真实移动光标） | 未开启测试；但从本次 landed:true 实测看投递链完好 |
