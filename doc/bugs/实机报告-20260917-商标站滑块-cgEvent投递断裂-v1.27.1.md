## P0：desktop cgEvent 鼠标事件未投递到 browse_headed 的 Chrome 窗口

### 现象
所有经 `desktop act`（`served_by: desktop.cgEvent`，API 层一律返回 `worked`）发出的鼠标动作，目标页面**零反应**。包括一次对"必然产生可见状态变化的控件"的点击。

### 坐标标定（排除定位错误的努力）
- headed 窗口度量（页内 `evaluate` 实测）：`screenX=8, screenY=40, outerW=1024, outerH=768, innerW=1024, innerH=625, dpr=2`
- 换算：内容区原点 = `(screenX, screenY + (outerH - innerH))` = **(8, 183)**；页内 CSS 坐标 1:1 映射屏幕 pt（dpr=2 只影响物理像素）
- 截图（2048×1250）→ CSS = img/2 → 屏幕 = `(8 + imgX/2, 183 + imgY/2)`
- 桌面截图 2880×1800 = 2×pt，与单屏一致，排除多屏/缩放错位

### 实验记录（全部 API 层 "worked"）
| # | 调用 | 目标 | 页面结果 |
|---|------|------|---------|
| 1 | `drag(323,628)→(363,628)` | 验证码滑块柄（img≈630,890） | **零变化** |
| 2 | `click(900,740)` + `drag(323,628)→(358,628)` | 先聚焦空白处再拖柄 | **零变化**（`document.hasFocus()=true` 但无法归因——可能本就 true） |
| 3 | **`click(833,453)`** | **验证码卡片关闭 X（img≈1650,545，可见控件）** | **零变化** ← 决定性实验 |

**diff 判定法**：每次动作前后各截一张当前页截图，PIL `ImageChops.difference` 比对。三组 diff 的 bbox 全部仅为 `(1806,25)-(1838,55)`（右上角 33×30px 恒定小动画，与动作无关的证据见 02↔03↔04↔05 逐张几乎相同的 diff）。一个真实落地的关闭 X 点击必然消失验证码卡片（数百 px 级 diff）。

**辅助排除**：desktop 截图不含鼠标光标（macOS 采集 API 默认省略），光标可见性验证不可行；Chromium 的 AX 树不暴露 web iframe 内容（`find role=slider / text=滑块` 均 0 命中），AX 路线对 captcha iframe 天然不可用。

### 结论
cgEvent 事件被 post 到了某处，但**没有到达 lasso-headed Chrome 窗口**。API 层 `worked` + 实际零效果 = 静默失败，比报错更危险。

### 疑似根因（按概率排序）
1. **会话/bootstrap 上下文错位**：rust-helper 由 MCP server 进程 spawn；若其 bootstrap 与 WindowServer 登录会话不一致，`CGEventPost(kCGHIDEventTap)` 的事件进不了任何用户会话窗口
2. **未定向投递**：未使用 `CGEventPostToPid(chrome_pid)` 锁定目标窗口
3. **TCC Input Monitoring（输入监控）未授权**：doctor 的 `tcc_event_synthesizing` 在 macOS<15 判 `not_required` 可能过松—— Monterey 上 CGEventPost 合成鼠标仍可能要求 posting 进程受信（Accessibility ≠ Input Monitoring，是两个独立授权）
4. 坐标空间错位（可能性低，见标定）

### 影响
captcha iframe（跨域，evaluate 不可达）+ AX 不暴露 ⇒ **headed 窗口 + desktop 真鼠标是滑块类反爬的唯一程序化通路**，此路断裂 = 此类站点只能人来拖滑块。这也直接卡住了本次商标查询任务（滑块待用户手动完成后自动化才能继续）。

### 修复建议
1. helper 增加 `CGEventPostToPid` 定向路径（目标 = 通道自开的窗口所属 pid）
2. doctor 增加「合成事件投递自检」：自开一个带可点击控件的小窗 → 发 click → 读窗口状态变化 → 红绿报告（把本次的手工 diff 判定法固化成自检）
3. 核查并纳入 Input Monitoring TCC 到 doctor 检查项（macOS 12 实测行为与之相关）
4. `desktop act` 在 cgEvent 路径增加「落地回执」语义（至少可选）：无回执的动作不该报 `worked`

## P1：browse_headless 在 tm.aliyun.com 的拦截面位移

- **首页**：navigate + snapshot 完整可用（标题/搜索框/全部导航在位）——v1.26 时代「加载 ~2-3s 重定向驱逐到推广页」**未复现**，行为改善
- **查询提交**：steps 链 `fill(喵虎) → click(立即查询) → wait url_contains searchList`：fill/click 均报 worked，但 **10s 超时无跳转、页面无任何变化**（final_url 停留首页）——提交被静默吞掉
- headed 同一提交则弹出阿里云滑块（证据 01）——即拦截仍在，只是从「页面驱逐」上移到「提交消费」层
- **建议**：「检测面三层判定=反爬选型前提」的文档需要更新此站的分层画像（首页层已放行 / 提交层拦截）；headless 提交无反馈的静默失败模式也值得在 steps 真值化语义里标注（click worked ≠ 提交被接受）

## P2：evaluate 返回值契约未文档化

- `js` 直接传表达式（`JSON.stringify({...})`）或对象字面量（`({...})`）→ 返回 `undefined` 或报 `fn is not a function`
- 仅 `function(){...}()` 形式可靠返回值
- 建议：工具 description 的示例体系补一条返回值形式说明；或上游包装自动兜 IIFE。本次浪费 2 次调用发现该契约

## P3：desktop screenshot 载荷形态

- 全屏截图返回 **860,832 字符 base64 JSON**（14 行），超出工具结果 token 上限，被强制落盘到 tool-results 文件
- 建议：参照 browse 通道「默认落盘 + 返回路径」；至少提供 `filePath`-免白名单的默认缓存目录
