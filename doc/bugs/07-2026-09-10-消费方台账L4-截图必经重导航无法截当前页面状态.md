## 1. 新增问题：L-4 两条截图路径均「先导航再截图」，状态敏感截图不可达（P2）

### 现象

消费方需要截取**已加载页面的当前状态**——具体场景：把 CSS 动画慢放后用 `getAnimations().pause()` 冻结在 35% 处，截取中间帧做像素级取证（View Transitions 伪元素动画的冻结态）。实测两条截图路径全部失效：

| 路径 | 行为 | 结果 |
|---|---|---|
| 独立 `screenshot` 工具 | 工具语义=「Navigates to the URL, takes a screenshot」——先重新导航 | 页面重载，冻结状态丢失；截回的图经视觉判读为重载后默认态 |
| `browse_headless action=screenshot` | NAV_FIRST 机制（`BrowseChannel.ts` `NAV_FIRST_ACTIONS = {network, screenshot, pdf}`）无条件先导航 | 同上 |

（第二条路径正是 BUG-05 决议 A 推荐的「一步导航+截图」正确用法——L-4 不是用法错误，是该形态覆盖不了这个场景。）

### 影响与判定

- 受影响场景族：**状态敏感截图**——动画中间帧（pause 的 CSS/WAAPI/VT 伪元素动画）、注入后的临时 DOM、依赖会话状态的任意瞬间取证。这类「对当前受管页面直接截屏」的能力在 lasso 当前形态下不存在。
- 不对称点：evaluate/snapshot/extract/console 通道的页面状态是**持续的**（state_id 复用，同一页面上连续 evaluate 的闭包状态、注入探针全部存活）——唯独**截图必经重导航**，把前面通道建立的全部现场洗掉。对「渲染类交付的验收必须含视觉级证据」的工作流（消费方引擎的验收纪律），这是链路上的断点。
- 判定：设计使然（nav-first 模型），非 bug；但消费方真机需求存在，且规避成本是**借道第二套浏览器自动化栈**（本轮用 playwright MCP 的 `browser_take_screenshot`——对当前页直接截屏不重载）——违反「单一交互抓手」的定位初衷。

### 消费方本轮规避

evaluate/snapshot/console 继续走 lasso（冻结/断言/探针主力）；仅「截当前帧」借道 playwright。

### 建议（供裁决，与 BUG-05 决议 A 的关系）

- 方向 A：`action=screenshot` 支持省略 url 语义——无 url 时对**当前受管页面**直接截屏（无活动会话则显式报错，不静默新开）。与 NAV_FIRST 不冲突（有 url=现状 nav-first，无 url=current-page 模式）。
- 方向 B：加 `options.screenshot.keepCurrent`（或 action 级 `current:true`）显式开关——默认行为字节不变。
- 两方向都可与决议 E 的 `LASSO_SCREENSHOT_DIR` 写根守卫正交组合（current-page 模式无 url，守卫面不变）。
- 决策点提示：这本质是「channel 的无状态单发模型」与「受管会话状态」的边界问题——snapshot/extract 已有 FRESH_PAGE_NAV 空白会话逻辑先例，screenshot 补一个「已有会话则不导航」分支在拓扑上同族。

## 5. 决议（2026-09-10，设计合成员裁决；白盒 + 外部调研双输入核毕）

> **r1 修订（2026-09-10 对抗复审否定轮，两项 P1 全部采纳）**：
> ① **自愈穿透**——LoggedInChannel 楔死自愈 heal 层 1（`new_page {about:blank, background:true}` 后**返回原 client**，LoggedInChannel.ts:529）与 getMcpClient 主动 heal 入口（:232-240）都使「同 client 换新空白页」对 client-身份型守卫不可见 → current-page 截图对 heal 出的空白页产出 outcome=worked 的状态伪造，击穿本决议 §5.3 自设的「绝不静默截 about:blank」。
> ② **错误形状未钉产生点**——若 no-session 契约以 dispatchAction throw 落地（其自然错误形态），classifyBrowseError 无 `no_active_session` 规则 → unknown → 三级劣化：breaker.recordFailure 熔断污染（3 次连续即 open 60s，殃及后续正常 url 调用被跳过、fallback 到 logged_in 驱动用户真 Chrome）/ fallback_exhausted 吞 error+hint / 复合串被 `upstream_wedge` 规则截胡。
> ③ 复核中另发现**第三条同型穿透口**（否定轮未列）：browseSingle catch 的 P6 `recoverNoPageSelected` 分支（BrowseChannel.ts:495-505；LoggedInChannel override 新建 about:blank tab + select_page 后同 client 重试）——对 current-page 截图同样空白页伪造，一并封堵。
> 修订落点：§5.2③（守卫位置更正）、§5.3（守卫升级+自愈禁令+invalidation+错误产生点铁则+classify/isFallbackWorthy 双兜底）、§5.4（熔断纯净性）、§5.6（T6 强化+T13-T16+INV-95 锚重写为四重形状锚）、§5.7（证明义务扩增）、§5.9（迁移口径补行为边界）、§5.10（预存缝隙记档）。

### 5.0 定案一句话

**方向 A⁺（混合定案）**：`url` 在 `browse_headless` / `browse_logged_in` / 独立 `screenshot` 工具三处 schema 可选化——**省略 url + action=screenshot = current-page 模式**（对当前受管页面直接截屏，零导航）；**有 url = 现状 NAV_FIRST 字节级不变**。无活动会话显式报错（didnt，不静默新开）。方向 B（keepCurrent 开关）**否决**。独立 screenshot 工具**纳入**同语义（迁移口径见 §5.11）。

### 5.1 方向裁决依据（A vs B 五维对比）

| 维度 | A（url 省略=current） | B（keepCurrent 开关） |
|---|---|---|
| 消费方工作流契合 | 直接命中：evaluate 冻结→`action=screenshot`（无 url）→console 取证，全程单工具 | 需另传开关；url 仍必填 → 调用方被迫填一个**将被忽略的 url** |
| 接口面诚实度 | 「无 url=无导航目标」语义自洽 | url+keepCurrent 同传=**接受即矛盾**的接口形态（正是 review-r1/r2 清理 wait_until/region 死参数要消灭的族类）；两 knob 优先级还要再定义 |
| schema breaking 面 | `required→optional` 纯加法：既有调用方全传 url，零影响；原先省略 url=zod 硬错，现在=结构化 InteractResult（严格更 informative） | 同样要动 schema，却换来更浑浊的语义 |
| FRESH_PAGE_NAV 同族度 | 同族正扩展：「已导航会话不回灌导航」（snapshot/extract 的 blank-gated 先例）延伸到 screenshot 的无 url 形态；机制上=NAV_FIRST 门加一个 url-definiteness 条件 | 无先例可依 |
| 行业/上游对齐 | 上游 take_screenshot **本就无 url 参数**（「截当前页」是上游原生语义，nav-first 是 lasso 自创组合）；Playwright/Puppeteer/WebDriver/CDP 四家导航与截屏皆正交原语；MCP 生态收敛「无状态协议+有状态工具」 | 与行业形态反而更远 |

**B 否决主因**：B 的 url 仍必填，迫使调用方在状态敏感场景传一个不再被消费的 url——这个「契约里活着、运行时死掉」的参数面，恰是本仓 INV-91/接口面诚实化纪律的存在理由。

**独立 screenshot 工具纳入理由**：它经 `headless.browse()` 走同一 HeadlessChannel 受管子进程（`subproc.ensureRunning("headless")` 单例）——「当前页」在两个入口指向**同一页面**，语义天然一致；若只给 browse_headless 开能力，两入口能力不对称，未来消费方在独立工具上必然重新发现 L-4（同会话不同命）。且 url-present 行为零改动（§5.8），纳入是纯加法。

**明确不在本期**：`pdf`（锁定上游 1.7.0 无该工具，开了=死面）、`network`（current-page 语义其实良定义——「上次导航以来的请求」，但消费方未提需求，守最小面）。机制上以 `CURRENT_PAGE_ACTIONS` 顶级 const 预留增项位（同 NAV_FIRST_ACTIONS house pattern），未来加=一行。

### 5.2 接口契约定案

1. **schema**（两文件三处，同 commit）：
   - `src/tools/browse.ts` `browseSchema.url`：`z.string().url()` → `z.string().url().optional()`——**禁 `.default()`**（absent 必须=undefined，不得注入 ""，守 byte-identical 断言纪律；extract_mode 同款）。
   - `src/tools/screenshot.ts` `screenshotSchema.url`：同上。
2. **分发语义**：
   - url 省略 + `action:"screenshot"` → current-page 模式：**零导航**，直接对当前受管页截屏。
   - url 省略 + 其它任何 action（含缺省 action=snapshot 的裸调用）→ 显式拒：`outcome:"didnt"`、`error:"url_required_for_action:<action>"`、hint `"url is optional only for action=screenshot (current-page mode); pass an explicit http(s) url"`。
   - url 省略 + `options.steps` 非空 → 同上拒绝（防 steps 链在隐式 current-page 上跑出未定义语义）。
   - 有 url → **现状全等**：NAV_FIRST 照旧先导航（`navigate_page {type,url,ignoreCache}` → `take_screenshot`），FRESH_PAGE_NAV 门照旧。
3. **通道层实现形状**（`BrowseChannel`）：
   - `browse(url: string | undefined, action, options)` 参数类型放宽（进程内 TS 面，无 MCP 影响）。
   - 新顶级 const `CURRENT_PAGE_ACTIONS = new Set(["screenshot"])`。
   - **r1 更正——current-page 守卫块位置在 `browseSingle`**（dispatchAction 之前、`try` 之外，与 unknown_action / upstream_unsupported 两个 early-return 先例同位）：`dispatchAction` 返回 `Partial<BrowseResult>`，**没有 outcome 面**，其唯一错误形态是 throw——正是 r1 发现 ② 要消灭的落点（throw → classify → unknown → 熔断污染）。守卫放 browseSingle 才能直接 return 完整 InteractResult(didnt)。
   - `dispatchAction` 门只做加法守卫：`url !== undefined && (NAV_FIRST_ACTIONS.has(action) || needsFreshPageNav(c, action, url))` → 原导航分支**逐字节不动**（current-page 已在 browseSingle 早退，永不达 dispatchAction）。
   - `needsFreshPageNav` 签名 `url: string | undefined` 并前置 `url !== undefined` 守卫（防 undefined 走 `url !== "about:blank"` 求值出 true 的隐性边——对抗复审自查项）。
   - 响应形状（current-page 成功）：`data.url = "current-page"` 字面量（诚实+可 grep，不伪造 URL）；`final_url` 同值回显；`preview = "screenshot saved to <path>"` 不变（`extractScreenshotPath` 兼容）。**解析真实页面 URL = 显式非目标**（需额外 take_snapshot 往返，YAGNI，记档）。
   - `ignored_options` 模式感知（INV-91 精神）：current-page 模式下 screenshot 的 consumed 集合去掉 `"no_cache"`（该键只经导航消费，无导航即死键）——调用方传 no_cache 必须出现在 `ignored_options`。消费表仍是单一真源，模式变体由运行时从表派生。

### 5.3 无活动会话错误契约（「显式报错，不静默新开」；r1 修订：守卫升级为「client 身份 ∧ 未被自愈换页」）

**判定两级**（正确性 + 零副作用）：

1. **pre-check（不获取 client）**：通道级 `lastNavigatedClient === null` → 立即报错。冷通道**不 spawn 浏览器子进程**就完成拒绝——「不静默新开」落到实处（headless 不拉 Chromium；logged_in 不拉 npx 上游）。
2. **获取 client 后复核**：`lastNavigatedClient === c && navSeenClients.has(c)` 不满足 → 同样报错。这层封 **respawn 边**（上游子进程重启换 McpClient 实例，新浏览器=空白页）**和 heal 换页边**（见下条 invalidation——同 client 但选中页已被自愈换成新空白页）。

**r1 实施铁则 (b)——自愈失效通知（封「同 client 换页」穿透）**：

楔死自愈有两层（LoggedInChannel.healUpstreamWedge）：层 1 `new_page {about:blank, background:true}` 后**返回原 client**（「选中页已重置——原 client 即已解楔」，LoggedInChannel.ts:529）；层 2 respawn 换新 client。原判定的两级守卫只比对 **client 身份**——层 1 的 client 身份不变，两级全过 → doScreenshot 对刚建出来的空白页截图 → outcome=worked 的**状态伪造**，直接违反本节「绝不静默截 about:blank」。另有第二入口更早：`getMcpClient` 的 reconcile 命中类型化楔死信号即在内部 heal 后直接返回（LoggedInChannel.ts:232-240），browseSingle 侧守卫连比较机会都没有。封法：

- `BrowseChannel` 增保护方法 `invalidateCurrentPageSession(): void { this.lastNavigatedClient = null; }`。
- 调用点（三处，全部在自愈成功路径上）：`healUpstreamWedge` 层 1 成功 return c **之前**、层 2 成功 return c2 **之前**、`recoverNoPageSelected` 返回 true **之前**（P6 自愈同样把选中页换成新建 about:blank tab——r1 复核发现的第三条同型穿透口）。getMcpClient 主动 heal 入口经 healUpstreamWedge 自动覆盖。
- 守卫语义从「client 身份」升级为「client 身份 ∧ 未被 heal 换页」：invalidation 置 null 后，level-1 pre-check 即拒绝（冷热同形），冷通道语义不变、被 heal 通道立即显式报错。
- `navSeenClients`（WeakSet，FRESH_PAGE_NAV 共用）**不动**——不 delete、不改写点（改它=动 FRESH_PAGE_NAV 既有 golden，超本决议边界）。current-page 有效性单一真源 = `lastNavigatedClient`。**诚实记档（预存缝隙，非本决议引入）**：heal 换页后 `navSeenClients.has(c)` 仍为 true，url-bearing 的 blank-gated action（snapshot/extract）会跳过回灌导航、在 heal 出的空白页上执行——BUG-04 heal 与 review-r3 F3 门控的组合缝隙，属既有行为，记入 §5.10 待独立裁决，本期不修（current-page 模式经 invalidation 不受其影响）。

**r1 实施铁则 (a)——current-page 模式禁自愈重试**：

browseSingle 的 dispatchAction catch 有两条「自愈 + 原样重试」路径（wedge-heal 重试 :491 / no-page-selected 恢复重试 :505）。对 current-page 模式（`url === undefined`）**两条都禁**：选中页被关 = 受管状态定义性消亡，heal 出的新页（无论同 client 还是 respawn）对状态敏感截图毫无意义——重试的唯一可能产出就是空白页伪造。实现：**仅在两条自愈分支内**前置 `url === undefined` 判定 → 直接 return session-gone didnt（early-return，**不 throw、不调 healUpstreamWedge / recoverNoPageSelected**）；其它错误（如 screenshot_write_failed）照常走 classify 原路径——**不得**做成 catch 顶部的裸 `if (url === undefined) return`（会把无关错误误报成 no-session，制造新的错误归因伪造）。url-present 路径的自愈重试**逐字节不动**（BUG-04 决议 B / P6 既有行为，INV-89(c) 锚不破坏）。

**错误产生点铁则（r1 发现 ② 封口）**：

no-session 契约必须是 **browseSingle 的 early-return**（完整 InteractResult：outcome:"didnt" + retrieval_method + error + hint 原样直达调用方），**禁止以 dispatchAction throw 形态落地**。白盒依据：dispatchAction 的自然错误形态是 throw → browseSingle catch → classifyBrowseError——该函数无 `no_active_session` 规则 → unknown → ① `breaker?.recordFailure()`（FallbackDecider.ts:317；threshold=3 连续即 open 60s，后续**正常 url 调用**被跳过、fallback 到 logged_in 驱动用户真 Chrome——熔断污染级联）；② isFallbackWorthy 排除集不含该码 → fallbacks=[] 链耗尽 → error="all_channels_failed_or_skipped"、retrieval_method="fallback_exhausted"、hint 全丢；③ 复合串 `upstream_wedge_unhealed:no_active_session:…` 被 upstream_wedge 规则截胡仍落 unknown。early-return 则 didnt → FallbackDecider 短路 + `breaker?.recordSuccess()`——零污染。

**belt-and-braces（classify 兜底规则）**：`classifyBrowseError` 增 `m.includes("no_active_session") || m.includes("url_required_for_action") → "didnt"`（§5.2② 的 url-required 拒绝同族同保），且**必须置于 `upstream_wedge` 规则之前**（否则复合串被截胡；铁则 (a) 落地后复合串本不可达，此规则防未来重构回退）。unknown_action（:437-447）与 upstream_unsupported（:460-467）是本铁则的仓库内先例——同为「策略确定性拒」的 early-return 家族。

**belt-and-braces 之二（isFallbackWorthy 排除集）**：`NOT_FALLBACK_WORTHY_PATTERNS`（fallback/outcome.ts:107-113）追加 `"no_active_session"` 与 `"url_required_for_action"`——万一残余 throw 路径仍产出 unknown+该码，FallbackDecider 的 unknown 分支走 `!isFallbackWorthy → 立即返回原 result`（error/hint **原样保留**，不落 fallback_exhausted 吞噬形态；FallbackDecider.ts:320-328）。这是发现 ②(ii) 劣化形态的第二道独立封口（第一道=early-return 铁则；classify 规则把 unknown 本身消掉，本条封「classify 漏、decider 收」的残余组合）。排除集现有五模式（404/not_found/403/forbidden/needs_manual_2fa）全部是「明确否信号误报成 unknown」族——no_session/url_required 同族，非特例开口。

**实现纪律（R-INT-07 教训）**：`lastNavigatedClient`（可空强引用）与既有 `navSeenClients`（WeakSet）**同两行写点、单写者**（dispatchAction 现有 `navSeenClients.add(c)` 两处），只增只读判定，不构成多消费者 mutable state 耦合面。唯一例外写点 = `invalidateCurrentPageSession()`（三处自愈调用点）——写者仍是通道自身（protected 方法，子类 heal 钩子内调用），无跨消费者面。

**错误形状**（FallbackDecider 语义下 `didnt`=短路不 fallback，双保险见 §5.4）：

```
outcome:          "didnt"          // 策略确定性拒，不可重试
retrieval_method: "current_page_no_session"
error:            "no_active_session:current_page_screenshot"
hint:             "current-page screenshot requires an active session on this channel:
                   run any url-bearing action (navigate / snapshot / evaluate / ...) first,
                   or pass url for the one-step navigate+shoot form. Refusing to shoot a
                   blank page — the previous page is gone (closed / rotated by self-heal /
                   cold channel), which would fabricate state."
```

（hint 覆盖三个触发路径：冷通道 / respawn / 选中页被关（含自愈换页）——下一步指引相同（重建会话或改传 url）。hint 为 additive 字段、error 字节稳定——BUG-05 决议 B3 同款范式。）

**LoggedInChannel 同门控**：统一保守——本通道未被 lasso 导航过（或会话已被 invalidation 判死）即视为无会话。「截用户 Chrome 当前选中 tab」是另一个特性（tab 定向捕获），本期不开、记档。

### 5.4 守卫组合与通道钉定

- **LASSO_SCREENSHOT_DIR（决议 E）正交不变**：写根守卫在 `doScreenshot` handler 内、先于一切上游调用——与是否导航无关。current-page 模式逐条：filePath 缺省 → 管理 `/tmp/lasso-screenshot-<uuid>.png`；显式+空根 → 拒；显式+非空根 → 双 containment 照旧。**判定顺序**：no-session（dispatch 门）先于 filePath 守卫（handler）。
- **SSRF**：url 省略 → `guardEntryUrl` 整体跳过（无导航目标可守，空集守卫=形式主义）；url 存在 → 原样照跑。
- **fallback 钉通道（新增铁则）**：`tools/browse.ts` 对 current-page 请求构建 `plan.fallbacks = []`（仅 primary）。否则 headless 中途 unknown 会 fallback 到 logged_in——静默截**用户 Chrome 当前 tab**，比失败更糟（跨浏览器状态伪造）。与 INV-23「不跨 surface fallback」同哲学的通道内收紧。独立 screenshot 工具本就直连 headless 无 fallback，天然满足。
- **r1——熔断纯净性**：上述 fallbacks=[] 与 §5.3 early-return 铁则合取后，current-page 无会话路径全程不产生任何 `recordFailure`（didnt → `breaker?.recordSuccess()`，FallbackDecider.ts:304-313）——**无会话误用不得污染通道熔断器**（3 次连续 unknown 即 open 60s，会把后续正常 url 调用挤到 logged_in 驱动用户真 Chrome）。测试锚见 T14。
