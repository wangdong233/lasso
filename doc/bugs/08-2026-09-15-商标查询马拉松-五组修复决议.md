## 1. 根因链（设计合成员源码复核，P0-1 为实证修正版）

**P0-1（长 evaluate → -32001 → 「连坐杀死 Chrome」——用户观察的一半是误判）**：

1. `McpClient.callTool`（McpClient.ts:205-214）不传任何超时 → SDK `Client.callTool` 落 `DEFAULT_REQUEST_TIMEOUT_MSEC=60000`。**60s 不是设计值，是 SDK 缺省事故**。
2. 上游 chrome-devtools-mcp@1.7.0：忽略 `notifications/cancelled` + 一把全局 `toolMutex` 串行化所有工具 → 长 evaluate 在服务端继续跑，期间**任何**后续 action 排队各烧满 60s → 逐个 `-32001`。**Chrome 从未死**——「只有 navigate 能重生」被真机证伪（楔死是时间性的：服务端 evaluate 结束（≤180s puppeteer protocolTimeout）后 mutex 释放，navigate 只是恰好晚到的下一个调用）。
3. **归因污染（用户误判「Chrome 死亡」的直接机制）**：`-32001` 文本无规则命中 → `classifyBrowseError` 落 unknown →（有 url 时）browse.ts:298 fallback 链 `[browse_headless → browse_logged_in]` → logged_in 对 9222 的连接失败错误成为 terminal `error`（FallbackDecider 全链耗尽时 terminal = **最后一跳**的 result，主通道错误只剩 actions_and_results 审计行）→ 调用方看到「Could not connect to Chrome... localhost:9222」。
4. `budget_ms` 单 action 路径零消费（CONSUMED_OPTIONS 注释自认）→ 进 `ignored_options` 回显（P2-3）——「收了不生效」。

**P0-2（内部栈死锁）**：chrome-devtools-mcp 栈是 SubprocessManager 进程内 spawn（procs map + lifecyclePids），**跨进程不可见**；台账（chrome-ledger.ts）主键 port + 归属标记 `--user-data-dir`（chrome-stop verifyOwnership:135-150）——内部栈两者皆无 → `chrome-stop --all` 返 `{"stopped":[]}`、deny-hook 正确拦 OS kill → 死锁。crash 路径（exit 钩子未达）遗留两代栈并存（1:06AM + 1:12AM 实锤），idle reaper 也是进程内的，无人扫。

**P0-3（无换脸逃生门）**：被服务端指纹拉黑后，同一通道会话内无任何「全新身份」出口——navigate 重试/no_cache/等待全部无效（惩罚按浏览器上下文隔离，用户在自己浏览器解封救不了无头实例）。

**P1-1（hash 假数据——本批最危险）**：上游 1.7.0 WaitForHelper 对 sameDocument/historySameDocument 显式短路（不重载）；lasso `doNavigate`（BrowseChannel.ts:1062-1099）零 hash 检测、`verifyNavigatedPage` 只查错误签名 → hash-only 导航后 SPA 状态残留，lasso 返 worked + 新 hash final_url。真机 marker 实验：hash-only 后 `window` 上下文存活（marker=42）而 `?v=2` 变更即重载（marker=null）——hash 特异性确证。

**P1-2（evaluate url 假 final_url）**：evaluate 不在 NAV_FIRST_ACTIONS（:1800）/FRESH_PAGE_NAV_ACTIONS（:1822）→ 带 url 直达 doEvaluate 不导航；partial 无 final_url → browseSingle `final_url: partial.final_url ?? effUrl`（:662）兜底**伪造目标 URL**。

**P1-3**：`CURRENT_PAGE_ACTIONS = new Set(["screenshot"])`（:1806）→ wait 报 `url_required_for_action:wait`。

**P2-1（修正版）**：`LASSO_CDP_PORT` 已存在（env + config 模板 LASSO_CDP_PORT:9222 + KEY-GUIDE:309 文档）且已接线到 LoggedInChannel——真缺口：9222 attach 失败时**无自动发现**（launch-chrome 起了 9223，logged_in 仍死磕 9222）+ 故障排查文档无此场景配方。

**P2-2**：`outcomeFromFetchError` 恒 unknown（Y2 裁决正确保留），但 `error = String(e)` = 裸 `TypeError: fetch failed`——undici 的 `e.cause`（ENOTFOUND/ECONNREFUSED/ETIMEDOUT/CERT_* 等）被丢弃，DNS/CONNECT/TLS/拦截不可分辨。

## 2. 定性（外部先例映射）

- **超时即「结果没拿到」而非「资源死亡」（P0-1）**：browserless 的 per-session TIMEOUT 语义——调用超时是调用层事实，不得触发资源层处置。误判的代价已实证：用户据 logged_in 的错误文案判 Chrome 死亡。归因保真是 P0 级修复面。
- **内部栈治理（P0-2）**：systemd `KillMode=control-group` = **单元级组杀**（以 cgroup 为界，绝不越界）→ lasso 对应「以登记 pid 的进程树为界」；Selenium Grid = **spawn 即登记 + 周期扫除**——崩溃互斥清理的直译就是「spawn 前扫同 channel 登记项」。与台账（detached 端口 Chrome 域）分域：**一个账本一个域**，跨域混载破坏既有消费方（chrome-stop --all / reaper / chrome-status 三方）。
- **身份即受管资源（P0-3）**：Crawlee Session 模型（身份生命周期状态机：max_age/usage 上限/错误分阈值/401·403·429 强制 retire）与 FP-Block/Laperdrix 铁则——**一个身份内部指纹必须自洽；「换脸」= 整个新一致身份，部分变异（旧 token 配新 profile）本身是被检测信号**。freshProfile 因此必须同时换 profile 目录与 stealth profile，且新身份要有会话生命期（非每调用一换），用后清理三路闭环（Puppeteer 默认「临时 profile、关即删」同型）。
- **假数据比崩溃危险一个数量级（P1）**：P1-1 真机场景 = 差点把「哒哒=0 条干净」写进报告（真值 3718）。安全方向裁决：**宁可 reload**（数据正确性优先于加载性能）。

## 3. 架构决议（A–E）

### 决议 A：【稳定性】evaluate 调用预算 + 超时类型化不连坐 + 归因保真

**A-1 callTool timeout 传导（机制，全调用点缺省不变）**

`McpClient.callTool(name, args, timeoutMs?: number)`——timeoutMs 传入时走 SDK `client.callTool(params, undefined, { timeout })`（RequestOptions；实施时以仓内 @modelcontextprotocol/sdk@^1.30 的 .d.ts 实读核对参数形状，上游只读依赖红线）。**不传 = 现状字节级不变（SDK 60s）**。接线面：仅 evaluate 路径传入（其余 action 生命周期短，60s 缺省是正确缺省）。

**A-2 evaluate 调用预算（P2-3 的「收了就生效」）**

- 新常量 `DEFAULT_EVAL_CALL_TIMEOUT_MS = 120_000`（放 McpClient.ts 或 BudgetTracker.ts，实施批定；取值 = `DEFAULT_CHAIN_BUDGET_MS` 同值对齐——链级预算与单 evaluate 预算同一数量级是既有设计事实，非新拍脑袋）。env `LASSO_EVAL_TIMEOUT_MS` 覆盖（NaN/负 → 回默认，parseCdpPort 同范式）。
- `options.budget_ms`（既有 zod 键，int>0 ≤600_000）对 evaluate **生效**：`budget_ms ?? env ?? 120s` 传导到 A-1。zod 上限 600s 即天然钳制（不引 clampChainBudgetMs——那是链预算的钳子，语义域不同）。
- `CONSUMED_OPTIONS.evaluate` 追加 `budget_ms`（+ D-2 的 `no_cache`）——单 action evaluate 传 budget_ms 不再进 ignored_options。

**A-3 超时类型化 + 不连坐 + 归因保真（本批核心正确性面）**

1. **类型化**：BrowseChannel catch 面识别 `-32001` / `Request timed out` → throw `mcp_request_timeout:<原文截断>`；`classifyBrowseError` 加规则 `mcp_request_timeout → unknown`（可重试 + fallback-worthy，语义与现状一致，但 agent 透明可识别）。
2. **不 respawn、不自动重试**：真机证明 Chrome 未死、楔死 ≤180s 时间性自解；respawn = killTreeSync 整栈（把「假死亡」变「真连坐」），代价大于等待。真死亡（transport closed / pid dead）由 `ensureRunning` 懒 respawn 结构性覆盖（任何 action 均可触发——报告所称「只有 navigate 能重生」不成立，修正进 hint 文案）。hint 附带教学：长批量 evaluate 请显式 `budget_ms`；通道级楔死 ~3min 自愈。
3. **归因保真（fallback 污染修复）**：FallbackDecider 全链耗尽（所有 hop 非 worked）时，terminal `error` 从「最后一跳错误」改为 **primary 错误为主**：`<primary_error> [fallback <last_channel>: <err 摘录 120 字符>]`；`actions_and_results` 审计链不动（每 hop 错误仍在）。效果：headless 超时 + logged_in 连接失败 → 调用方看到 `mcp_request_timeout:... [fallback browse_logged_in: Could not connect...]`——两层事实都可见，误判「Chrome 死亡」的机制消失。

- 向后兼容：A-1 缺省路径字节级不变；A-2 是新生效键（此前被 ignored_options 诚实标注为死键，现兑现——调用方语义纯增益）；A-3①③ 改 error 字符串形状（前缀/composite）——下游若断言 error 精确串需同步（仓内测试面自查）；分类 outcome 不变（unknown），熔断/fallback 行为零变化。
- 安全面：零 kill 面变化；不新增 spawn；hint 文案只教正门（budget_ms），不给 kill 指引。
- 实施面：`src/subprocess/McpClient.ts`（callTool 第三参）、`src/channels/BrowseChannel.ts`（doEvaluate 调用点传预算 + catch 面类型化 + CONSUMED_OPTIONS）、`src/config/config.ts`（parseEvalTimeoutMs，缺省 120s）、`src/fallback/FallbackDecider.ts`（耗尽路径 error 组装）、`src/tools/descriptions.ts`（evaluate/budget_ms 双例文档）。
- 测试面：McpClient.spec（timeout 透传——SDK options 形状断言）；BrowseChannel.spec（evaluate 传 budget_ms → callTool 收到 timeout；-32001 → `mcp_request_timeout:` 前缀 + unknown；60s 默认不再裸穿）；FallbackDecider.spec（双 hop 全失败 → error 以 primary 打头 + last-hop 摘录在尾；worked/didnt 终态路径 byte-identical 不变）；config-file.spec（LASSO_EVAL_TIMEOUT_MS 三态）。变异红证：拆类型化规则 → 前缀测试红。

### 决议 B：【内部栈治理】admin browser_recycle 单一正门 + spawn 即登记 + 同 channel 孤儿扫除

**B-1 回收出口裁决：admin `browser_recycle` 胜出；`chrome-stop --channel` 否决**

- ✅ **admin 新 action `browser_recycle`（单一正门）**：入参 `{channel: "headless"}`（v1 只开 headless；logged_in 的等价物 = 既有 profile_switch/respawn 路径，不重复开面）。执行体 = `SubprocessManager` 侧受控重启（forgetSpec/registerSpec 重建 spec + ensureRunning）——**进程内真源一致**：procs map、closed 标记、`navSeenClients`/`lastNavigatedClient`（BUG-07 会话守卫按 McpClient 实例身份自动重置为新空白会话）。返回 `{restarted: true, spec, pid}`。
- ❌ 台账路线（内部栈写入 chrome-ledger + `chrome-stop --channel headless`）否决，四条理由：①台账主键 port——内部栈无 CDP 端口，塞合成 port 是 schema 弯曲；②归属验证协议不同——台账 kill 前 cmdline 验 `--user-data-dir=<profileDir>`，内部栈上游自管临时 profile 无此标记，混载 = 弱化验证；③**既有消费方契约红线**——`chrome-stop --all` 现语义「台账记录全停」，内部栈入账会静默扩大 --all 的杀面（reaper/chrome-status/执守三方读同一账本，全部被动改行为）；④进程内资产的正门本来就该是进程内（admin action 与栈同进程，能原子更新全部内存态；进程外 kill 留下陈旧 McpClient 句柄）。
- 与 C 组合：`browser_recycle` 支持可选 `{freshProfile: true}` 直接走决议 C 的换脸重启（一个正门两个深度）。

**B-2 崩溃互斥清理（spawn 即登记 + 扫除，Selenium Grid 先例直译；R1 修订：pid 级归并版）**

- 新 sidecar `~/.cache/lasso/headless-stacks.json`（env `LASSO_HEADLESS_STACKS_PATH` 测试隔离）：数组 `[{specName, pid, ownerPid, spawnedAt}]`。`SubprocessManager._spawnWithBackoff` spawn 成功即追加登记（与 lifecyclePids 同点）。注意登记面是**全部 spec**（headless / logged_in / browserbase / steel 共用同一 spawn 通路），sidecar 天然多 spec 混载——这正是必须 pid 级归并的原因（见下）。
- **判杀算法（R1 重写——先归并、后逐条、lstart 交叉核对）**。触发点：**任何 spawn 前**（不限同 spec——陈旧记录的清理收敛性不应依赖同 spec 再被使用；Selenium Grid「周期扫除」的本义）。步骤：
  1. **pid 级归并（R1 新增，防跨记录 pid 复用杀活栈）**：把 sidecar 全部记录按 pid 分组；**任一记录的 ownerPid 仍活 → 该 pid 整组跳过（零动作）**，仅清除组内 ownerPid 已死的陈旧记录条目（活服务器的栈绝不动——多 lasso server 并存合法；即使两条记录同 pid、陈旧条 owner 死而活条 owner 活，也由归并整体豁免）。
  2. 组内全部 ownerPid 已死 → 对 pid 本体三重判定：①pid 存活（`process.kill(pid,0)`）；②`ps -p <pid> -o command=` 含精确包串 `chrome-devtools-mcp@1.7.0`（锁定版本常量拼入——排除非 lasso 进程复用该 pid，verifyOwnership 同哲学不同标记）；③**进程起始时间交叉核对（R1 新增，一劳永逸封死 pid 复用类）**：`ps -p <pid> -o lstart=` 解析后与记录 `spawnedAt` 比对（容差 ±5s；不符 = 该 pid 已被**任何**新进程复用——哪怕是另一 lasso 栈——只清记录**绝不杀**）。
  3. ①不成立 → 清记录；②或③不成立 → **只清记录绝不杀**（pid 复用嫌疑）；全过才杀：`killTreeSync(pid, "headless-stack-mutex")`（npx→node→Chromium 整树，systemd 单元级组杀对应物）+ 清该组记录。
  - 实证背景（R1 复核锚点）：四个 channel 的 spec 共拼同一 `chrome-devtools-mcp@${LOCKED_CDP_MCP_VERSION}`（HeadlessChannel.ts:80 / LoggedInChannel.ts:180 / BrowserbaseChannel.ts:168 / SteelChannel.ts:265）——条件②对任何 lasso 栈恒真，**唯一能区分「谁家的栈」的维度是 ownerPid，而 ownerPid 判定必须按 pid 归并后做**，逐记录独立评估会被「陈旧 logged_in 记录的 pid 被活 server B 的 headless 栈复用」击穿（server C 崩→孤儿栈消亡→pid 复用给 B→任何 logged_in spawn 触发扫除：①活②包串同③C 死→误杀 B 的活栈）。
- server 正常停机已有 killAllSync 兜底；exit 钩子顺带清自己 ownerPid 的 sidecar 记录（best-effort）。**防误伤红线机械化**：杀的对象永远 = 「lasso 登记过 + 无任何活 owner 认领 + cmdline 仍是 lasso 锁定上游 + 进程起始时间与登记一致 + 主人已死」的进程树——任一条件不满足即零动作，绝不触碰非 lasso 进程（用户浏览器天然无此包串 + 无登记）。
- 向后兼容：sidecar 全新增（best-effort 写，失败不阻断 spawn——台账容错同款）；无既有消费方读它；chrome-stop/reaper/chrome-status 零改动。
- 安全面：唯一新增 kill 路径 = B-2 扫除（pid 归并 + 三重守卫 + 包串精确匹配——R1 后守卫从三道扩为归并前置 + 三道）；admin browser_recycle 复用 SubprocessManager 既有 _kill（INV-78c 零新 kill 原语）；deny-hook 正门提示文案不动语义（chrome-stop 仍是 detached Chrome 的正门；内部栈正门在本决议后为 browser_recycle——文档面同步，hook 属 ~/.claude 项目外，仅登记协调项）。
- 实施面：`src/subprocess/SubprocessManager.ts`（spawn 登记 + spawn 前扫除，INV-7 纯 lifecycle 语义保持——不读协议帧）、新文件 `src/subprocess/headless-stack-ledger.ts`（sidecar 读写 + **pid 归并谓词 + lstart 解析比对**，导出供测试）、`src/tools/admin.ts`（browser_recycle action）、`src/tools/descriptions.ts`。

### 决议 C：【反爬逃生】freshProfile——完整新一致身份 + 三路清理

**语义（身份隔离铁则的直译）**：`options.freshProfile: true`（**仅 browse_headless**；browse_logged_in 传入即拒 `didnt` + error `fresh_profile_not_supported_on_logged_in`——用户真实 Chrome 红线，永不重造）。

- 执行体（browse() 入口、getMcpClient 之前拦截）：
  1. **新临时 profile（R1 修订：目录名编码归属锚）**：`~/.cache/lasso/headless-profile-<epoch>-<rand>-p<ownerPid>/`（命名镜像 `RENDER_PROFILE_PREFIX` 形态 + **ownerPid 后缀**——归属锚直接编码进目录名，崩溃原子、无侧车写竞态；profile 的孤儿判定不依赖任何外部状态）经 `--chromeArg=--user-data-dir=<dir>` 注入（v1.11 chromeArg 通道，UA/Accept-Language 同通道先例）；
  2. **stealth profile 轮换**：从宿主适用集合确定性取下一个 profileName（禁止随机——可复现性），UA/viewport/Accept-Language/JS evasion 同步整体切换——「换脸 = 整个新一致身份」，杜绝「旧指纹配新 profile」的部分变异检测信号；
  3. **完整栈 respawn**：forgetSpec("headless") + registerSpec（新 profile + 新 stealth 参数）+ ensureRunning（LoggedInChannel profile_switch 的 forgetSpec+registerSpec 既有范式，零新形态）；
  4. 会话守卫自动正确：新 McpClient 实例 → navSeenClients（WeakSet）自然失效 → FRESH_PAGE_NAV 门重新武装。
- **身份生命期（Crawlee Session 模型）**：新身份服务后续所有调用，直到 idle reaper 回收（LASSO_HEADLESS_IDLE_MS 5min）/ 下一次 freshProfile / server 退出——**非每调用一换**（会话内频繁换脸本身就是异常流量信号）。
- **清理（R1 重写：先杀后删 + 四路——三路即时 + 一路陈年兜底；复用 render 档 cleanupRenderProfile 基建形态且对齐其真实顺序，防 BUG-03 教训重演）**：
  - **顺序铁则（R1 修正核心）**：fresh profile 的一切 rmSync 一律在**所属 Chromium 树杀完成之后**发起。实证锚：初版把 rmSync 挂进 cleanupZombies 的 pre-kill reapHook 是错位——该 hook 在 `await this._kill(name)` **之前**跑且被 3s race 截断（SubprocessManager.ts:238-250），活体 Chromium 写盘（LevelDB journal/lockfile）与 rmSync 目录遍历竞态、SIGKILL 与删除并发 → 删一半留一半；而自引先例 cleanupRenderProfile 实为**先杀后删**（chrome-stop.ts:351 `stop_killed` / :434 `stop_sync_killed`，:349 注释明言「在杀进程之后」）。修正 = 对齐先例：
  1. 受控回收点（idle/zombie reaper、B-1 browser_recycle、freshProfile respawn）→ SubprocessManager 新增 **post-kill hook**（`setPostKillHook`，cleanupZombies 在 `await this._kill(name)` 完成后调用，forgetSpec/_kill 调用点同接）：`name === "headless"` → rmSync 该 spec 的 profile 目录。**既有 pre-kill reapHook（tab restore，需 Chrome 活着）零改动**——语义分离：pre-kill hook 只做「需要目标活着」的收尾，post-kill hook 只做「需要目标死了」的清理。post-kill rmSync 不进 3s race（树已死无竞态，重试安全；失败 best-effort 重试一次后 warn 放行，交陈年兜底）；
  2. server shutdown/exit（killAllSync 完成后）→ rmSync（顺序本就先杀后删，保持）；
  3. 下一次 freshProfile respawn：旧栈 `_kill` 完成后 → rmSync 旧 fresh profile（当前 server 自有资产，即时可删，无需 age 线）；
  4. **崩溃孤儿陈年兜底（R1 新增路径④——封死 SIGKILL 泄漏）**：SIGKILL 崩溃下②不可达（exit 钩子未跑）、①不可达（新 server 的 procs map 无该 spec）、③无记忆、B-2 扫除只杀孤儿栈进程**不触及其 profile 目录** → 残留目录此前永无清理者（本机 ~/.cache/lasso 3.3GB/448 条目实证「缓存域清不动」是本库失败模式；fresh profile 单目录 50-200MB，代价更高）。直译 render-doctor 陈年扫描先例（render-doctor.ts `RENDER_STALE_PROFILE_MS = 24h`，「age 线避免与拉起窗口竞态」）：扫描 `headless-profile-*-p<digits>` 目录，**双闸全过才删**——目录名编码的 ownerPid 已死 **且** age > 24h（freshProfile 身份生命期上界 = idle reaper 5min 级，24h 线极保守）。两闸皆 fail-safe：pid 复用只会让死 owner **显活** → 跳过（泄漏顺延到 pid 释放后的下一轮扫描），任何情况下不误删活 server 的在用 profile。**明确禁止** `glob headless-profile-*` 无条件全删实现（并发双 server 时会删掉对方在用活 profile——macOS 上 in-use 目录被 rm → 对方 Chromium 新写失败/会话态毁）。扫描点：搭 B-2 spawn 前扫除同点（一次 spawn 顺带收敛）+ doctor 可观测清单。
  - 全部 rmSync 带 basename 前缀守卫 `headless-profile-`（cleanupRenderProfile 的「删目录与杀进程同红线」镜像）；即时路径（①②③）额外守卫 = 当前 server 自有 spec 引用；陈年路径（④）守卫 = ownerPid 死 + age 线。
- 响应标注：`data.fresh_profile: true`（该次调用确实换了身份——调用方审计可见）。
- 向后兼容：纯 opt-in 新键，缺省 false = 现状字节级不变；默认 spec（无 user-data-dir 注入）零改动——既有 headless 行为完全不变。
- 安全面：respawn 只杀 lasso 自有 npx 树（SubprocessManager._kill 既有原语）；profile 目录创建/删除都在 `~/.cache/lasso/` 域内 + 前缀守卫 + 归属守卫；stealth 轮换不触碰 INV-30 anti-gaming 面（profileName 选择在 lasso 侧，非 LLM 可控输入）。
- 实施面：`src/channels/HeadlessChannel.ts`（freshProfile 方法：spec 重建 + stealth 轮换 + 目录名含 ownerPid；陈年扫描函数）、`src/channels/BrowseChannel.ts`（browse() 入口拦截 options.freshProfile → 子类钩子，默认 no-op 保 LoggedInChannel 拒绝语义）、`src/subprocess/SubprocessManager.ts`（**新增 post-kill hook** + cleanupZombies 在 `_kill` 后调用之；pre-kill reapHook 不动）、`src/tools/browse.ts`（schema 键）、`src/tools/descriptions.ts`。
- 测试面：HeadlessChannel.spec（freshProfile → forgetSpec+registerSpec 调用序 + 新 spec args 含 user-data-dir + 目录名含 `-p<ownerPid>` + stealth 参数随 profile 变化；连续两次 freshProfile → 轮换确定性）；**清理各路钉**（post-kill hook 分派 / killAllSync 点 / respawn 前 / 陈年扫描——rmSync 前缀守卫注入验证：非法 basename 拒删）；**R1 新增顺序断言**：mock `_kill` 与 rmSync，断言 rmSync 发起时刻**晚于**树杀完成（pre-kill 窗口内零 rmSync 调用）；**R1 新增陈年扫描真值表**（owner 活 → 留；owner 死 + age<24h → 留；owner 死 + age>24h → 删；目录名无 `-p<digits>` 归属锚 + age>24h → 删；前缀不符 → 跳过）；BrowseChannel.spec（logged_in 传 freshProfile → didnt + 专用 error 码）；schema（缺省无键 byte-identical）。真机验收（用后清理）：真站拉黑形态难复现，以「两次 freshProfile 后 cookie/localStorage 不跨身份」代证 + profile 目录零残留（find ~/.cache/lasso -name 'headless-profile-*' 为空，含手动 SIGKILL server 后触发一次 spawn 再验）。

### 决议 D：【假数据面】hash 导航默认 reload + evaluate url=ensure-navigation + wait 当前页

**D-1 hash/same-document 导航检测——默认 reload（安全方向裁决：宁可 reload）**

- `doNavigate` 前先读当前页真实 URL（quickSnapshot 式单次 `evaluate_script` 读 `location.href`；失败/空白页 → 跳过检测，现状路径不变——与 verifyNavigatedPage 同 best-effort 哲学）。
- 判定：目标 URL 与当前 href **去掉 hash 后完全相等** 且**完整串不同** → same-document 导航形态 → navigate 后追加 `navigate_page {type:"reload", ignoreCache: opts.no_cache}`（上游原生 type=reload；实施时以 listTools/上游 tarball 实读核对参数名——只读依赖红线）。reload 后页面在目标 hash 上全量重执行（查询类 SPA 数据正确性恢复——marathon 假数据场景的根治）。
- 返回标注：partial 增 `same_document_navigated: true`（检测命中）+ `same_document_reloaded: true/false`（是否补了 reload）。**opt-out**：`options.no_reload: true`——保留「SPA hash 路由由应用自处理、重载反而破坏会话态」的显式逃生（此时仅标注不重载，假数据风险交还调用方知情承担）。
- 成本：每次 navigate 多一次轻量 evaluate（~几十 ms 级 RTT；verifyNavigatedPage 本就做 snapshot+evaluate 双调用，边际成本低）。仅当两侧 URL 均含 hash 或去 hash 相等才可能命中——常规跨页导航零行为变化。
- 向后兼容：非 hash 导航字节级不变；hash 导航从「worked+旧数据」变「worked+重载后的新数据」——行为变更但方向 = 数据正确（changelog 显著位声明）；`no_reload` 为新 opt-in 键。
- 安全面：零（纯导航语义）。实施面：BrowseChannel doNavigate + CONSUMED_OPTIONS.navigate += `no_reload` + browse.ts schema + descriptions。测试面：doNavigate 单测（同 path 差 hash → reload 调用发出 + 双标注；`?v=2` 类变更 → 不 reload；no_reload:true → 只标注；URL 读取失败 → 现状路径）；真机复跑 finding 的 marker 实验（reload 后 marker=null 断言）。

**D-2 evaluate url 语义定案：url = ensure-navigation（先导导航）**

- `doEvaluate` 前读 `location.href`：**不同或无页** → 先走完整导航（复用 wrapNavigate 链——含 stealth afterNavigate）；**相同** → 原地执行零开销。
- `final_url` = 先导导航的 final_url 或读到的当前 href——**两路都是真实值**，`partial.final_url ?? effUrl` 的伪造路径对 evaluate 永不触发（消灭 P1-2 的「preview 是当前页、final_url 是目标 URL」自相矛盾）。
- 语义依据：url 显式传入 = 调用方声明「在这个页上跑」；url 省略 = 当前页（现状）。与 FRESH_PAGE_NAV（snapshot/extract 的空白门控）差异是有意的：evaluate 是驱动/变异型 action（非观察型），显式目标就该到达——P1-2 受害者的心智模型正是如此。已导航会话传**相同** url 零扰动（读 href 相等即原地跑），cc-control 等消费方传匹配 url 的存量模式不受影响。
- 向后兼容：url 省略路径字节级不变；url 传入且 ≠ 当前页 → 从「静默跑错页+伪造 final_url」变「真导航+真实 final_url」——修正型行为变更（changelog 声明）。CONSUMED_OPTIONS.evaluate += `no_cache`（先导导航消费）。
- 测试面：doEvaluate 单测（url≠当前 → navigate 先行 + final_url=nav 值；url=当前 → 零导航调用 + final_url=href；url 省略 → 现状）；与 D-1 组合（evaluate 到 hash-only 目标 → 先导导航触发 D-1 reload——两决议组合语义钉）。

**D-3 wait 支持当前页**：`CURRENT_PAGE_ACTIONS += "wait"`（一行——house pattern 注释预留的增项位）。doWait 不读 url，天然兼容；BUG-07 会话守卫（level-1 冷通道不 spawn 即拒 / level-2 实例复核）自动生效——无会话当前页 wait = `no_active_session` 拒（与 screenshot 同契约，不静默等空白页）。`urlRequiredResult` hint 文案与 descriptions.ts 同步（"only for screenshot" → "screenshot / wait"）。向后兼容：url 传入路径不变；纯增新形态。测试面：browse.spec（wait 无 url 有会话 → worked；无会话 → no_active_session didnt；hint 文案更新断言）。

### 决议 E：【P2 批】logged_in 端口三层解析 + fetch_url 失败细分

**E-1 logged_in 端口：显式配置恒赢 → 运行时自动发现 → 原错误（三层）**

1. **LASSO_CDP_PORT env/config 显式**（现状已有）→ 恒赢，自动发现永不介入。
2. **运行时自动发现（新增，仅默认 9222 attach 失败时）**：LoggedInChannel.getMcpClient 抛连接类错误且 `cdpPort === 9222 && 无显式覆盖` → 读台账取最新 `launchedAt` 的**非 render** 记录（渲染档确定性红线——browse 流量会污染消费方 golden；userTakenAt 记录**允许**——attach 非生命周期操作）且该 port CDP 探活通过 → respawn spec 到该端口重试一次 → 结果携带 `note: "auto_discovered_port:<port>"`（retrieval_method 加法标注，调用方可见）。**只在失败路径介入**：默认 9222 可达时（绝大多数存量用户，含无台账的自开 Chrome 用户）行为字节级不变。
3. 均失败 → 原错误如实（不被自动发现污染）。
- 文档面：`doc/usage/02-TROUBLESHOOTING.md` 增「9222 被占/自有 Chrome 在他口」配方（marathon 场景原样：chrome-status 鉴定 → launch-chrome --port 9223 → browse_logged_in 自动发现或显式 LASSO_CDP_PORT）。
- 向后兼容：9222 健康路径零变化；失败路径从「死磕 9222 报错」变「失败前多一次有标注的自救」——纯增益。安全面：自动发现只读台账 + CDP 探活（零 kill/零 spawn Chrome）；attach 对象恒为 lasso 台账资产。
- 测试面：LoggedInChannel.spec（9222 失败 + 台账 9223 记录 → spec args 端口切换 + note 标注；台账仅 render → 不发现；显式 env → 永不发现；9223 探活失败 → 原错误）。

**E-2 fetch_url 失败细分（error 字段信息加法，outcome 语义零变化）**

- 新分类函数 `classifyFetchFailure(e)`：解 undici `TypeError: fetch failed` 的 `e.cause.code` → `fetch_failed:<kind>:<detail>`，kind ∈ `dns_failed`(ENOTFOUND/EAI_AGAIN) / `connect_refused`(ECONNREFUSED) / `connect_timeout`(ETIMEDOUT/UND_ERR_CONNECT_TIMEOUT) / `tls_failed`(CERT_*/SELF_SIGNED_*/ERR_TLS_*) / `aborted_timeout`(AbortError——opts.timeout_ms 到点) / `other`。cause 缺失 → `fetch_failed:other:<原文>`（不猜）。
- `outcomeFromFetchError` 保持恒 unknown（v1.18.2 Y2 裁决——DNS/连接错是环境瞬态可重试——语义正确，不动）；只把 `String(e)` 换成分类串。调用方由此分辨「本机代理/DNS 环境」vs「目标站拒绝」。
- 向后兼容：error 字符串形状变化（前缀化）；outcome/served_by/data 零变化；isFallbackWorthy 排除集不受影响（fetch_url 本就不挂 fallback 链）。
- 测试面：fetch-url.spec（六 kind 真值表——注入带 cause.code 的 Error 形状；cause 缺失 → other；AbortError → aborted_timeout）。

> 输入不在商标马拉松报告内——独立用户实锤：lasso 测试残留的 vitest forks-pool worker 孤儿群曾把用户整机负载打到 **188（单个 worker 87% CPU）**。机理 = agent/进程被中断时 vitest 主进程死而 worker 子进程存活自旋（忙测试体 `await` 长 sleep，主进程之死不唤醒它）。与 BUG-03/BUG-06 同族（进程生命周期收尾缺口），但域在**仓内测试基建**（非 lasso server 运行时面）。

**白盒（vitest 2.1.9 `dist/config.js:99 pool: "forks"`——CLI help 的 "default: threads" 是误导文案，resolver 实际缺省 forks）+ 真机复刻（本批 spec 行为组三钉）**：

- **forks 池**：worker = 独立子进程（探针 marker 实证 worker pid ≠ 主 pid）。SIGKILL(vitest main) 后**忙 worker 原样存活**——事故形态复刻成功；killTreeSync 追杀后清零（对照组证明事故可治理）。
- **threads 池**：worker = 主进程内 worker_thread（探针实测 worker pid == 主 pid）。主死 = 线程随之死——**孤儿 worker 类结构性消灭**。运行期唯一子进程 = 瞬时 esbuild service（stdin 连主进程，主死自退——两池同型，非孤儿源）。
- **隔离语义等价**：threads + `isolate:true`（缺省）= 每测试文件新 worker 线程；worker 线程 `process.env` 是独立副本（Node 缺省非 SHARE_ENV）——逐文件 env 隔离与 forks 等价。兼容性验证 = 全量 gate 绿（2988→2997 既有用例零红，含 timing-sensitive 桶）。

### F-1 结构层：`ORPHAN_GUARD_POOL = "threads"` 显式钉死（vitest.workspace.ts 两 project 同钉）

缺省 forks 是事故根源 → 显式常量钉 threads，两 project（default + timing-sensitive）同钉防部分回退。守卫锚 = `test/unit/vitest-orphan-governance.spec.ts` 纯锚组（常量改 forks / 删任一 project 的 pool 行即红）；**不进 check-invariants**（INV 面是 src/ 运行时契约；测试基建的契约由测试自身钉——变异锚同效）。真机残余自旋 worker 不需要迁移处理：threads 只影响**新跑**的测试进程，既有孤儿（若有）按 B-2 哲学「下次可观测 + 手动 ps 清」——本批实施时机器已零残留（ps 实证）。

### F-2 belt 层：gate.mjs vitest 树超时追杀带（E1 白盒时序修正版）

- **belt 预算**：`LASSO_GATE_VITEST_TIMEOUT_MS`（未设/NaN/非正 → 缺省 20min；健康全量水位 3-7min，belt 永不该在健康跑开火）。判绿：belt 开火/异常终态（status null/带信号/watchdog）→ **恒红**（超时无退出码可言）。
- **🔴 E1 时序实锤（本组实施期的否定发现——初版 belt 被推翻）**：初版用 `spawnSync timeout + 返回后 chaseVitestTree(r.pid)`。E1 真机实验证明该形态**追空树**：spawnSync timeout 只对**直子**（npx）发 SIGTERM，且 spawnSync 要等子进程死透才返回——返回时刻树根已死、后代已 re-parent 给 launchd，`pgrep -P <死根>` 恒空；且 SIGTERM(npx) 后 vitest main 优雅死、空闲 worker 随死，**唯忙 worker 原样存活**（E1 数据：树 9 成员，post-term 幸存者恰为 marker 忙 worker）——即初版 belt 在它唯一的目标场景（超时楔死）里恰好漏杀事故主角。
- **修正实现**：gate.mjs 的 vitest 步骤改走 `gate-lib.mjs runWithBelt`（async spawn + 手动超时竞赛）——belt 到点在**树根仍活**时 `killTreeSync(根)`（kill-tree.ts「先全量枚举后统一 SIGKILL」单趟，根活时调用 = npx→node(vitest)→esbuild→worker 整树全灭；成员按 pid 直杀，re-parent 不再是逃生通道）。belt 后 exit 必至（SIGKILL）；总 watchdog = belt+15s 宽限+5min 兜底防 gate 永挂。两 timer 定局后一律 disarm（防「健康退出后 timer 迟到开火」误杀复用 pid）。外部击杀形态（belt 未开火而异常终态）保留死后 best-effort 追杀（chaseVitestTree——死根恒空手为已知残余，E1 注）。
- **单一真源纪律**：树杀动态 import `dist/util/kill-tree.js`（gate 门序 build 先于 vitest，dist 必在；gate-lib 零第二份 pgrep 递归——变异锚钉）。

### 残余观察项

1. **belt 只护 gate 语境**：开发者裸跑 `npx vitest run` 被中断时无 belt——threads 池结构层已把该形态的 worker 孤儿类消灭（主死线程死），残余面只剩测试自 spawn 的子进程（既有现象，非本组新增；esbuild 瞬时类自退）。
2. **E1 后 chaseVitestTree 对死根恒空手**：外部击杀形态（如 OOM killer 杀 gate）的 re-parent 残余不可达——已知残余，与 B-2「依赖下一次 spawn」同形同裁决（可观测 + 下次收敛）。
3. **threads 池行为差异**：worker 内 crash 不再是独立进程 crash（forks 下 node 子进程崩溃不影响主，threads 下 worker 线程未捕获异常由 vitest 线程层兜底转译为测试失败）——全量 gate 绿为兼容性实证；若未来出现线程形态特异 flake，回退 forks 前必须先解决孤儿治理（结构锚会红——设计意图）。
4. **threads 池禁 process.chdir（全量 gate 首跑实锤并当场修）**：`rust-helper-path.spec.ts` 的 cwd 解耦用例原用 process.chdir(os.tmpdir())——worker 线程下 Node 平台级抛 `TypeError: process.chdir() is not supported in workers`（forks 下合法）。修正 = `vi.spyOn(process,'cwd')` 假 cwd 等价实证（默认分支 import.meta.url 不读 cwd → 路径不变；回归为 path.resolve 相对形态则消费假 cwd → 路径漂移红）——变异等价、零 dist 依赖、零子进程。此后新测试在 worker 内禁 chdir（用 cwd spy 或子进程形态）。
