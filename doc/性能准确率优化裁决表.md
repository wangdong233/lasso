## 2. 立即修（下一实施轮）

### PERF-1（P0）cdp-mcp spawn 的 npx registry 税

- **what**：headless/logged_in 通道每次冷启动走 `npx -y chrome-devtools-mcp@1.7.0`——npx 每次做 registry packument 校验，代理拥塞时 3-17s；空闲 5min（`LASSO_HEADLESS_IDLE_MS` 默认 300_000）后的首个 browse 突发重付全税。profile_switch（forgetSpec+respawn）与 `_spawnWithBackoff` 退避（2/4/8/16s）为放大器。
- **代码锚点（本轮复核）**：`src/subprocess/SubprocessManager.ts:55`（LOCKED_CDP_MCP_VERSION="1.7.0"）+ `:521`（退避）；`src/channels/HeadlessChannel.ts:71-73` 与 `src/channels/LoggedInChannel.ts:165-167`（两处 `command:"npx", args:["-y", ...]`）；`src/config/config.ts:113`（DEFAULT_HEADLESS_IDLE_MS=300_000）。
- **证据**：perf 轮真机四轮 `npx -y chrome-devtools-mcp@1.7.0 --version` = 17.2s/7.8s/5.1s/3.3s；`npm exec --prefer-offline` 同命令 0.22s（78×）；SDK 全链 spawn+initialize 5649ms。**本轮独立复测**：`time npx -y chrome-devtools-mcp@1.7.0 --version` = **3.9s**（落 3-5s 常态带；17s 极值为代理拥塞方差）。perf 轮对「SIGKILL 后 15-20s」专项复测已排除 SIGKILL 为独立诱因（真构成 = registry 方差 + 退避叠加 + 旧树孤儿争资源）。
- **修法（最小面）**：两处 registerSpec 的 args 前插 `"--prefer-offline"`（一行 ×2；npx/npm exec 同体，flag 直通）。预期冷启动 ~5.6s → ~2.8s（Chromium 起动 ~2.3s 为不可约地板）。
- **测试**：既有 channel spec 增断言「注册的 spawn args 含 `--prefer-offline`」（锚死不回退）；真机复测计时进验收记录。
- **边界诚实**：`--prefer-offline` 首次无缓存仍走网络（首装一次付税后缓存自持）；与渲染档的关系澄清——`render-chrome --ensure` 直接 spawn Chrome 二进制不经 npx，20s 拉起预算不受此项影响；npx 税仅在消费方 `npx -y lasso-mcp` 兜底解析 lasso 时出现，消费方契约已放宽该路径 90s。

### PERF-2a（P0）看门狗双宿主双倍执行

- **what**：server 进程内看门狗 + 独立 hide-enforcer 执守同时以 1.5s tick 各跑一轮 osascript reassert——正确性幂等（设计明示「双执守最坏一次重复 AX 读」，desired-hide-enforcer.ts:21-22），但 CPU 成本双倍。
- **代码锚点（本轮复核）**：`desired-hide-watchdog.ts:72`（DESIRED_HIDE_WATCHDOG_INTERVAL_MS=1_500，注释明示「闪现上限 = intervalMs」产品语义）；`chrome-hide.ts:70-115`（reassert 变体 = 单次 osascript「查可见→可见才压回」，nomatch 路径仍付全量 AX 枚举）；执守体复用同一调度真源（desired-hide-enforcer.ts:17-18）。
- **证据**：perf 轮真机 osascript reassert nomatch 纯枚举路径 ~873ms/次（平凡 osascript 基线 288ms）→ 单宿主 ≈58% 单核、双宿主 >100% 单核持续占用（System Events 进程）。
- **修法**：server 装配侧让位——启动看门狗前 `probeHideEnforcer()` 为 running 则不自起（执守为权威宿主；probe not running 才自起兜底）。零语义变化：闪现上限仍 1.5s（由执守承载），server 侧本就是冗余 belt。
- **测试**：装配侧单测（注入 probe 结果两态：enforcer 在 → server 不 schedule；不在 → schedule）；既有 watchdog spec 全绿不回归。

### ACC-1①（P1）onResult 死返回契约

- **what**：`SerpHealthMonitor.onResult` 内 `void this._maybeDetectRedesign(...).then(changed => { redesignConfirmed = ... })` 后**同步** `return redesignConfirmed`——Promise 未决即返回，恒 null。头部注释承诺的「extract.ts 通过 onResult 返回值标记 retrieval_method」是死契约。
- **代码锚点（本轮复核）**：`src/serp/SerpHealthMonitor.ts:91-99`（竞态本体）+ `:16`（死承诺注释）；调用点共五处（本轮 grep 全量核实）`extract.ts:157/:176`、`http-serp.ts:280/:345/:365` 均为语句位置调用——**返回值实际无人消费**（逐点核实，`?.onResult(...)` 全部弃值）。测试漏网原因：serp-health-monitor.spec.ts 无非空返回断言。
- **修法（最小面）**：返回值无消费方 → **删死契约**：onResult 改 void 返回 + 删 :16 死承诺注释；确认通路维持 logger + recordings（现状已走）；若未来需要信号，经 snapshot()（doctor/admin 已有面）而非返回值。
- **测试**：先红后绿——mock detectChange 返 changed:true，断言 logger `serp_layout_changed` 事件 + recordings.save 触发（现状这通路也因零 baseline 从不 fire，与 ACC-1② 连测才真正绿）。

### ACC-1②（P1）生产环境零 captureBaseline

- **what**：`captureBaseline` 全仓仅测试调用（本轮 grep 复核：src 生产面零调用点）；`ChangeDetection.ts:108-110` 文件不存在 → `{changed:false}` 不告警 → detectChange 恒 false、recordings 恒不触发——**改版检测链在生产双重失效**。
- **修法**：首次成功抽取后自动 captureBaseline（幂等：无既有 baseline 才写）；写入点在 SerpHealthMonitor 命中路径（hit 时且 baseline 缺失）。doctor serp_health 快照暴露 `baseline_age`（陈旧度可见）。
- **测试**：无 baseline 时首次 hit → baseline 文件落盘；已有 baseline 不覆盖；doctor snapshot 含 baseline_age。
- **诚实边界**：自动首录在「首次运行即已改版」场景会把新布局录为基线（该场景现状本就永不告警，不劣化）；真正的改版检出延迟 = ①② 落地后「改版发生 → 下次查询报警」≤1 次查询。

## 3. 留档（理由在案）

| 项 | 理由 |

| PERF-1'：optionalDependency + `node <pkg>/build/src/index.js` 直起 | `--prefer-offline` 已消 93% 税（78×）；直起引入依赖维护面（版本锁 + 入口漂移 + 安装形态分叉），等实测证明 prefer-offline 不足再升级 |

## 4. 需用户裁决

### PERF-2b：1.5s tick 的 AX 枚举成本 vs「闪现上限」产品语义

- **现状**：粘滞账非空期间，单宿主每 1.5s 付 ~873ms System Events 枚举（≈58% 单核持续）；PERF-2a 去重后仍存。1.5s 不是随便选的——`desired-hide-watchdog.ts:15` 明示「闪现上限 = intervalMs」：上游掀出的隐藏窗口至多存活一个 tick。
- **备选**：
  - 甲（维持 1.5s）：接受 CPU 成本为产品核心循环的定价（PERF-2a 后减半）。
  - 乙（自适应退避）：账写事件后热相 1.5s 保 N tick，零复隐命中则几何退避至 12-30s，任何命中/账写重置——代价：静默期闪现可存活至退避上限，产品保证弱化（闪现与近期 hide 活动相关性高，但非因果保证）。
  - 丙（更便宜的预检门）：tick 内先做廉价「Chrome 是否 frontmost/近期激活」探测，未激活才跳过全量枚举——需真机验证「隐藏窗口被 CDP 掀出时 Chrome 是否必经激活态」，未证前不可靠。
- **裁决建议**：甲 + PERF-2a（本轮）；乙/丙 单独立真机实验轮取证后再议。**此条不阻塞渲染档**（渲染档 headless 无窗口，不进 desired-hide 家族——设计决议 §3.12 边界 6）。
