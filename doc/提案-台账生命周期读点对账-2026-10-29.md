> **状态：v2 终版（三路隔离审查 A/B/C 全 findings 并入 + 否定重查六项亲验闭合——见文末「审查收口」）**

## 第 0 步：不变量陈述（本方案使什么不可能）

**INV-L（本案立法目标，断言句形态）：**

1. **凡 `readLedgerSync()` 返回的记录，pid 必活**——「死 pid 记为 ready」这个状态的寿命 ≤ 一次读取。任何消费方（doctor / reaper / stop / status / A2 门 / 执守 / launch）读到的账**物理上不含死条目**，不需要知道「死条目」这个概念、不需要各自配对账分支。
2. **销账不需要「杀」授权**——`already_dead` 是纯账面操作（零 kill）；gate / modes / userTaken 豁免挡的是 **kill**，永不挡**销账**。「资产」与「资产的账面记录」是两个正交语义，永不共用谓词判定。

不满足 1 与 2 的现状（详见第 1 步）：死条目寿命 = ∞（全库无自动销账路径）；visible 死条目被 kill 豁免扩大解释为销账豁免（`chrome-stop.ts:277-298` 判定先于 `:311` 探活）。

**「简单到简单」的架构演进声明**（稳定性/性能/扩展性三面）：

- **稳定性**：账实分离寿命 ∞ → ≤1 次读取；每个消费方的状态空间各 -1（不再需要死条目分支）；doctor #41 的误导归因形态、chrome-status `ledger_stale` 的「pid 已死/端口已释」子形态、launch 启动对账需求（报告建议 1）、agent 指令面死锁——**四个症状面一次性消解，零新增消费方代码**。
- **性能**：`process.kill(pid,0)` 微秒级 × 条目个位数（台账是本机 Chrome 清单，非舰队）；最高频消费方 desired-hide-watchdog tick 1.5s（A-F4 更正：非 reaper）+ LoggedInChannel 按请求热路径——微秒级 syscall × 个位数条目，开销可忽略；探活不触网、不 spawn 子进程（INV-109 同步冻结红线无涉——kill(pid,0) 是信号探针非子进程）。
- **扩展性**：未来任何新通道/新消费方读台账即得活账，无需知道死条目概念；台账若迁移存储（SQLite/远端），对账随单一读口迁移——收敛点不散。

## 诚实边界（在案接受；v2 扩充）

1. **pid 复用形态**（pid 死后被复用）：读点探活见「活」不销——留给 chrome-stop 循环的 verifyOwnership（cmdline 证据）以 pid_reused_skipped 销账。读点只做无证据不销账的保守对账。
2. **Z 状态进程**（未 reap 僵尸）：kill(pid,0) 返回成功 → 读点判活 → 该条目经显式 chrome-stop 出账（argv 已丢 → verifyOwnership 失败 → pid_reused_skipped）。账实分离窗口可超一次读取——如实登记，不假装 INV-L1 对 Z 态成立。
3. **render 档盘垃圾**：销账连带 cleanupRenderProfile（搬家后）覆盖 stop 路径同款清理；极端并发窗内可能残留临时 profile（缓存区，量小，接受）。
4. **多进程并发写**：台账无锁是既有形态（last-writer-wins）；读点成为**新写者**，与 recordLaunch 的 read-modify-write 存在交错面——最坏丢一条新记录或复活一条死记录至下次读（形态有界；B-F6 措辞更正：非「不恶化」，是「新增写者与交错面」）。
5. **EPERM 谓词分叉**：读点 ESRCH-only 判活 vs chrome-stop catch-all 判死——极低频形态下两谓词给出相反裁决，方向安全（销账不杀），登记不统一（为极低频分叉配共享抽象反而增耦）。
6. **重启全账死亡场景**（收益注记）：整机重启后台账 pid 全死——读点一次读取全清，比现状（全挂）是纯收益。
7. **「只读」契约面微调**：chrome-status/doctor 经 readLedgerSync 可能落账面清理（B-F5 申报）——README chrome-status「只读」措辞指对**页面/进程**零操作，账面自愈不违其意，doctor.ts:2538「零触网」为真（kill(pid,0) 是信号非网络），注释补一行对账注记。
