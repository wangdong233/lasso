# P16：二轮执行中浏览器窗口可见（守则违例）+ 效率观感

## 现象
用户观察到浏览器窗口打开并进入得到（应后台静默）；且"才刚开始"（工作流启动约 22 分钟后才见浏览器动作）。

## 白盒根因（两层）
1. **可见性**：85359（13:25 起的隐藏实例）全程存活未死——窗口可见由二轮 agent 的脚本操作触发（对隐藏 Chrome 开新 tab/窗口时 macOS 平台行为可将其置前/创建可见窗口）；且**二轮工作流 COMMON 只告知"Chrome 在隐藏态"，未给 agent「保持隐藏/开窗后立即复隐」的纪律**——这是编排缺陷（我的）。抢救过程中另犯一错：osascript 按进程名全量 hide 误伤用户日常 Chrome（已立即定向恢复；教训：**hide/show 操作必须 PID 定向，禁按进程名全量**——chrome-hide.ts 的 PID 红线本就如此，手工命令也要守）。
2. **效率观感**：二轮探察 agent 前 ~22 分钟做白盒读档（上轮脚本/断言/PDF 分析）后才触浏览器——白盒先行是质量设计，但「环境自检」应前置为第 0 步消除空窗期观感。

## 判断：流程编排缺陷（非产品）+ 人工命令纪律
修复：①二轮工作流 COMMON 注入「静默纪律」：全程保持 Chrome 隐藏（lsappinfo 验证）；如操作导致窗口可见立即 PID 定向复隐；环境自检（Chrome 活否/CDP 通否）为第 0 步 ②hide/show 手工命令一律 PID 定向（沿用产品红线）。

## 三轮实施增补（2026-08-19，v2 管线实施轮）

1. **P14 增补条款复现**：实施轮再次实测——extract-v2/produce-all **零开窗**（复用既有 tab），但 navigate 后 Chrome 仍会被置可见；`chromeGuard()`（analyze.mjs，lsof 9226 → PID → System Events `first process whose unix id is`）每章后检查，本轮捕获 2 次并 PID 85359 定向复隐成功。守卫已固化进产线（produce-all 每章后调用）。
2. **会话初人工违例（无害但记录）**：环境自检时用了 blanket `set visible of process "Google Chrome" to false`（按进程名，非 PID 定向）。事后核验：另两个 Chrome 进程（2420/6141）**均零窗口**，实际未造成用户可见面损失；但该命令形式违反红线，正确形式为 `tell application "System Events" to set visible of (first process whose unix id is <pid>) to false`。已在 chromeGuard 中固化正确形式。
3. System Events 按 unix id 寻址的可用形式：`get visible of (first process whose unix id is 85359)`（返回 boolean）；`get {unix id, visible} of (every process whose name is "Google Chrome")` 可一次列出全部同 名进程的可见性，用于巡检。
