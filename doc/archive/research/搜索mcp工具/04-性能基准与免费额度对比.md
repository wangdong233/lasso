# 04 · 性能基准与免费额度对比

> 数据全部来自第三方基准（AIMultiple）与各项目官方文档，经对抗核验。注意**免费方案缺乏公开延迟基准**——下表延迟数据是付费 API 的，仅作横向参考。

---

## 一、第三方延迟基准（AIMultiple · 2026-05）

**方法论**：8 个搜索 API × 100 query，bootstrap 置信区间，GPT 评判答案质量（Agent Score）。

| API | 平均延迟 | Agent Score | 免费层 |
|---|---|---|---|
| **Brave Search** | **669ms**（最快） | **14.89**（最高） | 2000 次/月（需 Key） |
| Tavily | 998ms | 13.67 | 1000 credits/月（需 Key） |
| Exa | 中等 | — | ~1000 req/月（远程 URL 免 Key） |
| Parallel Search Pro | 13.6s（最慢） | — | — |
| Perplexity | 11+ 秒 | — | 无（付费） |

**关键结论**（`3-0` 通过）：
- 延迟跨度达 **20 倍**（Brave 669ms ↔ Parallel Pro 13.6s）。
- Tavily 与 Brave 的 Agent Score 差距仅 ~1 分，是基准中唯一有统计意义的质量差异。
- Perplexity 平均 11+ 秒，**不适合交互式 agent**。

**⚠️ 被否决的延伸结论**（`0-3`，见 [05](05-避坑-被否决的误导结论.md)）：
- "Brave 是全场最优推荐" —— 因果过度延伸，已剔除。
- "Perplexity 全场最慢故不推荐" —— 同上，仅保留延迟数字本身。

## 三、限速与并发注意事项

| 方案 | 限速表现 | 多轮研究 agent 下的建议 |
|---|---|---|
| One Search / mcp-web-search | 受上游（DDG 等）隐式限速 | 多源 fallback 设计天然抗限速 |
| duckduckgo-mcp-server | DDG 可能 IP 限速 | 装浏览器 backend；或换 mcp-web-search |
| Jina（匿名） | **硬限 20 RPM** | 研究类高频场景务必申请免费 Key（500 RPM） |
| Exa | ~1000/月硬限 | 仅适合低频；超额降级到 One Search |
| Brave / Tavily | 月额度硬限 | 超额需付费或多 Key 轮询 |

> **降级策略**：本机推荐组合（One Search 主力 + Jina 兜底）天然提供"搜索 + 阅读"双通道；将来若高频，可叠加 Brave/Tavily 作为带额度的质量层。

## 四、免费方案为什么没有公开延迟基准？

- **原因**：DDG/SearXNG/One Search local 这类免费方案的延迟取决于**本机网络 + 浏览器启动 + 上游引擎**，无法标准化基准。
- **实测建议**：装好后用同一组查询在本地实测（建议测：首次冷启动 vs 热查询、中文 vs 英文、单条 vs 并发）。
- **经验值**：DDG 直连类通常 1–3 秒；浏览器自动化类（local）冷启动会慢 2–5 秒，热查询 <2 秒。

## 五、稳定性维度（非数值，定性）

| 方案 | 稳定性来源 | 风险点 |
|---|---|---|
| mcp-web-search | 三源自动 fallback | Bing 回源需 Chrome+Puppeteer |
| SearXNG 系（自建） | 200+ 引擎聚合，最抗封 | 需运维；公共实例限速 |
| One Search（local） | 多后端可切 | 依赖浏览器进程 |
| Jina / Exa | 官方托管运维 | 受官方额度/政策影响（Tavily 收购案为鉴） |
| duckduckgo-mcp-server | 单源 | TLS 反爬对抗（需 browser extra） |
