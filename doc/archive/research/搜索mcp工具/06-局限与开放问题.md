# 06 · 局限与开放问题

> 诚实交代本调研**没覆盖、不确定、有时效性**的部分。选型落地前建议据此做针对性实测。

---

## 一、时间敏感性（额度/定价会变）

- **Tavily**：2026-02 被 Nebius 收购（最高 4 亿美元），免费层（1000 credits/月）长期存续存在风险。
- 各项目（Tavily / Jina / Exa）的额度数字以 **2025–2026 文档**为准，使用前请核对官方最新页面。
- MCP 生态迭代快，README 细节（如 One Search 的 provider 列表、DDG 的 backend 默认值）可能随版本变化。

> 📌 **建议**：落地前用 `claude mcp list` + 一次实测确认行为，别完全依赖本文数字。

## 二、单源依赖

- **性能/延迟基准（见 [04](04-性能基准与免费额度对比.md)）完全来自单一行业分析机构 AIMultiple**。
- 其方法论透明（100 query、bootstrap CI、GPT 评判），但仍是单一来源。
- 其中"Brave 全场最优、Perplexity 全场最慢"两条因果结论已在验证阶段被 0-3 否决（见 [05](05-避坑-被否决的误导结论.md)），未纳入发现。
- 免费方案（DDG/SearXNG/One Search local）**无任何公开延迟基准**，需本地实测。

## 三、2-1 分票结论（可信但有分歧）

以下 3 条结论为 `2-1` 通过（两票支持、一票反对），结论方向可信，但建议以各项目最新 README 为准：

1. **whw23/searxng_http_mcp 的"免费定位"**：多数证据支持其完全免费，但有 voter 指出 uvx 模式需既有 SearXNG 实例，存在前置成本。
2. **duckduckgo-mcp-server 的 TLS 封锁隐患**：维护者自披露，但不同 voter 对"默认 backend 是否已足够"有分歧。**实操建议：装上 `[browser]` extra 保险。**
3. **Jina s.jina.ai 拒绝匿名访问**：search 类工具缺 Key 时返回 Authentication failed；有 voter 认为极低频可能放行，但主流证据是直接 block。**实操建议：搜索类务必配 Key。**

---

## 四、本机环境约束（来自记忆）

- 本机 **8GB 内存、日常占用 ~94%、未装 Docker**。
- 因此 **SearXNG 系（自建）实际落地成本偏高**。
- 本地原生二进制方案对当前机器更友好：
  - One Search MCP（`local` / `duckduckgo` 模式）
  - mcp-web-search（DDG 模式）
  - duckduckgo-mcp-server（带 browser extra）
- ⚠️ One Search `local` 模式会起浏览器进程，**内存吃紧时可能加剧 503**（瞬时峰值，直接重试，勿调高阈值）。此时可临时切 `duckduckgo` 模式。

---

## 五、中文搜索质量未被直接验证

- **One Search MCP** 含百度/搜狗（`local` 模式），是唯一明确支持中文的方案，但**召回与摘要质量缺乏对照基准**。
- DDG / SearXNG / Jina / Exa 的中文召回同样无对照数据。
- 结合本机记忆中"智谱 GLM Coding Plan 优先"的偏好：
  - One Search 的 `zhipu` provider（需 Key）可能是中文场景的优质补位项。
  - 建议装好后用 5–10 个真实中文查询做 A/B 实测。

## 六、商业 / 许可风险

| 项目 | 许可 | 商用注意 |
|---|---|---|
| SearXNG 本体 | **AGPL-3.0**（非 MIT） | 商用需复查 AGPL 传染性条款 |
| Jina 10M 免费 token | 据条款**限非商业用途** | 商用需付费计划 |
| 其余（One Search / mcp-web-search / DDG MCP） | MIT | 相对宽松 |

> 📌 若用于商业产品（如彩票平台等本机记忆中的项目），**务必复查 SearXNG 的 AGPL 与 Jina 的非商业条款**。

## 七、长期稳定性存疑

- 免费层（尤其 Tavily 被 Nebius 收购后）能否持续？
- DDG 的 TLS 反封锁对抗（`html.duckduckgo.com` 端点）是否可持续？维护者已在用 `curl_cffi` 模拟 Chrome 131 TLS 应对，但这是猫鼠游戏。
- **生产/高频场景**的最终答案可能是：**自建 SearXNG 实例**作为最稳定后端（届时本机需升级或上服务器）。

---

## 八、限速降级策略（待实测）

各 MCP 在多轮搜索/研究 agent 触发限速后，是否原生支持 fallback/重试/多 Key 轮询？

| 方案 | 原生降级支持 |
|---|---|
| mcp-web-search | ✅ 三源自动 fallback（最佳） |
| One Search | ⚠️ 需手动切 `SEARCH_PROVIDER`（非自动） |
| Jina（匿名 20 RPM） | ❌ 超限即拒绝，需手动换 Key 或降频 |
| Exa（~1000/月） | ❌ 超限 429 |
| duckduckgo-mcp-server | ❌ 单源，靠 browser backend 绕反爬 |

> 多 Key 轮询可参考本机记忆中的"LLM key gateway selection"思路（new-api 原生 exe 方案）。
