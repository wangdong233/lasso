# Lasso 增量排期：桌面通道插入（v0.3.5，2026-07-21）

> 增量排期文档，不重写 09。在原 v0.1→v1.0 排期基础上插入 **v0.3.5 DesktopChannel MVP** + 后续版本相应修订。已确立的 24 条核心决策与 v0.1-v1.0 阶段划分全部保留；09 附录 2 中"multi-root forest 永远不进 / AX outline 永远不进"两条**推翻**（见本文件 §1.3）。

## 1. 桌面通道加在哪个版本：**v0.3.5 DesktopChannel MVP**

**插入位置**：v0.3（多步链式 + session 隔离）之后、v0.4（cloud 浏览器）之前。

**版本号选择**：用小数 **v0.3.5** 而非重排 v0.4-v1.0，**不破坏 09 既有所有版本引用**（v0.4 cloud / v0.6 dynamic / v0.7 doctor / v0.8 login / v0.9 wayback / v1.0 stable 全部保留原义），降低文档震荡成本。

### 1.1 理由 1：依赖前置完备（决定性）

DesktopChannel 的核心抽象在 v0.1 + v0.3 才齐备，提前会变成"半成品 + 重构"：

| 依赖项 | 来源 | 用途 |
|---|---|---|
| BaseChannel 7 契约方法 | v0.1 F3.6.1-3, 8-9 | DesktopChannel 平级实现的基础接口 |
| FallbackPlan / CapabilityBag / CircuitBreaker 类型 | v0.1 F3.4.1-9 | desktop 4-tier fallback 复用同类型，不开第二套（R-CI-02 红线） |
| isFallbackWorthy / getFallbackChannel / activeProvider | v0.1 F3.4.x | desktop fallback 复用**同一函数**（F3.9.9(c) 不变量） |
| tri-state outcome (worked/didnt/unknown) | v0.1 F3.4.11（pi 修正） | desktop_act 返回值；expect 失败检测 |
| Subprocess Manager（单一） | v0.1 F3.5.x | Rust helper 子进程挂载点（不开第二套进程管理） |
| doctor CLI 框架 | v0.1 F3.6.7（pi 修正） | desktop_doctor 复用 |
| 架构不变量测试 CI 脚本 | v0.1 F3.9.8（pi 修正） | F3.9.9 新增 8 项 desktop 不变量断言 |
| ToolAnnotations 四象限 | v0.1 F3.3.13（pi 修正） | desktop_* 工具同范式 |
| ProviderConfig 单一注册表 | v0.1 F3.7.x | 4 desktop providers（ax/appleScript/cgEvent/screenshotVlm）同表注册 |
| StateStore + stateId LRU(128) + AsyncLocalStorage | v0.3 F3.2.10/19 | desktop_snapshot 的 stateId 共享存储（`StateStore<OutlineSnapshot>` 替换 `StateStore<PageSnapshot>`） |
| expect 后置条件 + actions_and_results 审计链 | v0.3 F3.2.11/18 | desktop_act 的 expect 与审计同范式 |
| InteractTask 类型 + rootRef dormant 字段 | v0.3 | desktop 用 `@wN` 激活一半（browse 仍 `@pN`） |

**关键**：v0.1/v0.3 已把"抽象同构"做完（OutlineNode / FallbackPlan / InteractTask / tri-state），v0.3.5 只需"加第 3 个 BaseChannel 实现 + 1 个 Rust helper 子进程"——这是 R-CI-02 红线（不开第二套做法）能否守住的决定性条件。

### 1.2 理由 2：简单性刻度全绿（架构性）

按 02 清单四刻度评估 v0.3.5 的简单性影响：

| 刻度 | 评分 | 证据 |
|---|---|---|
| 交织度（Hickey） | 🟢 守住 | OutlineNode 无 surface 字段；BaseChannel 无 AXAPI/CDP 关键字；UiAction 单一 union（dispatch 按 rootRef 前缀，不按 surface type 分支） |
| 模块深度（Ousterhout） | 🟢 守住 | DesktopChannel 7 契约方法（≤7 上限），构造参数 3 个（<4 上限）；AXAPI 细节隐藏在 Rust helper（depth 厚）；穿堂式方法=0 |
| 变更放大率（Ousterhout） | 🟡 中等风险 | 加新通道 >5 处（BaseChannel 注册 + CapabilityBag + FallbackPlan + doctor + 不变量测试 + Subprocess Manager + 工具族），但加通道是稀有事件，固有成本接受；加新工具 ≤3 处的验证标准单独守住 |
| 概念完整性（Brooks） | 🟢 守住 | 同一 fallback 范式 / 同一状态模型 / 同一工具描述风格 / 同一 InteractTask 形状 / 同一 OutlineNode 序列化 |

**在 v0.3.5 落地而非更晚**的理由：越晚插入，browse 通道的 BaseBrowseChannel 形状越容易被业务特化（SERP selector / snapshot YAML / expect_login），届时再加 desktop 要么污染 BaseChannel（R-CI-02 红线破坏）要么被迫继承 BaseBrowseChannel（更糟）。**早插=抽象成本最低**。

### 1.3 理由 3：用户需求强度（战略）

用户 MEMORY 锚点明确："macOS AXAPI 无视觉路线是重点自建方向（契合 Rust 背景）"。这一条把 desktop 从"可选扩展"提升到"用户核心诉求"。结合：

- cc-control-all 02 文件调研结论：macOS AXAPI 无视觉路线是重点自建方向
- 用户背景：Rust/Tauri + macOS（Rust helper 一人维护可行；Swift helper 是 6 个月支线，v1 不做——F3.10.13）
- 双子星叙事完整化：media-gen-mcp（图像生成+识别）↔ Lasso（外部交互：浏览器+桌面）
- **09 附录 2 "multi-root forest 永远不进 / AX outline 永远不进"两条判断被本方案推翻**（web-only 领域错位前提不再成立）

**推迟到 v0.4+ 的代价**：若 desktop 留到 v0.5+ 才做，v0.6 动态启停的演示价值减半（只能 demo browse/cloud 启停，少了"打开/关闭桌面通道"这种最直观的场景）；v0.7 doctor CLI 也少了 desktop 检查项的完整化窗口。

### 1.4 为什么不是更早或更晚

- **不进 v0.1**：v0.1 已锁定 3 工具 + 单 fallback 骨架（pi 修正后 +5 项已满载）；加 desktop 会让 v0.1 从"3 通道 MVP"变成"4 通道半成品"，违反"每阶段可独立交付与验证"原则
- **不进 v0.2**：v0.2 是 search 深化（Brave + cache），与 desktop 无依赖关系也无概念重叠；强行合并会让单阶段承担两个不相关能力跃升
- **不进 v0.3**：v0.3 是多步链式（CC 把 5 次调用压成 1 次），核心交付是 steps DSL + expect + StateStore；这些是 desktop 的依赖前置，必须先稳定
- **不延后到 v0.5**：v0.5 是工具集扩展（fetch/screenshot/pdf/network），与 desktop 平级而非递进；延后会让 desktop 错过 v0.6 动态启停演示窗口
- **不延后到 v1.0**：v1.0 是稳定发布（跨平台 + 文档 + npm publish），desktop 在 v1.0 才进等于 macOS-only 能力强行跨平台，违反"v1.0 跨平台"目标；desktop 必须在 v1.0 之前至少有 1 个版本的 macOS 实战验证

### 3.4 验收标准（量化）

**M0.5a Observe-Only 验收**：
- [ ] `desktop_snapshot(app:"Finder")` 返回 stateId + outline 树（maxDepth=3 时节点数 ≥20）
- [ ] `desktop_find(stateId, where:{text:"新建文件夹"})` 在 Finder 快照中正确返回 @eN 或 []
- [ ] AX→OutlineNode 映射覆盖率 ≥80%（采样 10 个常见 native app：Finder/Mail/Safari/Xcode/系统设置/Notes/Calculator/Terminal/Preview/Calendar，每个采 3 个 window）
- [ ] desktop_snapshot 中位延迟 ≤30ms（native app, maxDepth=3；desktop-pilot 20ms 是目标，30ms 是 MVP 可接受线）
- [ ] `desktop_doctor` 检查 ≥6 项（AX 授权 / Screen Recording 授权 / Rust helper 进程 / Developer ID 签名状态 / AX 可读率 / media-gen-mcp vlm provider 可达性），返回结构化 JSON + blockers + next_step
- [ ] TCC 首次启动引导：检测到未授权 Accessibility 时返回 `{readiness:"blocked", blockers:["tcc:accessibility"], next_step:"open x-apple.systempreferences:com.apple.preference.security?Privacy_Accessibility"}`
- [ ] Rust helper Developer ID 签名后，rebuild 不再重弹 TCC 授权弹窗
- [ ] 架构不变量 F3.9.9 (a)(c)(d)(e)(f) 5 项通过

**M0.5b Act + Fallback 完整验收**：
- [ ] `desktop_act(stateId, actions:[{kind:"click", ref:"@e3"}])` 在 Mail 中点击"新邮件"按钮，窗口出现新邮件 → outcome="worked"
- [ ] `desktop_act` 在 Electron app（如 VSCode）AXSetValue 失败时，自动降级到 cgEvent 档点击 → outcome="worked"，`fallback_used:"cgEvent"`
- [ ] `desktop_act` 在 canvas/Metal app（如 Sketch 画布区域）AX 完全无 element 时，降级到 screenshotVlm 档识别坐标 → outcome="worked"，`fallback_used:"screenshotVlm"`，节点标 `pictureOnly:true`
- [ ] `desktop_act` 在 scriptable app（Finder）AX 表达不全时，降级到 appleScript 档（typed action enum，非 raw 脚本）→ outcome="worked"，`fallback_used:"appleScript"`
- [ ] `desktop_wait(stateId, condition:{appFrontmost:"Mail"}, timeoutMs:3000)` 在 Mail 已前台时返回 "preexisting"（tri-state 诚实报告，条件本就成立）
- [ ] `desktop_screenshot(ref:"@e5")` 返回 base64 PNG，仅对 pictureOnly 节点有效
- [ ] 典型原生 app 操作成功率 ≥85%（采样：Finder 新建文件夹 / Mail 发邮件 / Safari 打开书签 / 系统设置切换 WiFi / Notes 新建便签 各 10 次）
- [ ] fallback 触发率可观测（每档 fallback 总次数 / app 维度分布，audit log 可查）
- [ ] 60s 短熔断：模拟 axProvider 连续失败 5 次，60s 内不再尝试 ax 档
- [ ] Argus 60min 长熔断：模拟 desktop 通道 1 小时内 10 次失败，60min 内整个 desktop 通道熔断（**不 fallback 到 browse**——F3.9.9(h)）
- [ ] 架构不变量 F3.9.9 全部 8 项通过（含 (b)(g)(h)）
- [ ] audit log 写入 `~/Library/logs/<mcp>/audit.log`，含 run_id / fallback 链 / tri-state outcome / 10MB 轮转
- [ ] headless:true 模式下，`desktop_act` 拒绝任何 activate/raise/focus/cursor/raw input 调用，返回 `{outcome:"didnt", reason:"headless_mode_boundary"}`

### 3.5 实现要点（借鉴哪个范式）

1. **DesktopChannel 镜像 BaseBrowseChannel 的 7 契约方法**：is_available / status / capabilities / observe / act / wait / health_check；关键差异是 dataModel 字段（`"ax"` vs `"dom"`，**仅描述不参与路由**）
2. **Rust helper 复用 pi Windows bridge 的 stdin/stdout JSON-lines 协议**：挂现有 Subprocess Manager（F3.5.x），不开第二套进程管理；helper crash 后复用 v0.2 的指数退避重启
3. **AXUIElementCopyMultipleAttributeValues 批读**：一次读 6 属性（role/title/position/size/enabled/focused），这是 desktop-pilot 20ms 快照的 perf 来源；不批读则降到 200ms+
4. **AppleScript typed action enum 借鉴 mac-mcp OSAKit 路径**：osakit crate（不 spawn osascript 子进程，避免每次启动开销）；sdef 检测判断 scriptable app，决定 Layer 2 是否值得走
5. **screenshotVlm 档复用 media-gen-mcp vlm provider**：双子星协同；调 media-gen-mcp 的 describe_image / extract_text 工具，传入 base64 截图 → 返回 element 坐标
6. **CapabilityBag 同构 media-gen-mcp 0.10.0**：4 providers 各声明 `{canObserve, canAct, priority}`；getFallbackChannel 按能力袋+优先级选下一档（与 browse 同一函数，F3.9.9(c)）
7. **ToolAnnotations 复用 v0.1 F3.3.13 四象限**：`desktop_act` 标 `openWorld: true, destructiveHint: true`（与 browse_logged_in 同等级风险）
8. **CC 工具描述内嵌路由提示**：6 desktop 工具 description 明确"何时用 desktop_* vs browse_*"（08 附录 C/G 模板）

### 3.1 内联差异率分析（必须先做才能定 forest 是否值得）

| 原语 | CDP（browse） | AXAPI（desktop） | 共享? |
|---|---|---|---|
| navigate | `Page.navigate` | `AXSetValue`/AppleScript `activate` | 语义同, 实现异 |
| click | `Input.dispatchMouseEvent` | `AXPress` | 语义同 |

### 3.2 v0.1 抽象同构（Day 1 就做）

```typescript
// OutlineNode 统一形状（DOM 和 AX 都映射成这个）
interface OutlineNode {
  role: string             // "button"/"link"/"textfield"/"window" 等 (DOM role 或 AX role 标准化)
  label: string            // 可见文本 (DOM) 或 AX title
  ref: string              // @eN (element ref, scope=stateId)
  rect: {x,y,w,h}          // bounding box (坐标动作兜底用)
  children?: OutlineNode[]
  pictureOnly?: boolean    // pi 关键概念: 有视觉证据但无 AX/DOM element
  // 注: 没有 surface 字段——那是内部 metadata, 不进 model 接口
}

// InteractTask 形状 (browse+desktop 共享)
interface InteractTask {
  rootRef: string          // v0.1: browse 用 @pN, desktop 用 @wN (双空间)
                           // v0.4+: 共享 nextRootRefIndex 计数器
  stateId: string          // StateStore<OutlineSnapshot> key
  actions: UiAction[]      // 共享 UiAction union
  expect?: ExpectCondition // 复用现有 expect 范式
}

// UiAction union (双 dispatch path, 单一形状)
type UiAction =
  | {kind:"click", ref:@eN}
  | {kind:"type", ref:@eN, text:string}
  | {kind:"press", key:string}
  | {kind:"scroll", ref:@eN, dx:int, dy:int}
  | {kind:"hotkey", keys:string[]}
  // dispatch by rootRef 前缀: @pN→CDP, @wN→AX
```

## 6. 简单性自检（诚实标注风险）

### 6.1 四刻度评分

| 刻度 | 评分 | 证据 |
|---|---|---|
| **交织度（Hickey）** | 🟢 守住 | OutlineNode 无 surface 字段；BaseChannel 无 AXAPI/CDP 关键字；UiAction 单一 union；dispatch 按 rootRef 前缀不按 surface type 分支 |
| **模块深度（Ousterhout）** | 🟢 守住 | DesktopChannel 7 个契约方法（<7 上限），构造参数 3 个（<4 上限）；AXAPI 实现细节隐藏在 Rust helper（depth 厚）；穿堂式方法=0 |
| **变更放大率（Ousterhout）** | 🟡 中等风险 | 加新工具：tool def + handler route + invariant test = 3 处（≥5 才告警，守住）；**加新通道：>5 处**（BaseChannel 注册 + CapabilityBag + FallbackPlan + doctor + 不变量测试 + Subprocess Manager + 工具族），这是真实风险，但加通道本就是稀有事件 |
| **概念完整性（Brooks）** | 🟢 守住 | 同一 fallback 范式 / 同一状态模型 / 同一工具描述风格 / 同一 InteractTask 形状 / 同一 OutlineNode 序列化 |

### 6.2 第二套做法红线（R-CI-02）逐项核验

| 维度 | browse 通道 | desktop 通道 | 是否第二套？ |
|---|---|---|---|
| fallback 范式 | isFallbackWorthy/getFallbackChannel/activeProvider | **同一函数** | 🟢 否 |
| 状态模型 | InteractTask/stateId/expect/StateStore LRU(128) | **同一类型** | 🟢 否 |
| 工具描述风格 | BrowseOptions + ToolAnnotations + `[Prefer X]` | **同风格**（DesktopOptions 同构） | 🟢 否 |
| 熔断策略 | 60s 短 + Argus 60min 长 | **同一 CircuitBreaker** | 🟢 否 |
| tri-state outcome | worked/didnt/unknown | **同一枚举** | 🟢 否 |
| 日志/配置/生命周期 | 现有 Subprocess Manager + ProviderConfig 注册表 | **同一套** | 🟢 否 |

### 6.3 风险标注（不回避）

**🟡 中等风险**：

1. **双数据模型（DOM/AX）**是最大复杂度风险点。OutlineNode 抽象能否真正覆盖 AX 的特殊概念（`AXMenuItem`/`AXMenuBar`/`AXPopover`）需在 v0.x 实现时验证。**缓解**：若 AX role 无法干净映射到 DOM role 标准，允许 OutlineNode 加 `axRole?` 内部字段（仅 debug 用，不进 model 接口）。

2. **Rust helper 工程量**。用户熟悉 Rust 但 `accessibility`/`osakit` crate 生态不熟（"读着费劲"但不等于结构缠绕，防偏差 #1）。**缓解**：v0.x 先实现 `desktop_snapshot`+`desktop_find` 两个工具（observe-only），验证 AX→OutlineNode 映射后再加 `desktop_act`。

3. **变更放大率 ≥5**（加新通道要触及 >5 处）。**缓解**：这是加通道的固有成本，不是架构问题。验证标准：加新工具（不是新通道）应 ≤3 处。

**🔴 红线（必须守住）**：

- BaseChannel 不能加 `mode:"web"|"desktop"` 参数（错误抽象退化起点）
- CapabilityBag 不能加 `if surface==desktop` 分支
- 不能为 desktop 写第二个 fallback engine / 第二个状态模型 / 第二套工具描述风格
- AXAPI 关键字不能进 BaseChannel 基类（grep 跨模块命中即🔴）
- 不能跨 surface fallback（desktop 失败 fallback 到 browse 是参数蔓延信号）

### 6.4 holistic 适应度函数补位（01 §2.6）

新增适应度函数（CI 断言，F3.9.9(i)）：

> **"fallback 链不得跨 surface 类型"**——desktop 的 4 档 fallback 必须全部在 desktop 内部，不能 fallback 到 browse；反之亦然。这是模块级刻度覆盖不到的系统级耦合度量。

## 总结：本方案守住简单性的三个关键决策

1. **抽象同构先于工具统一**（v0.1-v0.3 不做 interact_roots，但 day 1 就让 DesktopChannel 和 BrowseChannel 同走 BaseChannel）——避免过早抽象 forest
2. **DesktopChannel 是 BaseChannel 的第三个实现，不是 BaseBrowseChannel 的子类**——避免 BaseChannel 被 AXAPI 污染
3. **4 档 desktop fallback 复用同一 FallbackPlan/CapabilityBag/CircuitBreaker**——不开第二个 fallback engine（R-CI-02 红线）

风险诚实标注：双数据模型（DOM/AX）是最大复杂度风险点，Rust helper 工程量是最大执行风险。两者都有明确缓解路径（observe-only MVP 先行 / `axRole?` 内部字段兜底）。
