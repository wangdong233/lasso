# 方向 C：新奇方案与性能洞察（03）

> 这一章不列具体产品，而是抽「**怎么做才能更快/更省/更准**」的底层洞察——它们是选型背后的物理规律。

---

## 1. ⭐ 最重要洞察：75–94% 的延迟来自 LLM 规划/反思，不是截图

【验证，[arXiv 2506.16042v1](https://arxiv.org/html/2506.16042v1)《OSWorld-Human: Benchmarking the Efficiency of Computer-Use Agents》】

> 「planning and reflection steps, both involving calling LLMs, take the majority of time, **accounting for 75% to 94% of the total latency** across all tasks, and their latencies grow as a task takes more steps.」

测试对象：**Agent S2**（流行的开源 computer-use agent，作者指出其框架具代表性）。

**拆解**：在主流 vision 桌面 agent 里——
- **LLM 规划 + 反思**：占总延迟 **75–94%**
- 截图、坐标定位（grounding）、动作执行：占比极小

**对落地的决定性含义**：
1. 想提速桌面自动化，**「减少推理调用次数 / 用更小的规划模型 / 减少任务步数」远比「优化截图或 grounding」有效**。
2. 这解释了 **browser-use 为什么能在 web 任务上反超截图派 CUA**——它把规划**转成确定性的 Playwright 代码**，一次规划、多次执行，把 LLM 调用压到最少。
3. 别在「更快的截图工具」上纠结，先问「**能不能少调几次 LLM**」。

**可操作的优化杠杆**（按收益排序）：
| 杠杆 | 收益 | 例子 |
|---|---|---|
| 把规划转成确定性代码 | 极高 | browser-use、Stagehand v3 的 replay |
| 用更小的模型做规划/反思 | 高 | 主任务用 Opus，规划用 Haiku |
| 减少任务步数（更好的任务分解） | 高 | 一次规划多步动作 |
| 把页面状态写磁盘而非灌上下文 | 高（token） | Playwright CLI 模式 |
| 更快的截图工具 | 低 | 边际优化 |

## 2. 感知模态选择：a11y tree vs Set-of-Marks（任务相关，没有银弹）

【一手，来自 workflow fetch 的 OSWorld-Human 类研究】

不同「喂给 LLM 看什么」的策略，效果**强依赖于任务类型**：

| 感知模态 | 适合 | 不适合 | 代价 |
|---|---|---|---|
| **可访问性树（a11y tree）** | 元素少/树有助于定位：OS、GIMP、Chrome | 视觉密集应用：LibreOffice | 生成树本身要 **3–26 秒**，且每步**多几千 token** |
| **Set-of-Marks（SoM，截图上叠编号）** | 总体能**减少步数** | — | 要画标记 |
| **纯截图（vision）** | 自绘/Canvas/无 a11y 的应用 | 元素多时 grounding 慢 | 截图 vision 成本 |

**关键反直觉**：a11y tree 不是万能省——**对 LibreOffice 这类视觉密集应用，生成 a11y tree 反而显著拉高延迟**（3–26 秒/次 + 每步多 token）。

**落地含义**：
- 对**网页 / 元素清晰**的应用：优先 a11y tree 或代码驱动（chrome-devtools-mcp / Stagehand）。
- 对**自绘 / Canvas / Office** 类：用 Set-of-Marks 或纯 vision。
- **混合策略**最优：按 app 类型动态切换感知模态。

## 3. 真正「寄生」的本地模型路线 — 现状是空白，但方向值得盯 ⚠️

你的原始直觉里最激进的一条：「**agent 直接寄生在浏览器进程里，还用本地模型**（WebLLM / Gemini Nano / Service Worker）」。这是理论上**效率最高**的形态（同进程、零 IPC 往返、零 API 费用、隐私）。

**本轮调研的诚实结论：没找到成熟的可验证代表**（synthesize 报告 caveats #4 + 开放问题 #1）。现状：

| 候选 | 机制 | 现状 |
|---|---|---|
| **WebLLM**（[mlc-ai/web-llm](https://github.com/mlc-ai/web-llm)） | WebGPU 在浏览器里跑 LLM | 能跑，但作为「浏览器 agent 的决策大脑」未成熟；模型能力远弱于 Opus |
| **Chrome 内置 Gemini Nano** | 浏览器原生本地模型 API | 能力极有限（~小模型），做不了复杂 agent 规划 |
| **Service Worker agent** | 在 SW 里常驻 agent 逻辑 | 可行但无成熟框架，要自己造轮子 |

**为什么这条路线有潜力但仍空缺**：
- 本地模型（浏览器内）能力不足，撑不起长程规划。
- 没人把「Service Worker 常驻 agent + 本地小模型 + 可选云端升级」做成成品。

**可作为后续探索方向**：如果你想做一个真正差异化的项目，「**浏览器扩展常驻 agent + 本地小模型 + 必要时调用 CC/云端**」仍是有空间的空白区——但这是自建项目，不是现成方案。

## 4. DOM → 结构化上下文压缩（省 token 的通用套路）

所有省 token 的高级方案都在做同一件事：**不要把原始 DOM/截图灌进 LLM 上下文，先压缩**。

| 方案 | 压缩方式 |
|---|---|
| Playwright CLI | 快照写磁盘 YAML，上下文只拿文件路径 |
| Stagehand | DOM → a11y tree |
| chrome-devtools-mcp `--slim` | 精简工具集 + 结构化返回 |
| browser-use | 规划转成 Playwright 代码（执行时无 LLM） |
| OmniParser | 截图 → 结构化元素 token |

**通用模式**：`原始页面 → 结构化/持久化表示 → 上下文只拿指针或最小摘要`。

## 5. 云浏览器（无头后端）

代表：[Browserbase](https://www.browserbase.com/)。serverless 无头云浏览器，支持 Playwright/Puppeteer/Selenium + CDP，无需本地 GUI——直接服务「后台无头」目标，是 Stagehand / Skyvern 的默认后端。

**唯一大坑**：**2FA / 登录处理失败率约 60%**（Skyvern 测试 10 次失败 6 次）。
- 登录态不重要的任务（公开数据爬取）→ 云浏览器很合适。
- 需要登录的任务 → 别用云浏览器，改本地 Chrome + `--browser-url` 或 Claude in Chrome。

---

## 6. 投屏 + 视觉（移动/远程设备控制）⚠️ 通识

对于「控制手机 / 远程设备」：
- **scrcpy**（Android 投屏 + 控制）+ 视觉模型 → 可做 Android 自动化。
- **ffmpeg** 抓屏 + 视觉 → 远程桌面控制。
- 配合 Anthropic CU API 的 agent loop，可驱动任意「能截图 + 能发鼠标键盘」的目标。

这些没有成熟的开箱 CC 集成，属于「自己拼」的范畴，本轮未深验证。

---

## 7. 自建桌面 MCP server 生态

CC 的 MCP 客户端能接任何 MCP server，所以另一条路是**把你要控制的东西包成 MCP server**【验证，CC MCP 文档】：
- 社区已有：apple-notes-mcp、filesystem-mcp、各种 SaaS 连接器。
- 自建模式：用 MCP SDK 把你的内部工具/API 暴露给 CC，比 computer use 精确得多、可无头。
- 这是「connectors 优先级最高」的实际落地——能做成 MCP 连接器的，就别用 computer use。

---

## 8. 开放问题（综合）

1. **是否存在成熟的「同进程寄生 + 本地模型」浏览器 agent？** 本轮没找到——这是理论上效率最高但实践空缺的形态，可作为自建项目方向。
2. **CC 内置 computer use 能否强行无头？** 用 Xvfb + 远程桌面能不能绕过「隐藏其它窗口 + 仅前台已批准 app」的产品约束？这对无人值守部署是关键。
3. **Claude in Chrome 与 CC 的通信通道**未明确（native messaging / stdio / MCP / WebSocket）——决定登录态复用稳定性与跨域。
4. **代码驱动 vs 视觉驱动的真实美元成本对比**缺失——同类长程任务上 dollars/task 谁更低？这比延迟数字更决策性。
