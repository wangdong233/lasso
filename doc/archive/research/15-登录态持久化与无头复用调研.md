# Lasso 登录态持久化与无头复用调研报告

> **用户问题**：Lasso 能否做到 login-once → 登录态持久 → headless 无头复用（如小红书）？开源怎么做的？
>
> **证据基线**：Lasso 源码（`lasso/src/logged-in/` + `src/channels/` + `src/launcher/`）逐行核对 + 4 簇开源调研 findings（小红书自动化生态 / Playwright storageState / stealth 现状 / 法律边界）。
>
> **成文**：2026-07-22

---

## 0. TL;DR（直接回答）

1. **「login-once → 持久 → 复用」的闭环 Lasso 已经有，但物理边界是「同一台可见 Chrome（:9222）」**——`browse_logged_in` 复用用户已登录的本机 Chrome + v0.8 `CookieStore`（AES-256-GCM 加密落盘）+ `ProfileRegistry`（多 profile user-data-dir 配置）已构成「登一次 → cookie 持久 → 关 Chrome 重启/换机器后 import 复用」的链路。**这一层已满足「login-once」的字面语义**，且是业界最稳的「活体复用」哲学（与 `xpzouying/x-mcp` 浏览器插件派、`browser-use Browser.from_system_chrome()` 同路）。

2. **「login-once → 持久 → headless 无头复用」Lasso 目前做不到**——`HeadlessChannel` 源码注释明写「干净、隔离的 headless Chromium——无登录态、无 cookie 持久化」（`HeadlessChannel.ts:4-6`），`cookie_restore` 的 import 目标锁死在 :9222 的可见 Chrome（`LoggedInChannel.ts:240,278` 的 `new CdpClient(this.cdpPort)`，`cdpPort` 默认 9222）。headless 子进程由 chrome-devtools-mcp 内部独占，不暴露 WebSocket debugger URL，`CdpClient` 无路径可达。**这是架构性 gap，不是 bug。**

3. **对小红书这类强风控站点，即使补上 headless cookie 注入，cookie-only 也不够**——业界主流（`yangsijie666/xiaohongshu-crawler`、`NanmiCoder/MediaCrawler`）是 `storage_state`（cookie+localStorage）+ 固定指纹（user-data-dir 或 browserforge）+ stealth 补丁 + 行为延迟 + 滑块回环，且默认 `headless=false`。强风控站点的 headless 复用价值有限、寿命 1-7 天、且有明确 ToS/法律风险。

4. **诚实结论**：不推荐为「小红书 headless 复用」专门加路线。Lasso 现状 `browse_logged_in` 已是最适合这类站点的形态（复用真实 Chrome 活体，天然带完整指纹/扩展/历史，反检测最强）。若未来要扩 headless 复用，应走路线 3（`launchPersistentContext` + user-data-dir + stealth），但明确止步于「真实浏览器驱动 + 状态持久」，**不碰签名纯算（刑事红线），不鼓励反风控军备竞赛**。

## 1. 用户场景拆解 + 关键技术约束

### 1.1 场景拆解

用户说的「login-once → 登录态持久 → headless 无头复用」实际是三个动作的链：

| 阶段 | 动作 | Lasso 对应 | 状态 |
|---|---|---|---|
| ① login-once | 可见浏览器扫码/账密登录（含 2FA）一次 | `lasso launch-chrome` + 人工登录 | ✅ 已支持 |
| ② 持久 | 登录态落盘（跨重启/跨机器可恢复） | `admin cookie_restore op=export` → `CookieStore` AES-256-GCM 落盘 | ✅ 已支持（cookie 子集） |
| ③ 复用 | 后续无需重登直接访问受保护页 | **a. 灌回可见 Chrome :9222** ✅ / **b. 灌进 headless 无头 Chromium** ❌ | 半支持 |

关键歧义点：用户说的「复用」到底是 ③a（还用那台可见 Chrome）还是 ③b（真正的无头无人值守）？这两个的工程难度和风控后果差一个量级。

### 1.2 五条关键技术约束（决定成败）

1. **session cookie 失活**：未带 `expires` 的 cookie 默认随浏览器进程结束而失活。即使持久化到磁盘，Chrome 默认不在下次启动复活 session cookie（chromium.org headless-dev 群帖原文 "Headless Chrome does not remember cookies from previous instances"）。需 `--restore-last-session` 或把关键 cookie 强制带 `expires`。**Lasso 的 `CookieStore` 把 cookie 元数据（含 `session` 字段）都存了，但 import 时 `toSetCookieParams` 透传 `expires?`——对 session cookie（`expires` 为空）灌回后是否长期有效，取决于服务端 TTL，不是客户端能控制的。**

2. **HttpOnly cookie**：JS `document.cookie` 永远拿不到 HttpOnly cookie（多数 sessionid 是 HttpOnly）。Lasso 走裸 CDP `Network.getAllCookies` 能拿全（含 HttpOnly），这点是对的。但开源届用 `evaluate_script` 读 cookie 的方案（parse9 §3.1 已论证跑在 page context 无法调 `Network.*` 域）会静默丢 HttpOnly——Lasso 没踩这个坑。

3. **localStorage / sessionStorage / IndexedDB / ServiceWorker**：现代 SPA（Firebase Auth、AWS Cognito、很多 React/Vue 应用、小红书部分 token）把 JWT/refresh token 存在这里。**cookie-only 方案对这类站点直接失效**。Playwright 官方 auth 文档虽然写 "covers cookies, local storage and IndexedDB based authentication"，但多个权威社区源证实 `storageState` 实际只序列化 cookies + localStorage，**不含 IndexedDB/sessionStorage/ServiceWorker**（Stack Overflow Firebase 鉴权失败案例原文 "Playwright currently only stores cookies when saving storageState"）。**这是 Lasso 当前最深的语义 gap——用户期望「登录态」，实得「cookie 子集」。**

4. **设备指纹绑定**：强风控站点（小红书 `xsec_token`、`a1`/`webId` 指纹种子）把 session 与「设备指纹 + IP + 行为」强绑定。把 cookie 注入到不同指纹的 headless（不同 UA/Canvas/WebGL），服务端做会话-指纹校验立即失败，典型表现：重定向滑块验证码页、461/403、限流、长期触发封号。**小红书 `web_session` 与当前 IP/环境绑定是公开记录（知乎专栏文章实证）。**

5. **行为风控**：均匀请求间隔被识别为机器人，需 ±30% 随机抖动；频繁抓取触发滑块（数美）；同账号网页多端登录会互相踢（xiaohongshu-mcp README 原话 "不要再在其他网页端登录该账号，否则会把当前 MCP 的账号踢出登录"）。

| 复用可见 Chrome（:9222 attach） | `LoggedInChannel.ts:120-128` `ensureProfileSpec` | `chrome-devtools-mcp --browser-url=http://localhost:9222` | ✅ 已具备 |

| **headless 复用登录态** | `HeadlessChannel.ts:4-6` | 源码注释明写「无登录态、无 cookie 持久化」；`HeadlessChannel` 零引用 `logged-in/` 任何模块 | ❌ **gap（架构性）**：headless 子进程是 chrome-devtools-mcp `--isolated` 内部独占的干净 Chromium，CDP 端口不暴露，`CdpClient` 无路径可达 |
| **cookie_restore 注入 headless** | `LoggedInChannel.ts:240,278` | `new CdpClient(this.cdpPort)`，`cdpPort` 默认 9222，与可见 Chrome 同一进程 | ❌ **gap**：注入目标是可见 Chrome :9222，**不是** headless 子进程 |
| **localStorage/IndexedDB 捕获** | `CdpClient.ts:130-158`（仅 3 方法 `getAllCookies`/`setCookie`/`close`） | 全仓 grep `DOMStorage\|localStorage\|sessionStorage\|IndexedDB` 命中 0 条 | ❌ **gap（语义层）**：用户期望「登录态」，实得「cookie 子集」。parse9 设计阶段未将 DOM storage 列入 F3.3.9-10 范围 |
| 2FA 检测（不解 2FA） | `LoggedInChannel.ts:157-187` `_detect2FA` + 附录 B `BROWSE_LOGGED_IN_DESCRIPTION` | 命中关键词 → `NEEDS_MANUAL_2FA`，fallback 引擎识别后终止链 | ✅ 已具备（铁律：不解 2FA） |
| headless → logged_in fallback | `FallbackDecider.ts:36` | headless 失败**重试**到 logged_in 通道（顺序 retry），**不是** headless 继承 logged_in 的 cookie | ⚠️ 常被误读为「cookie 跨通道」，实为 retry |
| high-risk gate（身份风险） | `LoggedInChannel.ts:213-215` `createHighRiskGate` | 仅 logged_in 启用（携带身份 → 风险高）；HeadlessChannel 不重写（走默认 null） | ✅ 已具备（且反证 headless 不带身份的设计意图） |

### 核心结论

**Lasso v0.8 的登录态持久化是「单通道闭环」**——`browse_logged_in` 自身的 login-once → cookie AES 加密落盘 → import 灌回同一可见 Chrome。headless 通道被**故意**排除在登录态之外（`HighRiskGate` 只在 logged_in 启用就是设计意图的反证）：cookie=身份（parse9 §1.3），让一个无头无观察的进程携带用户身份运行，违反 logged_in 的 human-in-the-loop 隐含前提。**目前没有任何代码注释或 parse 文档把「headless 不接 cookie」显式写成红线**（建议补一条 INV 把这个意图固化）。

### 3.1 小红书自动化三大流派

| 流派 | 代表项目 | 登录态持久化载体 | headless 可行性 | License |
|---|---|---|---|---|

### 3.2 通用层（非小红书专属）持久化范式

| 路线 | 代表 | 捕获范围 | 复杂度 | Lasso 对应 |
|---|---|---|---|---|
| ① Playwright `storageState` | Playwright 官方 auth / browser-use | cookies + localStorage（**不含 IndexedDB/sessionStorage/SW**） | 极低（3 行） | 无 |
| ② `launchPersistentContext(userDataDir)` | Puppeteer/Playwright / chrome-devtools-mcp 非 isolated 模式 / Steel / Kernel / Browserbase | **全 profile**（cookies+LS+IDB+SW+扩展+密码） | 低 | 无（ProfileRegistry 配置层就绪但 D-v08-1 架空） |
| ③ Chrome `--user-data-dir` 裸 CDP | Browserless 博客 / **Lasso `browse_logged_in`** | 同 ② | 中 | ✅ `browse_logged_in` 已是此路线 |
| ④ CDP `Network.setCookie` 注入 | Puppeteer `browser.setCookie` / **Lasso `cookie_restore`** | 纯 cookie | 中 | ✅ `cookie_restore` 已是此路线 |
| ⑤ 浏览器扩展导出 | EditThisCookie / Cookie-Editor | 纯 cookie（**含 HttpOnly**） | 极低（UX 差） | 无 |

### 3.3 关键观察

- **业界共识**（browser-use 文章原文证实 Steel/Kernel/Browserbase）：复杂登录态选 userDataDir，简单 cookie 鉴权选 storageState，**没有一家靠裸 CDP setCookie 做主路线**。Lasso 当前 `cookie_restore`（路线 ④）是 cookie-only 里最严谨的（AES-256-GCM + Keychain），但捕获面窄。
- **最优雅的 login-once** 是浏览器插件派（`x-mcp`）——不持久化快照，直接复用活体。**Lasso 的 `browse_logged_in`（复用本机已登录 Chrome）本质就是同一哲学**，只是用 `--browser-url` attach 而非插件注入。
- 首次登录几乎必然要在可见浏览器完成（扫码/滑块/2FA 都要人）；headless 登录替代方案是手机号+短信验证码（MediaCrawler `login_by_mobile` / xiaohongshu-mcp-pro），把 SMS 码经 redis/缓存中转——但仍需人工收码。

## 4. 技术现实：cookie-only vs user-data-dir vs stealth

### 4.1 捕获面对比（诚实表）

| 维度 | ① storageState | ② launchPersistentContext | ③ --user-data-dir | ④ CDP setCookie（Lasso 现状） |
|---|---|---|---|---|
| cookies（含 HttpOnly） | ✅ | ✅ | ✅ | ✅ |
| localStorage | ✅ | ✅ | ✅ | ❌ |
| sessionStorage | ❌ | ✅ | ✅ | ❌ |
| IndexedDB（Firebase Auth 等） | ❌（关键短板） | ✅ | ✅ | ❌ |
| ServiceWorker | ❌ | ✅ | ✅ | ❌ |
| 跨浏览器复用 | ✅（中立 JSON） | ❌（Chrome 锁定） | ❌ | ✅ |
| session cookie 跨重启复活 | N/A | ⚠️ 默认不复活，需 `--restore-last-session` | ⚠️ 同左 | ✅（可强制 expires） |
| 指纹稳定性 | 低（每次新 context） | **高**（profile 锁指纹） | **高** | 低 |

### 4.2 强风控站点的现实（小红书为典型）

对小红书，**cookie-only 注入 headless 大概率触发风控**。完整链需要四件套：

1. **`storage_state`**（cookie + localStorage，不是单纯 cookie）——CSDN 实战文章明确指出「注意不要关闭浏览器，浏览器一关 cookie 就失效了」，暗示 cookie 与运行时上下文（localStorage 里的 `xhsTrackerId`/`timestamp2.sig`）有隐性绑定。
2. **固定指纹**（user-data-dir 或 browserforge 生成一致 UA/Canvas/WebGL）——`a1` cookie（52 位）是设备指纹种子，`webId` 由 `a1` 派生，`xsec_token` 与指纹强绑定。
3. **stealth 补丁**——2026.4 scrapewise 基准：JS-patch（puppeteer-stealth/playwright-stealth）已基本失效，二进制级 patch（Patchright/Camoufox）才能过 Cloudflare Enterprise；但**小红书主防线是签名+指纹不是 TLS**，所以 `playwright-stealth + browserforge` 低频可用（yangsijie666 实证），Patchright/Camoufox 是 over-engineering。
4. **行为延迟**（笔记间 2-5 秒随机，搜索间 3-8 秒，±30% 抖动）——均匀间隔必被识别。

### 4.3 stealth 2026 现状速记

| 方案 | 类型 | 强风控通过率 | 状态 |
|---|---|---|---|
| `puppeteer-extra-plugin-stealth` | JS-patch | Cloudflare Enterprise ✗ | **2023.3 后停更** |
| `playwright-stealth` v2.0.2（2026.4） | JS-patch | ✗ | 仍维护，天花板是 JS 层 |
| Patchright | Chromium 二进制 patch | ✓ 多数过 | 活跃，Node 栈首选升级 |
| Camoufox | Firefox fork C++ patch | ✓✓ 0% 检测率 | 单次挑战 42s，小团队维护 |

**对小红书的映射**：签名是主防线，浏览器指纹次要。Lasso 若要做，`playwright-stealth + browserforge` 低频够用，但需配套滑块回环（检测到 `/web-login/captcha` 重定向 → 上抛 `needs_interaction` → 用户手动过滑块 → 刷新 storage_state）。

## 5. Lasso 能否做到 + 三条路线

### 路线 ① 现状已够（`browse_logged_in` 复用本机 Chrome 即「login-once」语义）

- **做法**：什么都不加。`lasso launch-chrome` → 人工登录 → `browse_logged_in(url)` 直接复用 :9222。需要跨重启则 `admin cookie_restore op=export/import`。
- **工作量**：0（已交付）。
- **收益**：反检测最强（真实活体 Chrome，全指纹/扩展/历史/IndexedDB 天然完整），ToS 风险最低（等价用户手动浏览）。
- **风险**：不能无人值守（Chrome 必须开着）；多 profile 物理隔离需用户手动启停（D-v08-1）。
- **适合场景**：**绝大多数 authenticated browsing**（GitHub/Jira/internal tools/小红书低频采集）。这是业界 `x-mcp`/`browser-use from_system_chrome` 的主流哲学。

### 路线 ② 补 cookie_restore → headless（cookie-only 注入，轻但风控脆弱）

- **做法**：给 `HeadlessChannel` 加 cookie 注入点。需先解决架构 gap——chrome-devtools-mcp `--isolated` 内部 Chromium 的 CDP 端口不暴露，三条修复路径：(a) 改 upstream 透传 port；(b) headless 也走 `--browser-url` 模式 lasso 自管 Chrome；(c) 通过 `evaluate_script` 用 `document.cookie`（只能拿 non-httpOnly，parse9 §3.1 已否决）。
- **工作量**：中（需改 chrome-devtools-mcp 或自管 headless Chrome spawn）。
- **收益**：轻量，对纯 cookie 鉴权的老站点（PHPSESSID/JSESSIONID/GitHub sessionid）有效。
- **风险**：**对现代 SPA（Firebase/Cognito/小红书）直接失效**（localStorage/IndexedDB 盲）；指纹 mismatch 触发风控；违反 INV-52 精神（让无头进程携带身份）。
- **适合场景**：窄（仅纯 cookie 鉴权 + 公开/弱风控站点）。**不推荐作为主路线。**

### 路线 ③ 补 user-data-dir 全 profile 持久 + stealth（重但业界主流，强风控站点必需）

- **做法**：headless 走 `launchPersistentContext(userDataDir=<lasso-managed-dir>)`，Lasso 自己管 profile 目录（仿 chrome-devtools-mcp 的 `~/.cache/.../chrome-profile-{channel}/`）。补 `storageState` 全量序列化（cookie+localStorage+sessionStorage）。强风控站点叠加 `playwright-stealth + browserforge` + 行为延迟 + 滑块回环。
- **工作量**：大（新通道或改造 HeadlessChannel + stealth 集成 + 滑块检测工作流 + e2e 测试）。
- **收益**：覆盖全鉴权载体（含 IndexedDB），指纹稳定，是 Steel/Kernel/Browserbase/browser-use 的生产主路线。
- **风险**：profile 锁（同 userDataDir 不能两进程同时开）；跨机器迁移要搬整个目录（几十 MB～GB）；**反检测军备竞赛是长期债**（stealth 脚本要持续跟版）；**强风控站点 ToS/法律风险显著**（见 §7）。
- **适合场景**：批量无人值守采集强风控站点（小红书/微博/抖音）。**但这是 Lasso 当前定位（抓手 MCP）之外的场景。**

## 6. 推荐路线 + 落地

### 推荐：**路线 ① 为主（现状已够），路线 ③ 仅作 v0.4+ 评估项，路线 ② 否决**

理由：
1. Lasso 定位是「CC 的全交互抓手 MCP」（08 架构 §0），不是爬虫框架、不是反风控引擎。`browse_logged_in` 复用活体 Chrome 已覆盖 authenticated browsing 的绝大多数真实需求。
2. 小红书等强风控站点的 headless 复用，技术可行但**寿命 1-7 天 + ToS 灰区 + 写操作已触 2026.3 高压线**（见 §7），投入产出比差。
3. 路线 ②（cookie-only 注入 headless）捕获面窄 1/3（localStorage/IndexedDB 盲），对现代 SPA 几乎必败，工程上性价比最低。

### 若未来确实要做路线 ③（v0.4+ 评估，非现在做），落地建议

| 落点 | 模块/版本 | 复用关系 |
|---|---|---|
| user-data-dir 物理隔离落地 | 修 `LoggedInChannel.ensureProfileSpec` 的 D-v08-1 偏离：等 chrome-devtools-mcp 支持传 `--user-data-dir` 后补回 args（或自管 spawn） | 复用 `ProfileRegistry`（配置层已就绪，`userDataDir` 字段已建好） |
| headless 全 profile 复用 | 新增 `PersistentHeadlessChannel`（或给 HeadlessChannel 加 `--user-data-dir` 模式），v0.4+ | 复用 `SubprocessManager` lifecycle；**不**复用 `cookie_restore`（路线 ③ 不靠 cookie 注入，靠 profile 持久） |
| storageState 全量捕获 | 扩 `CdpClient` 加 `DOMStorage.getDomStorageItems` / `IndexedDB.*` 域，v0.4+ | 复用 `CookieStore` 的 AES-256-GCM 加密范式（新 `SessionStore` 类） |
| stealth | 集成 `playwright-stealth` + `browserforge`（评估后），v0.5+ | 不复用 Lasso 现有基建（这是新债） |
| 滑块回环 | tri-state `needs_interaction` 上抛（已与 12 F.1 `outcomeAfterCheck` 契合） | 复用现有 tri-state outcome + `ExpectCondition` |
| 登录探活 | 新工作流：访问受保护页 → 检查 302/200 → 失效上抛 | 复用 `browse` 的 `expect.url_contains` |

### MVP 范围（若做）

仅做「user-data-dir 持久 + cookie/localStorage 捕获 + 登录探活」三件，**不做 stealth/签名/滑块自动过**（那是爬虫框架的活，不是抓手的活）。明确文档边界：「Lasso 提供 login-once + 状态持久基建，不保证绕过任何站点风控；headless 复用成功率站点相关，强风控站点建议用 `browse_logged_in`」。

### 与 `browse_logged_in` :9222 的边界（不重复造）

- `browse_logged_in` = 复用**用户本机已开**的 Chrome（活体，`--browser-url` attach）—— login-once 的最优雅形态，**不持久化快照**。
- 路线 ③ headless persistent = Lasso **自己 spawn** 的 headless Chrome + lasso 管理的 user-data-dir —— 无人值守形态，**持久化整个 profile**。
- 两者不重叠：前者要人看着 Chrome，后者要 Lasso 自管 profile。不要把 `browse_logged_in` 改成也走 user-data-dir（破坏现有活体复用语义）。

## 7. 风险 + 边界（法律 / ToS / 伦理）

### 7.1 法律红线（刑事）

**破解小红书加密算法 + 伪造数据请求侵入服务器 + 批量爬取牟利 = 刑事犯罪**。已有判刑案例：三人因破解小红书 App 加密算法、伪造数据请求侵入服务器、非法爬取用户昵称/ID/笔记等核心数据牟利 **653 万元**，被以「非法获取计算机信息系统数据罪」判刑（secrss / ipeconomy 报道）。法院关键认定：**破解加密算法 + 伪造请求是侵入行为**，不同于普通浏览器访问。

**Lasso 红线**：绝不内置签名纯算（`x-s`/`x-t`/`x-s-common` 等逆向 JS）。`Cloxl/xhshow`、`cv-cat/Spider_XHS` 的 execjs 调逆向 JS 路线是刑事高风险，Lasso 不碰。

### 7.2 ToS 灰区（民事/违约）

手动扫码登录后用 Lasso 浏览/采集公开数据：技术上可行，但**可能违反小红书用户服务协议**（明确禁止「通过非官方渠道获取登录凭证」「实际控制多个账号」）。固乔公司被诉案法院认定构成**不正当竞争**（被抓取网站设置技术保护措施 + 商业替代关系）。**用户自担风险**，Lasso 须在产品层显著告知「可能违反站点用户协议，账号有被封风险」。

### 7.3 2026 新增高压线（写操作）

2026-03-10 小红书公告**严格禁止利用技术手段模拟真人进行非真实内容创作或虚假互动**，对「通过 AI 托管工具完成注册、发布、互动」的账号批量封禁（新浪财经报道，「第一批养虾人已被封号」）。

**Lasso 红线**：
- **读操作**（采集公开笔记）：ToS 灰区，用户自担风险，产品须告知。
- **写操作**（自动发布/评论/点赞）：**直接禁止或强制人工确认**。2026.3 后这是明确高压线。`HighRiskGate`（`LoggedInChannel.ts:213-215`）应把写操作类动作纳入 gate。
- **签名破解**：绝不内置（刑事红线）。

### 7.4 伦理边界（Lasso 定位）

**Lasso 是「抓手」不是「破解」**。Lasso 的价值是「让 CC 高效和已登录的浏览器/桌面交互」，不是「绕过站点风控」。不鼓励反风控军备竞赛（stealth 脚本持续跟版是长期债，且违背 Lasso「零侵入跟随上游」原则）。诚实陈述成功率边界：**headless 复用对强风控站点没有保证**，用户若需高可靠性，应回退到 `browse_logged_in` 复用活体。

### 7.5 cookie 持久的有效期限

实战报告：小红书 `web_session` 寿命 1-7 天（取决于使用频率，常用则长，长期空闲会失活）；IP 切换触发失活；签名算法每几个月升级一次（浏览器方案相对免疫，纯算方案需跟版）。Lasso 应提供「登录探活」工作流，失效后提示用户重登，不硬冲。

## 8. 诚实结论

**不为了推销功能而推荐做。**

1. **「login-once → 登录态持久 → 可见 Chrome 复用」Lasso 现状已满足**，且是业界最稳的活体复用哲学（`browse_logged_in` 复用本机已登录 Chrome + v0.8 `CookieStore` AES-256-GCM 加密落盘 + `ProfileRegistry` 多 profile）。这一层覆盖 authenticated browsing 的绝大多数真实需求，ToS 风险最低。**不需要为「login-once」加任何东西。**

2. **「headless 无头复用」对强风控站点（小红书）价值有限**——cookie-only 不够（localStorage/IndexedDB 盲 + 指纹 mismatch 触发风控），补全 user-data-dir + stealth 是大工程且是长期债，寿命 1-7 天，且有明确 ToS/法律风险。**Lasso 当前定位（抓手 MCP）不该承担这个。**

3. **若用户真实诉求是「小红书自动化」**，诚实建议：用 `browse_logged_in` 复用本机 Chrome（活体，反检测最强），接受 Chrome 必须开着的约束；若要无人值守，直接用专用爬虫框架（`yangsijie666/xiaohongshu-crawler` / `NanmiCoder/MediaCrawler`）而非把 Lasso 改造成爬虫——那是不同的产品。

4. **Lasso 的诚实定位**：止步于「真实浏览器驱动 + cookie/profile 持久化基建」，不碰签名纯算（刑事红线），不鼓励反风控军备竞赛（伦理 + 长期债）。路线 ③（persistent headless + stealth）列为 v0.4+ 评估项，**非现在做**，且做前要先回答「这是不是 Lasso 该承担的场景」。

5. **建议补一条架构不变量**（INV）：把「`HeadlessChannel` 不接 `logged-in/` 任何模块、不携带用户身份」显式写成红线。当前是「故意未实现但无文档」，parse10/11/12 roadmap 无相关项。补 INV 能防止未来误改。
