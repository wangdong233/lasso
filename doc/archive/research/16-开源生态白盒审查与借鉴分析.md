## 0. TL;DR（核心结论 + 推荐路线，5 句）

1. **Lasso 的反检测能力是当前最严重的业务短板**——`HeadlessChannel.ts` 全文 38 行无 stealth override，`browse_headless` 默认零反检测注入；`StealthEngine` 只覆盖 4 个 JS 属性（vs 业界标准 16 路），UA 固定 Chrome 120（现已是 13x+），HTTP header 一致性完全空白（sec-ch-ua vs UA 不一致是头号检测点）。**这不是架构债，是业务功能缺失**——CC 用 `browse_headless` 访问真实站点会被基础 bot 检测挡住，「全交互抓手」名不副实。**P0 必须修**。

2. **开源生态对 Lasso 最有价值的 3 项借鉴全部在反检测域**：① `puppeteer-extra-plugin-stealth`（MIT，补齐 12 路 JS 注入）；② Apify `fingerprint-suite/header-generator`（Apache-2.0，生成 UA+sec-ch-ua+sec-fetch-* 完整一致 header 集，堵最大破绽）；③ `patchright` 的启动 flag 思路（Apache-2.0，`--disable-blink-features=AutomationControlled` + 移除 `--enable-automation` 写进 SubprocessManager 启动 args）。三项合计 ~1-2 周工作量，零架构冲突（全在既有 StealthEngine / SubprocessManager 内部增强），license 全兼容。

3. **Steel（Apache-2.0，7458★）是当前最值得新增的通道**——「自托管 Browserbase」，与 Lasso `BrowserbaseChannel` 范式 1:1 同构（REST → wsUrl → chrome-devtools-mcp --browser-url），但可自托管 = 零 per-session 费 + cookie 不出本地（对 INV-48..53 cookie=身份红线极友好）。新增 `SteelChannel extends BrowseChannel`，落地成本 ~3-5 天。Obscura（Apache-2.0，Rust headless + TLS stealth）是次优先级，需先 spike CDP 兼容性 + 渲染保真度再决定是否进 fallback 链。

4. **Kitesurf / Firecrawl / Index 对 Lasso 的净价值有限**——Kitesurf 未开源 + 不能反检测/长认证（踩中 Lasso 两块核心），当前只是 v0.4 cloud tier 的成本档；Firecrawl AGPL + 重型 server（Redis+PG），只能 API 调用且与 Lasso「本机优先」定位重叠低；Index 自带双 LLM agent 循环，与 Lasso「CC 是唯一推理者」哲学根本冲突。**三者均不建议深度集成**，但 Kitesurf 值得等开源后重评。

5. **本报告的推荐路线**：v1.5 修 stealth P0 短板（header-generator + 16 路 evasions + patchright flags）→ v1.6 新增 SteelChannel（自托管 cloud 通道）→ v1.7 doctor 集成 creepjs 回归门禁 + 评估 ObscuraChannel spike → v1.8+ 评估 proxy-chain IP 层 + Lightpanda/Obscura 作为可选高性能后端。**所有推荐项均不破坏 R-CI-02**（全在既有模块内部增强或作为 BrowseChannel 平级兄弟子类），license 全兼容 MIT。

## 2. 用户指定项目深度审查

### 2.1 Kitesurf 无头浏览器（Cloudflare）

**基本信息**（基于 Cloudflare 官方博客 2026-08-06 + Browser Run 官方文档，一手）：

| 字段 | 值 |
|---|---|
| **repo** | **无公开仓库**（博客承诺"open source once ready, hopefully soon"，截至 2026-08-10 仍未开源） |
| **license** | **未公开 / 专有（SaaS 服务条款）**——只能作为 Browser Run 云服务调用，无源码可 Embed |
| **主语言** | Rust（编译到 WASM，跑在 Workers V8 isolate）+ TypeScript（Worker 编排） |
| **定位** | 运行在 Cloudflare Workers V8 isolate 上的**无状态、为 AI agent 定制的浏览器引擎**（非 Chromium fork，从零用 Blitz+Stylo+Boa JS 构建） |

**架构（博客"How we built it"原文）**：Engine（CDP WebSocket + REST）+ PageScript（Dynamic Workers isolate 跑 Blitz+Stylo+Boa）+ PageRenderer（光栅化 JPEG/PNG/PDF）

**对 Lasso 的价值判断：部分有益（中低优先级）**

**架构契合度：极高（接入零摩擦）**——Kitesurf 在协议层与 Browserbase **完全同构**：
```jsonc
// chrome-devtools-mcp 通过 --wsEndpoint 直连 Kitesurf（docs 原文）
"command": ["npx","-y","chrome-devtools-mcp@latest",
  "--wsEndpoint=wss://api.cloudflare.com/client/v4/accounts/<ID>/browser-run/devtools/browser?browser=kitesurf",
  "--wsHeaders={\"Authorization\":\"Bearer <TOKEN>\"}"]
```
Lasso 的 `BrowserbaseChannel.ts` 已是"chrome-devtools-mcp + `--wsEndpoint` 远端 CDP"范式，复制改 spec/wsEndpoint 即可，不破坏 R-CI-02（平级 BrowseChannel 子类）。

**但范式/定位冲突点（决定"部分有益"而非"有益"）**：
1. **Kitesurf 的强项（省 CPU/内存 3-7×）对 Lasso 单机本地场景价值小**——Lasso 的 `browse_headless` 跑在用户本机，Chromium 内存是用户付。省资源是云服务商视角的账单优势。
2. **Kitesurf 的硬伤恰好踩中 Lasso 的两块核心**：
   - ❌ "不能协商真实 TLS 指纹的 bot-challenge"——这正是 Lasso `StealthEngine`（detectCloudflareChallenge）+ `browse_logged_in` + stealth 要解决的场景。Kitesurf 在反检测维度**比本地 headless Chromium 更弱**。
   - ❌ "不能长时认证 session"——直接否定 `LoggedInChannel`（多 profile 持久化）的核心用例。
3. **Lasso 已有 BrowserbaseChannel 占了"云端 CDP 浏览器"位**。Kitesurf 的差异化只剩"更便宜的截图/抽取"——成本优化，不是能力解锁。

**具体可融入 Lasso 的模块**（若要做）：新增 `KitesurfChannel extends BrowseChannel`（仿 `BrowserbaseChannel.ts`），作为 v0.4 cloud tier 的**成本档**（Kitesurf 处理"公开页截图/抽取"，Browserbase 处理"需反检测/认证"）。或更轻：作为 `BrowserbaseChannel` 的 provider 选项（加 `?browser=kitesurf` 开关）。

**license 兼容性**：无源码可 Embed，调用远程服务不触发 license 问题；但引入 = SaaS 强依赖 + 需 Cloudflare 账号 + API token 配置。与 Lasso「本地优先、可离线」气质有张力。

**结论**：**v0.4 cloud 通道时评估，非当前优先**。当前 P0 是修 stealth 短板（Kitesurf 在反检测维度更弱），Kitesurf 只是 Browserbase 的成本替代。等 Kitesurf 开源后再重评（若开源，自部署可消除 SaaS 依赖，价值上升）。

### 2.2 Index 浏览器（lmnr-ai/index）

**基本信息**（README + LICENSE 全文直读）：

| 字段 | 值 |
|---|---|
| **repo** | `github.com/lmnr-ai/index`（公开） |
| **license** | **Apache License 2.0**（Copyright [2025] LMNR AI, Inc.） |
| **主语言** | **Python**（`pip install lmnr-index`） |
| **定位** | **SOTA 开源"浏览器 agent"——LLM 驱动、自主完成复杂 web 任务**（**不是浏览器引擎**，是基于 Playwright+Chromium 的 agent 框架） |

⚠️ **关键澄清**：Index **不是"浏览器"**，是"浏览器 agent"。它自己**不渲染网页**——用 Playwright 驱动真实 Chromium。把它和 Kitesurf 并列称为"两个浏览器"是**范畴错误**。

**核心能力**（README + HN 创始人说明；**.py 源码未直读，已标注**）：
- LLM 驱动（Gemini 2.5 Pro / Claude 3.7 Sonnet / OpenAI o4-mini），**自带独立的 LLM 推理循环**（agent 自主 step：Opening→Scrolling→...→Done）
- Playwright patched 全 session 录制 + agent step/LLM call 双轨 trace
- Pydantic 结构化抽取
- 本地 Chrome 模式（`index run --local-chrome`）复用用户登录态

**对 Lasso 的价值判断：无益（作为组件）/ 仅作参考（作为理念）**

**范式根本冲突（决定性）**：
1. **双 LLM 循环红线**：Lasso 的核心设计是 **CC（Claude Code）是唯一的 LLM 推理者**——Lasso 只提供确定性原语（navigate/click/extract/evaluate），决策由 CC 做。Index **自带一个独立的 LLM agent 循环**。把 Index 嵌入 Lasso = 在 Lasso 内引入**第二个 LLM 决策者**，直接违背 Lasso「黑板零 LLM 推理」式的设计哲学。
2. **R-CI-02 衍生冲突**：Index 不是"一个通道"，它是一个**完整的 agent 栈**——嵌它等于在 Lasso 内塞一个平行宇宙的 agent 系统。
3. **技术栈断层**：Index 是 Python（+ patched Playwright），Lasso 是 TypeScript/Node。嵌入需走 Python 子进程，引入第二个运行时——违反 INV-7「纯 lifecycle」简洁性。

**唯一可借鉴的"思路"（非代码）**：Playwright session 全程录制 + agent step/LLM call 双轨 trace——Lasso 现有 `actions_and_results` 审计链是文本/结构化审计，**没有浏览器 session 的可视回放**。Index/Laminar 这套"录屏同步 trace"对 Lasso v0.7 可观测性是有价值的**理念参考**（实现路径不同，需 CDP `Page.startScreencast`）。

**结论**：Index 对 Lasso **无作为组件的价值**（范式冲突 + 栈断层 + 双 LLM 红线）。与 Lasso 是**同类问题不同哲学的竞品关系**，而非可融入的积木。唯一价值是 v0.7 可观测性理念参考。

### 2.3 Firecrawl（mendableai/firecrawl）

**基本信息**（源码 + README 直读）：

| 字段 | 值 |
|---|---|
| **repo** | `github.com/mendableai/firecrawl` |
| **star** | 官网自称 150K+（营销口径，无法独立核实精确数） |
| **license** | **AGPL-3.0**（主仓库/apps/api）；**SDK 是 MIT**（apps/js-sdk/LICENSE、python-sdk/LICENSE 独立） |
| **主语言** | TypeScript（API server + 所有 SDK） |
| **定位** | 面向 LLM/agent 的 web 数据 API——把整个 web（含 JS-heavy 页）转成 clean markdown/structured JSON/screenshot，并提供 crawl/map/agent/interact 编排 |

**核心能力（基于源码，非猜测）**：
- v2 endpoints：`scrape / search / crawl / map / batch / extract / agent / browser` + `/interact`（v2.9.0 browser interaction）
- **scrape 是多引擎 fallback**（`apps/api/src/scraper/scrapeURL/engines/`）：fetch + playwright + fire-engine（商业反检测代理，付费）+ pdf/OCR + document + wikipedia + index。Firecrawl 自身就是"多引擎 + fallback"范式，与 Lasso 的 channel+FallbackDecider 同构。
- **重型 server**：controllers(v0/v1/v2) + services/(redis、supabase、billing/stripe、queue-worker、redlock、rate-limiter) + search/。**自托管需要 Redis + Postgres + 队列 worker + 可选 runpod OCR**，非轻量库。
- crawl/map 编排：全站爬取 + sitemap + 并发 + 队列（Lasso 当前无此能力）。

**对 Lasso 的价值判断：部分有益，但 AGPL + 重型 server 双重门槛**

**能融入 Lasso 的能力**：
- `/scrape` markdown 输出：Lasso 的 MarkdownExtractor（defuddle + turndown）已覆盖 80% 场景；Firecrawl 的优势是 JS-heavy + 反检测页（fire-engine 引擎）。**但 fire-engine 是付费商业代理**（自托管版没有），自托管拿不到这部分。
- `/interact`（v2.9.0）+ `/agent`：Lasso **没有**的能力——scrape 后用 AI prompt 继续点击/填写/抽取。但这是新功能域，不是增强既有模块。
- crawl/map 编排：Lasso 目前是单页 browse，无全站 crawl。

**架构契合：范式冲突（不能代码依赖，只能 API 调用）**
- Firecrawl 的 scrapeURL 多引擎 fallback 与 Lasso FallbackDecider **同构但平行**——若把 Firecrawl scrape 代码 import 进 Lasso，等于在 Lasso 内嵌第二套 fallback 引擎，**直接违反 R-CI-02/INV-18**（禁自造 fallback 循环）。
- Firecrawl 自带 controller/services/redis/queue 是独立后端服务，不是可嵌入库。

**license 兼容性（Lasso 是 MIT）**：
- **AGPL-3.0 强传染**：若 Lasso import Firecrawl 源码（即便改写），Lasso 整体须开源 + AGPL。**不可代码依赖**。
- **API 调用隔离**（合法路径）：Lasso 作为客户端 HTTP 调用 Firecrawl 托管服务或**用户自托管的 Firecrawl server**，是独立进程、无衍生作品，**不触发 AGPL 传染**。
- **SDK 是 MIT**：apps/js-sdk 可被 Lasso npm 依赖，SDK 本身只是 HTTP client。但 SDK 调用的是 Firecrawl server（托管付费 or 自托管）。

**结论**：Firecrawl 对 Lasso 的**净价值有限**。它最值钱的 `/interact` + `/agent` 需要 Firecrawl server（付费托管 or 自托管 Redis+Postgres）。最现实的集成是 Lasso 新增一个 `FirecrawlChannel`（仿 BrowserbaseChannel），作为 browse_headless 的一个**可选付费 fallback channel**，纯 HTTP 调用、零代码依赖。但这只是「多一个云抓取后端」，与 Lasso「本机优先、AES cookie、四通道本地抓手」的定位**价值重叠低**。**不建议深度集成**，可作为 v0.2+ 可选 channel 记入文档。

### 2.4 Obscura（h4ckf0r0day/obscura）

**基本信息**（源码 + README + docs 直读）：

| 字段 | 值 |
|---|---|
| **repo** | `github.com/h4ckf0r0day/obscura` |
| **star** | README 自述 10,000 stars（无法独立核实精确实时数） |
| **license** | **Apache-2.0**（根 LICENSE + `crates/obscura/Cargo.toml` 双重确认） |
| **主语言** | **Rust**（8 crate workspace：obscura-cli/cdp/browser/js(V8)/dom/net/mcp/lib） |
| **定位** | 用 Rust 写的开源 headless 浏览器引擎（自嵌 V8 + 自实现 DOM + CDP server），为 AI agent 自动化和大规模 web scraping 设计，drop-in 替代 headless Chrome |

**核心能力（基于源码/文档，非猜测）**：
- **CDP server**（`obscura serve --port 9222`）：实现 Chrome DevTools Protocol，Puppeteer/Playwright 可直连。**与 chrome-devtools-mcp 协议层兼容**。
- **standalone MCP server**（`crates/obscura-mcp/src/lib.rs`，87KB，32 个 tool 定义）：stdio + HTTP 双 transport
- **stealth mode**（`--features stealth` 编译 + `--stealth` 运行时 flag）——**这是对 Lasso 最有价值的能力**：
  - **TLS 层指纹模仿**（`obscura-net/wreq_client.rs` + BoringSSL）：呈现真实 Chrome 的 ClientHello/ALPN/cipher order
  - tracker blocklist（3520 域）
  - 浏览器 profile 内部一致：navigator.platform / userAgentData / UA / WebGL GPU renderer 内部自洽
  - timezone 由进程 zone 驱动，geolocation 可配，profile rotation 可选
  - 文档**诚实声明局限**：「What stealth does not handle: Cloudflare interactive challenges / Datadome / Akamai bot manager active challenges / CAPTCHAs / IP-based rate limiting」
- 性能（README 自述，未独立核实）：内存 30MB（Chrome 200+MB）、二进制 70MB、页面加载 85ms、启动即时
- 官方 release 提供 `-stealth` 预编译二进制（Linux/macOS/Windows），**可直接下载二进制，免编译**

**对 Lasso 的价值判断：部分有益——TLS 层 stealth 是最契合的补强**

**能融入 Lasso 的能力（按模块）**：
- **StealthEngine 的 TLS 层补强**（最高价值）：Lasso 的 StealthEngine 只在 CDP JS 层抹 navigator.webdriver/UA。Obscura 的 stealth 在 **TLS ClientHello 层**——这是 Lasso 通过 CDP 注入 **永远够不到的一层**（CDP 管的是已建立的 Chromium，TLS 握手在它之下）。反检测站点先看 TLS JA3 再看 JS，Lasso 当前完全裸奔。Obscura 把这层补上。
- **新 BrowseChannel 引擎选项**（次高价值）：Lasso 的 SubprocessManager 已有 spawn 子进程 + CDP 驱动范式。Obscura `serve --port 9222 --stealth` **同构**——可作为 HeadlessChannel/BrowseChannel 的**备选渲染引擎**（spawn Obscura 替代 Chrome）。

**架构契合：高契合（subprocess + CDP，不触红线）**
- Obscura 是**浏览器引擎**（rendering + CDP），**不是 markdown extractor**。Lasso 用它渲染页面后，仍走 Lasso **单一** MarkdownExtractor 抽取——**不触发 R-CI-02/INV-68「第三套 extraction runtime」红线**（那条管的是 extractor 数量，不是 browser 数量；类比 Chrome→Firefox 换引擎）。
- 作为 subprocess 接入（spawn `obscura serve`）与 Lasso 现有 RustBridge + SubprocessManager 范式一致，不引入第二调度层。
- fallback 仍走 Lasso 单一 FallbackDecider（Obscura 作为一个 channel 注册进 breakers Map），不违反 INV-18。

**license 兼容性**：**Apache-2.0 与 MIT 兼容**（双向）：Lasso 可链接、调用、改写 Obscura，Lasso 仍可保持 MIT（只需保留 Apache NOTICE）。**无传染风险**。唯一约束：stealth feature 编译需 BoringSSL + clang + cmake，但**预编译二进制可直接下载**。

**集成风险（诚实标注，非猜测）**：
1. **渲染保真度未独立验证**：Obscura 自实现 DOM（obscura-dom）+ V8，**不是 Blink/WebKit**。README 声称 CDP 兼容，但复杂 CSS / 视觉重排版面 / WebGL 实际渲染可能与 Chrome 有差异。benchmark 在独立仓（obscura-benchmark），**未读**，无法证实保真度。**待验**。
2. **Cloudflare 仍是天花板**：Obscura 文档明示不处理 Cloudflare interactive / CAPTCHA。与 Lasso 现状同 ceiling——Obscura 解决的是 TLS/JS 指纹层，挡不住 Cloudflare JS challenge。
3. **单 V8 isolate 串行**：一进程内所有 page 共享一个 V8 isolate + v8_lock 串行化。Lasso 单机低并发场景无影响。
4. **作者信誉**：仓库名 h4ckf0r0day + reddit 有用户反映「名字让 Claude 误判 malware」。代码本身读了 lib.rs/架构文档/Cargo.toml 无可疑行为，但建议 Lasso 集成前跑独立安全审查。

**结论**：Obscura 对 Lasso 的**净价值高于 Firecrawl**。最现实的 MVP 集成：v1.7+ 新增 `ObscuraChannel`（extends BrowseChannel），在 SubprocessManager spawn `obscura serve --port N --stealth`，复用 McpClient/cdp-actions 走 CDP，作为 HeadlessChannel 的**反检测增强 fallback channel**（Lasso 现有 StealthEngine JS 层 + Obscura TLS 层叠加）。**前置验证**：需先 spike 一个 Obscura 对 Lasso 目标站点的 CDP 兼容性 + 渲染保真度测试，再决定是否进 fallback 链。

## 5. 架构调整建议（按优先级排序）

### 建议 1（🔴 P0 / 高优先 / 低风险）：修 stealth P0 短板——HeadlessChannel 接 StealthEngine + header-generator + 16 路 evasions + patchright flags

| **A. HeadlessChannel override beforeNavigate** | Lasso 既有 BrowserbaseChannel 范式 | `src/channels/HeadlessChannel.ts` 加 `override beforeNavigate` 调 StealthEngine.inject | ~0.5 天（范式已有） | — |

### 建议 3（🟡 P2 / 中优先 / 修正）：对齐 StagehandChannel 集成方式 + doctor 探测

**背景**：白盒审查发现 `StagehandChannel.ts:196-206` 的 REST 契约 `api.stagehand.dev/{verify|extract}` 在 stagehand repo 内**无源码佐证**——实际 Stagehand SDK 是 CDP+RPC 客户端，不是 REST 客户端。Lasso 的 REST 契约可能是 v0.4 设计期的假设。

**动作**：
- **动作 A**：doctor 探测 `api.stagehand.dev/{verify|extract}` REST 端点是否真实存在
- **动作 B**：若不存在，改走 Stagehand SDK 直连（`npm i stagehand` → SubprocessManager 起本地实例）；或降级移除 StagehandChannel 直到有明确需求

**R-CI-02 影响**：✅ 不破坏（修正既有通道，非新增范式）

**工作量**：~1 天（doctor 探测 + 决策）

---

### 建议 4（🟡 P2 / 中优先 / 低风险）：creepjs 作为 doctor stealth-check 回归门禁

**动作**：`lasso doctor --stealth-check` 让 browse_headless 访问 creepjs（`abrahamjuliot.github.io/creepjs`），解析 `window.Fingerprint`/`window.Creep` 返回的 lies 数量，作为隐身回归门禁。

**价值**：隐身有效性的度量衡。Lasso 的 StealthEngine 应该能在 creepjs 上跑出可量化的分数，否则「隐身能力」全是盲改。完全绕开四通道，不碰运行时路径。

**R-CI-02 影响**：✅ **完全不破坏**——不入运行时，做 doctor 测试夹具（FIXTURE）。

**工作量**：~1-2 天（creepjs 解析 + doctor 集成 + CI 断言）

---

### 建议 5（🟡 P3 / 低优先 / 需 spike）：ObscuraChannel spike——TLS 层 stealth fallback channel

**动作**：先 spike Obscura 对 Lasso 目标站点的 CDP 兼容性 + 渲染保真度测试（读 benchmark 仓或实测），通过则新增 `ObscuraChannel extends BrowseChannel`。

**价值**：
- **TLS 层 stealth 补强**——Obscura 的 stealth 在 TLS ClientHello 层（Lasso 通过 CDP 注入永远够不到的一层）
- subprocess + CDP 接入与 Lasso 现有 RustBridge + SubprocessManager 范式一致
- Apache 2.0 无障碍，预编译二进制免编译

**R-CI-02 影响**：✅ **不破坏**——ObscuraChannel 是 BrowseChannel 平级兄弟子类（与 SteelChannel 同构），Obscura 是浏览器引擎（不是 markdown extractor），Lasso 用它渲染后仍走单一 MarkdownExtractor。

**前置验证（必须）**：
1. Obscura CDP 兼容性测试（Lasso 的 cdp-actions.ts / McpClient 是否能无改造接入）
2. 渲染保真度测试（Lasso 目标站点在 Obscura vs Chrome 下的视觉一致性）
3. stealth 有效性实测（Obscura --stealth 在 sannysoft / bot-detection 上的通过率）

**工作量**：spike ~3-5 天；若通过，正式集成 ~1-2 周

**风险**：Obscura 自实现 DOM+V8（不是 Blink），复杂页面渲染保真度未独立验证。**不应宣传为「Lasso 接 Obscura 后反检测无敌」**——Cloudflare 仍是天花板（Obscura 文档诚实声明）。

---

### 建议 6（🟡 P3 / 低优先 / 讨论级）：正视 Camoufox 对 Lasso StealthEngine 的质疑

**事实**：Camoufox README 用大篇幅论证「JS-based stealth 注入天然可被检测」（`Object.getOwnPropertyDescriptor` 暴露覆写、`toString()` 暴露劫持、worker/window 上下文不一致）。**Lasso 的 `STEALTH_INJECTION_SCRIPT` 正是这种被判为弱方案的范式**。

**不是立即修**：C++ 源码级补丁集成成本极高（Firefox/Juggler vs Chromium/CDP 架构冲突）；但应：
1. 在文档中**显式承认这一已知 stealth 上限**
2. 把 Lasso 的 stealth 定位为「过 sannysoft / 基础 bot 检测，不承诺过 CreepJS / Datadome / Kasada」
3. 避免 CC 误判 Lasso stealth 能力边界

**可低成本借鉴**：Camoufox 用 BrowserForge 生成「市场占有率分布一致 + 内部一致」的指纹——Lasso 的 `stealth-profiles.ts` 目前只 3 条硬编码 UA，且不考虑 UA/GPU/屏幕分辨率/字体的内部一致性。建议 1 的 header-generator 已部分覆盖此需求。

**R-CI-02 影响**：✅ 不破坏（文档 + 思路借鉴，无代码依赖）

## 6. 不应做的（真正否决项）

> **原则**：只列真正否决项——license 不兼容 / 法律红线 / 明确技术不可行。**不因「架构偏好」否决业务需要的能力**。

### 6.1 license 硬红线（法律不可逾越）

| 项目 | license | 否决理由 |
|---|---|---|
| **nodriver** | **AGPL v3** | 强 copyleft + 网络条款：Lasso（MIT）若 link/import 触发 AGPL 传染（整个 Lasso 须转 AGPL）；即使经子进程调用，AGPL「网络服务」条款仍可能触发（Lasso 是 MCP server 提供网络服务）。**硬红线** |
| **undetected-chromedriver** | **GPL v3** | 强 copyleft + 已废弃（作者转向 nodriver）+ Selenium（Lasso 走 CDP via MCP） |
| **Botright** | **GPL v3** | 强 copyleft + Python + captcha 求解违反 Lasso「不自动 captcha 求解」政策红线 |
| **Firecrawl（代码依赖）** | **AGPL-3.0**（apps/api） | 若 Lasso import Firecrawl 源码，Lasso 整体须开源 + AGPL。**不可代码依赖**；但 API 调用（托管/自托管）合法 |

### 6.2 业务政策红线（用户硬约束 + 法律高压线）

| 能力 | 否决理由 |
|---|---|
| **自动 captcha 求解** | Lasso 政策红线（parse5 §3.3.1 铁律 4）：stealth 失败升 manual-switch，不自动 captcha 求解。Botright/nodriver 的 cf_verify 是一种「温和的可见 checkbox 点击」，边界讨论空间存在，但默认应禁 |
| **签名纯算（x-s/x-t/x-s-common 等逆向 JS）** | 刑事红线：破解小红书加密算法 + 伪造数据请求侵入服务器 = 刑事犯罪（已有判刑案例）。Lasso 绝不内置 |
| **自动写操作（自动发布/评论/点赞）** | 2026-03 小红书公告明确禁止「利用技术手段模拟真人进行非真实内容创作或虚假互动」。HighRiskGate 应把写操作类动作纳入 gate |

### 6.3 明确技术不可行 / 范式根本冲突

| 项目 | 否决理由 |
|---|---|
| **Index（作为组件）** | 自带独立 LLM agent 循环，与 Lasso「CC 是唯一推理者」哲学根本冲突（双 LLM 红线）；Python 栈与 Lasso TS 断层。**仅 v0.7 可观测性理念参考**（Playwright session 录制 + trace），不引代码 |
| **browser-use（作为组件）** | 本身是完整 agent（cdp-use + 多 LLM + agent loop + skills）；嵌入 Lasso = agent-in-agent，责任边界混乱。**仅作竞品对比**，不引代码 |
| **Camoufox（作为组件）** | Firefox/Juggler ≠ Chromium/CDP，Lasso 全栈基于 chrome-devtools-mcp@0.3.0（Chromium）。要让 Lasso 用 Camoufox = 把 `browse_headless` 整个换成 Firefox+Playwright，推翻现有基座。**若未来要做，应作为独立 `browse_camoufox` 通道（v2.0+ 范围扩张），而非增强现有 StealthEngine** |

### 6.4 不因「架构偏好」否决——以下是可做但有更低成本替代的

> **重要**：以下项目**不是法律/技术否决**，而是「有更优替代」。若业务需要且替代方案不可用，可降级考虑。

| 项目 | 不推荐理由 | 更优替代 |

| **Kitesurf（当前）** | 未开源 + SaaS 依赖 + 不能反检测/长认证 | 等开源后重评；当前用 BrowserbaseChannel（已占云 CDP 位） |

### 8.2 开放问题

1. **header-generator vs fingerprint-injector 的选择**：header-generator 只生成 header 集（最直接补 Lasso 破绽）；fingerprint-injector 生成完整指纹 + 注入脚本（更强但 hook Playwright/Puppeteer page 对象，与 Lasso McpClient.callTool 路径不直接兼容）。**v1.5 MVP 建议先走 header-generator**（纯函数库，TS 调用即可），v1.6+ 评估 fingerprint-injector 的注入脚本提取复用。

2. **Obscura vs Lightpanda 的取舍**：两者都是 Rust/Zig 写的高性能 headless 浏览器。Obscura 强在 TLS stealth（--stealth flag）；Lightpanda 强在 semantic_tree MCP 工具设计 + 更高成熟度（但 Beta）。**Obscura 优先**（stealth 是 Lasso 更急需的补强）；Lightpanda 留 v2.0+ 评估作可选高性能后端。

3. **Steel 自托管 vs Browserbase 云端的 fallback 链顺序**：建议 `browse_headless（本地）→ Steel（自托管云）→ Browserbase（商业云）→ browse_logged_in（本机 Chrome）`。Steel 在 Browserbase 之前（自托管更便宜 + cookie 不出本地）。

4. **TLS 层 stealth 的终极路线**：JS 路线有结构性上限（Camoufox 论证）。Lasso 最终要不要引入 Obscura（Rust headless + TLS stealth）或 Camoufox（Firefox C++ patch + 最强反检测但架构冲突）作为独立 stealth 通道？**v1.8 Obscura spike 后再决策**——若 Obscura CDP 兼容 + 渲染保真度通过，Obscura 是更低成本选择（Apache 2.0 + Rust 与 Lasso RustBridge 同语言）。

5. **proxy-chain IP 层的优先级**：反爬第一信号是 IP 信誉，再完美的指纹伪装也救不了数据中心 IP。但 proxy-chain 是正交能力（对 Lasso 四通道零影响）。**v1.9+ 按需扩展**——若用户实测试到 IP 被封场景，再引入 `anonymizeProxy` + `--proxy-server` flag。

6. **puppeteer-extra-plugin-stealth 停更的长期影响**：2023.3 后停更，社区喊「失效」。但本次源码核查确认 16 路 evasions 的**具体技术原理**（chrome.app/csi/loadTimes/runtime 覆写等）仍然有效——失效的是「对 2026 最新检测套件的通过率」，不是「16 路注入本身无效」。Lasso 合并 stealth.min.js 后，应配套 creepjs 回归门禁（建议 4）持续监控实际效果。

7. **chrome-devtools-mcp 版本解锁**：当前锁死 0.3.0（`SubprocessManager.ts:37`），导致多 profile 隔离无法自动化 + 需自写 CdpClient。是否在 v1.5+ 评估升级到最新版？**需先 spike 新版工具表兼容性**——升级后 stealth args（--disable-blink-features 等）的透传路径可能变化。

### 8.3 红线重申

- **license 硬约束**（不可逾越）：AGPL/GPL 项目不可代码依赖（nodriver/undetected-chromedriver/Botright/Firecrawl apps/api）；可 API 调用/独立进程/reimplement 算法
- **业务政策红线**：不自动 captcha 求解（escalateManualSwitch）；不内置签名纯算（刑事红线）；不自动写操作（2026-03 高压线）
- **诚实定位**：Lasso 的 stealth 定位是「过基础 bot 检测（sannysoft / 公开页 / 一般 SERP），不承诺过 Cloudflare Enterprise / Datadome / Kasada」。强反爬站点走 `browse_logged_in` 复用真实 Chrome（天然带完整指纹/扩展/历史，反检测最强）。**不鼓励反风控军备竞赛**——stealth 脚本持续跟版是长期债，且违背 Lasso「零侵入跟随上游」原则。
