# 方向 A：CC 控制浏览器 · 全景与对比（01）

> 目标：CC 高效、准确、最好后台无头地控制浏览器。
> 核心结论先行：**主流高绩效方案都是「外部代码驱动」（CDP/Playwright），不是「寄生在浏览器进程内」**。它们的效率优势来自「代码驱动 vs 视觉截图驱动」，而非「寄生 vs 外部」。

---

## 0. 先把「寄生 agent」这件事说清楚

| 架构 | 代表 | 离浏览器多近 | 现状 |
|---|---|---|---|
| **外部驱动**（CDP/Playwright 从外面控制） | chrome-devtools-mcp、browser-use、Stagehand | 浏览器是独立进程，通过协议控制 | ✅ 主流、成熟 |
| **扩展寄生**（agent 逻辑跑在浏览器扩展里） | **Claude in Chrome** | ✅ 真正在浏览器里，共享登录态 | ✅ 官方落地形态 |
| **同进程寄生 + 本地模型**（页面/Service Worker 里跑 LLM） | WebLLM / Gemini Nano / Service Worker agent | 最近（同进程、零往返） | ❌ 本轮未找到成熟方案 |

**为什么「外部驱动」也已经够快**：在主流视觉 agent 里，**LLM 规划/反思占总延迟 75–94%**（[arXiv 2506.16042](https://arxiv.org/html/2506.16042v1)），CDP/IPC 的往返开销相比之下可以忽略。真正决定效率的是「**少调用 LLM + 把页面状态写磁盘而不是灌进上下文**」——见下方 token 对比。

---

## 1. CC 原生：两条浏览器路径

CC 自己就内置两种浏览器控制方式【验证，[code.claude.com/docs/en/desktop](https://code.claude.com/docs/en/desktop)】：

### (1) 内置 Browser pane（隔离 profile）
- 用一个**干净、隔离的浏览器 profile**，没有你的登录态/历史/扩展。
- 适合：测试、爬取公开页面、不希望污染个人登录的场景。
- 局限：因为没登录态，需要登录的站点进不去。

### (2) Claude in Chrome 扩展（共享真实登录态）⭐ 最接近「寄生」
- 安装 [Claude in Chrome 扩展](https://chromewebstore.google.com/detail/claude/fcoeoabgfenejglbffodgkkbkcdhcgfn)后，CC 通过内置 `claude-in-chrome` MCP server 驱动你的真实 Chrome。
- **共享你浏览器的登录态**——Claude 能以你的身份操作已登录站点。
- CC 在两条路径都配置时**自动优先使用 Claude in Chrome**：「If the task is browser work and you have Claude in Chrome set up, Claude uses that.」
- 官方文档：[code.claude.com/docs/en/chrome](https://code.claude.com/docs/en/chrome) ｜ 产品页：[claude.com/claude-for-chrome](https://claude.com/claude-for-chrome)
- ⚠️ **限制**：需要有头 Chrome（非无头）；扩展与 CC 的具体通信通道（native messaging / stdio / MCP）本轮未被证据明确验证（见开放问题 #3）。

> **结论**：如果你要「以本人身份操作已登录网页」，Claude in Chrome 是官方首选，零配置成本。它就是方向 A 里最接近「寄生」的落地形态。

## 2. chrome-devtools-mcp ⭐ 方向 A 首选（外部 CDP 驱动）

Google Chrome DevTools 团队官方项目【验证，[ChromeDevTools/chrome-devtools-mcp](https://github.com/ChromeDevTools/chrome-devtools-mcp)｜[developer.chrome.com/blog/chrome-devtools-mcp](https://developer.chrome.com/blog/chrome-devtools-mcp)】。

**为什么是首选**：
- **基于 Puppeteer/CDP** 从外部驱动 Chrome：「Uses puppeteer to automate actions in Chrome and automatically wait for action results」。
- **原生支持无头**：`--headless`（后台无头运行，无 UI）——直接命中「后台无头」目标。
- **精简模式降 token**：`--slim`「If you are interested in doing basic browser tasks, use the --slim mode」。
- **复用已登录 Chrome 会话**：`--browser-url http://127.0.0.1:9222` 连到一个已运行的 debuggable Chrome，直接吃它的 Cookie/登录态（注意：「Some accounts may prevent sign-in when the browser is controlled via WebDriver」——少数站点会拒）。
- **CC 一等集成**，两条装机路径：
  ```bash
  claude mcp add chrome-devtools --scope user npx chrome-devtools-mcp@latest
  # 或 plugin marketplace
  /plugin marketplace add ChromeDevTools/chrome-devtools-mcp
  ```
- **工具覆盖广**：~52 个工具，覆盖输入 / 导航 / 网络 / 性能 / 堆快照 / 扩展管理等。
- **token 效率**：10 步操作约 ~50,000 tokens（介于 Playwright MCP 114k 和 Playwright CLI 27k 之间）。

**已知坑**：
- 默认工具数约 **28–29**，要拿到完整 ~52 需开启多个非默认 flag：`--memoryDebugging` / `--category-extensions` / `--experimentalVision` 等。
- Chrome 作为独立外部进程启动，会阻止 Web Store 扩展安装（[Issue #265](https://github.com/ChromeDevTools/chrome-devtools-mcp/issues/265)）——证明它是 external driver 而非寄生。
- `--browser-url` 复用登录态时，少数有反 WebDriver 检测的站点会拒登。

**装机步骤**：见 [04-CC集成操作手册.md](04-CC集成操作手册.md#chrome-devtools-mcp)。

## 3. browser-use ⭐ 长程复杂 web 任务首选

开源框架（[browser-use/browser-use](https://github.com/browser-use/browser-use)），97k+ stars【验证】。

**核心定位**：
- 通过 `browser-use skill install` 把 skill 写进 `~/.claude/skills/`（Claude Code）等助理目录，以 **markdown skill + CLI 桥接**的方式集成 CC（**不是 MCP server**）。
- agent 只需粘贴一句安装 prompt 即可自动配置并指派浏览器任务。
- 底层仍调用 **Claude Opus 4.7**（不是纯架构优势，见 caveats #2）。
- 官方文档：[docs.browser-use.com/open-source/browser-use-terminal](https://docs.browser-use.com/open-source/browser-use-terminal)

**实测成绩**：
- **Odysseys 榜 87.4% 平均分，#1**，超过 OpenAI/Anthropic/Google/Microsoft 的 vision-based CUA（[odysseysbench.com/leaderboard.html](https://odysseysbench.com/leaderboard.html)，第三方确认 #1 条目为 BrowserCode (Opus 4.7) Browser-Use 87.4）。
- WebVoyager 基准 89.1% 成功率，GitHub stars 97,000+。
- 支持 Claude / GPT-4o / Gemini 作后端，集成 LangChain。

**为什么强**：把 LLM 规划**转成确定性的 Playwright 代码**，把「每步都调 LLM」变成「规划一次 + 执行多次」——这正是它在 web 任务上反超截图派 CUA 的根本原因（呼应 75–94% 延迟洞察）。

**已知坑**：每步原本都需要一次 LLM 调用，多步任务的 API 成本和延迟会累积（除非用它的「规划转代码」模式）。

**装机步骤**：见 [04-CC集成操作手册.md](04-CC集成操作手册.md#browser-use)。

## 4. Token 效率深度对比：为什么 MCP 不一定是最优解 ⚠️ 重要

来自 Playwright MCP 官方 repo 的对比【验证】——**10 步浏览器操作**：

| 方案 | tokens 消耗 | 相对成本（Sonnet 4.6） | 机制 |
|---|---|---|---|
| Playwright MCP | ~114,000 | ~$0.34 | 把整个 a11y tree + 截图**灌进模型上下文** |
| chrome-devtools-mcp | ~50,000 | ~$0.15 | |
| Playwright CLI | ~27,000 | ~$0.08 | 把快照/截图/日志**写磁盘**（YAML/PNG/log），只返回**短文件路径** |
| Agent Browser | ~7,000 | ~$0.02 | |

**微软的官方建议**（[Playwright MCP repo](https://github.com/microsoft/playwright-mcp)）：
> Microsoft explicitly recommends CLI-based workflows exposed as Skills over MCP for modern coding agents like Claude Code, Cursor, and Copilot, because CLI invocations are more token-efficient.

**落地含义**：
- 如果你跑**长程、多步、批量**任务，**Playwright CLI 包成 Skill 比 Playwright MCP 省 ~4 倍 token**。
- 关键设计模式：**「页面状态写磁盘 → 上下文只拿指针」**，而不是「整页灌进上下文」。这是所有省 token 方案的共同套路。
- chrome-devtools-mcp 的 `--slim` 模式、browser-use 的「规划转代码」都是同一思想的不同实现。

## 5. Stagehand（Browserbase）— act/extract/observe 三原语

[Stagehand](https://github.com/browserbase/stagehand)，Browserbase 开源，基于 Playwright 之上的一层【一手】。

**特点**：
- 暴露三个**自然语言原语**：`act`（执行动作）/ `extract`（抽取结构化数据）/ `observe`（观察页面）。
- 支持任意带结构化输出能力的 LLM（含 Anthropic 模型）。
- **读页面用 accessibility tree 而非 CSS/XPath 选择器**，DOM 变化时仍能工作。
- **Stagehand v3（2026 年 2 月）**：AI-native TypeScript agent，直接走 CDP，移除传统自动化层，**比 v2 快 44%**；逐步把 AI 识别的动作**转成确定性 replay**（和 browser-use 同一思想）。

**已知坑**：
- 本地模型用不了（它们做不好 Stagehand 要求的结构化输出）——需要强力托管 LLM，带来**隐私 + token 成本**问题。

---

## 6. Skyvern — 视觉 + LLM，复杂表单最强

[Skyvern](https://github.com/Skyvern-AI/skyvern)【一手，来自 workflow fetch】。

**特点**：
- **计算机视觉 + LLM** 识别元素，**无需 CSS 选择器**——对 DOM 结构多变、反爬的站点更鲁棒。
- **Skyvern 2.0 在 WebVoyager 取得 85.85%**，在**表单填写（WRITE）任务上是表现最好的 agent**。
- 最适合：保险、政府、采购门户这类**结构高度可变、字段复杂**的表单。

**已知坑**：
- 视觉路线的通病：每步依赖 LLM + 视觉识别，延迟和成本高。
- 配合云浏览器时登录态是大坑（见下条 Browserbase）。

---

## 7. Browserbase — 无头云浏览器（带登录态坑）

[Browserbase](https://www.browserbase.com/)【一手】。

**定位**：serverless、无头云浏览器会话，支持 Playwright / Puppeteer / Selenium + CDP，**无需 GUI 或本地浏览器**——直接命中「后台无头」目标，也是 Stagehand / Skyvern 的默认后端。

**已知坑（重要）**：
- **2FA / 登录处理失败率约 60%**（Skyvern 测试中 10 次失败 6 次）——云浏览器方案在处理登录态时的通病。如果你的任务需要登录，云浏览器不是好选择，改用本地 Chrome + `--browser-url`（chrome-devtools-mcp）或 Claude in Chrome。

## 8. 已弃用 / 避坑清单 ⚠️

### AgentDeskAI/browser-tools-mcp — **官方已弃用**
- README 首行原文：「**THIS PROJECT IS NO LONGER ACTIVE PLEASE USE A DIFFERENT SOLUTION FOR THIS**」【验证】。
- 即便还在用，它的真实定位是「**浏览器监控 + Lighthouse 审计**」（console / network / 截图 / 选中 DOM / WCAG·SEO·性能审计），**不做 navigate/click/fill 等通用自动化**。
- 架构很重：要同时跑三个组件（Chrome 扩展 + Node middleware `browser-tools-server` + MCP server）。
- 要求交互式 Chrome 且 DevTools BrowserToolsMCP 面板常开——**非无头控制器**。
- **CC 用户应避开，优先选 chrome-devtools-mcp 或 browser-use**。

### AgentQL / MultiOn
- 商业产品，本轮未深入验证【通识】。AgentQL 偏「用自然语言定位元素」的查询层；MultiOn 偏全自主浏览器 agent SaaS。两者都是闭源商业服务，开源度低，不在「开源首选」范围内。

## 9. 方向 A 选型小结

| 你的需求 | 选这个 |
|---|---|
| 后台无头跑批量/测试 | **chrome-devtools-mcp `--headless`** |
| 用本人登录态操作 | **Claude in Chrome**（首选）/ chrome-devtools-mcp `--browser-url` |
| 长程复杂多步任务 | **browser-use（skill install）** |
| 复杂多变表单 | **Skyvern** |
| 极致省 token | **Playwright CLI 包成 Skill**（写磁盘） |
| TypeScript / 想要 act/extract/observe 三原语 | **Stagehand v3** |
| 云端无头（但登录态不重要） | **Browserbase**（注意 2FA 坑） |

> 装机与启用步骤统一见 [04-CC集成操作手册.md](04-CC集成操作手册.md)。
