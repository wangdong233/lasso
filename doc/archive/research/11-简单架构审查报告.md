## 1. Findings

### 🟡 F1 — browse_headless 接口过胖（11 参数 >7）

| 字段 | 内容 |
|---|---|
| `rule_id` | R-INT-03（接口过胖）+ R-DEP-01（public API 过大）+ R-ABS-01（参数蔓延） |
| `severity` | 🟡 Warn（R-INT-03/R-DEP-01 均 🟡；R-ABS-01 🔵；综合 🟡，但属 MVP 就该改的硬伤） |
| `location` | 08 附录 B `browse_headless` 签名 / F3.2.x |
| `evidence` | `browse_headless(url, action, selectors, js, steps, expect_login, wait_until, screenshot_full, screenshot_element, timeout_ms, no_cache)` = **11 个参数**，其中 `expect_login/screenshot_full/no_cache` 等 ≥4 个 boolean flag。`browse_logged_in` 同病（8 参数）。 |
| `why` | ① **接口过胖=浅模块信号**（R-DEP-02）：`depth = 实现/API` 被 11 参数稀释，模块深度趋低；② **参数蔓延=错误抽象退化路径**（R-ABS-01/01 §3.2）：多 boolean flag 按 caller 分流是错误抽象的可观测退化；③ **认知负荷**（R-CHG-02）：CC 每次调用要记住 11 参数顺序与含义，且 10 里强调"减少推理调用"与胖接口正相反。 |
| `suggestion` | 参数对象化：`browse_headless(url, action, options: BrowseOptions)`，`BrowseOptions = {selectors?, js?, steps?, wait_until?, screenshot?, timeout_ms?}`；`expect_login/no_cache` 折叠进 `options` 或由 `action` enum 承载。借鉴 mcp-chrome `chrome_computer` 用 `action` enum 折叠 15+ 动作的经验（08 F3.2.x 已引用）。 |
| `confidence` | high |

### 🟡 F2 — browse_headless 与 browse_logged_in 高度相似（双 Channel 内联差异率低）

| 字段 | 内容 |
|---|---|
| `rule_id` | R-ABS-02（内联差异率低/错误抽象）+ R-CI-08（知识重复） |
| `severity` | 🟡 Warn |
| `location` | 08 F3.2（browse_headless）/ F3.3（browse_logged_in） |
| `evidence` | 两通道都封装 chrome-devtools-mcp，差异仅子进程 flag（`--headless --isolated` vs `--browser-url`）；参数集 ~80% 重叠；行为（navigate/snapshot/screenshot/extract）几乎一致。 |
| `why` | ① **内联差异率 <50% 是错误抽象信号**（01 §3.4 有害象限）：两个独立 Channel 共享大部分实现，只有子进程参数不同；② **知识重复**（R-CI-08）：navigate/snapshot/extract 的逻辑在两通道各实现一遍 = 同一决策两处实现。 |
| `suggestion` | MVP **保持双工具**（CC 语义区分 + fallback 链需要，08 的论点成立），但**强制共享 `BaseBrowseChannel` 实现**——两通道只差 channel 配置（subprocess flag + cookie 策略），行为逻辑全部上提到基类。v0.3 评估是否合并为单 `browse(url, action, mode)` + `mode: headless\|logged_in`。 |
| `confidence` | medium（双工具 vs 单工具+mode 是设计权衡，非纯简单性问题） |

### 🟡 F3 — provider 矩阵的变更放大（加一个 provider 改多处）

| 字段 | 内容 |
|---|---|
| `rule_id` | R-CHG-01（touches-per-change）+ R-INT-02（开闭违反） |
| `severity` | 🟡 Warn |
| `location` | 08 F3.6 配置 / 10 D.2 F3.6.1（多 Key 池）/ F3.6.2（provider_type schema） |
| `evidence` | 加一个新搜索 provider 当前需改：`provider_keys` 配置 + `provider_type` schema + `free_quota_per_month` + `policy_risk` + fallback 链顺序 + 配额账本适配器 +（若需 SERP 兜底）selector——**潜在 ≥5 处**（R-CHG-01 阈值）+ **新增变体改 ≥3 处**（R-INT-02 阈值）。 |
| `why` | ① **变更放大**（R-CHG-01）：加 provider 是高频演进（v0.2/v0.3/v0.9 都加），每次触 5+ 处 = 系统在变复杂；② **开闭违反**（R-INT-02）：新变体应通过"扩展"加入而非"修改"多处。 |
| `suggestion` | 统一 `ProviderConfig` 注册表：一个 provider = 一个配置对象（含 type/key/quota/policy/licence/fallback_order），`CapabilityBag` 启动时自动加载并生成 Channel + 配额账本 + fallback 链。加 provider = config 加一项（开闭）。10 的 F3.6.1/F3.6.2 应收敛进这个注册表，而非分散字段。 |
| `confidence` | high |

### 🔵 F4 — 降级机制三套，概念完整性风险

| 字段 | 内容 |
|---|---|
| `rule_id` | R-CI-02（横切关注点变体 >1） |
| `severity` | 🔵 Review |
| `location` | 08 F3.4（60s/60min 熔断）/ 10 D.1 F3.4（扩容触发集）/ 10 D.2 F3.4.6（政策 gate）/ 08 §3.4 传输层 fallback |
| `evidence` | 三套降级机制：① 技术熔断（60s 短 + 60min 长）；② 政策风险 gate（F3.4.6，manual-switch）；③ 传输层 fallback（httpx→curl_cffi）。 |
| `why` | **横切关注点（降级）多种做法 >1**（R-CI-02）：同一类操作（决定是否降级）三套独立机制 = 概念完整性风险；调用方需理解三套规则。 |
| `suggestion` | 统一降级决策入口 `FallbackDecider`，内部按故障类型分发（技术故障→熔断；政策故障→manual gate；传输故障→transport fallback）。三套机制作为 Decider 的内部策略，对外一个入口。**当前不阻断**——三套对应不同故障类型，分层合理，但需一个统一入口防散乱。 |
| `confidence` | medium |

### 🔵 F5 — Tool Layer 与 Channel Layer 抽象可能重复

| 字段 | 内容 |
|---|---|
| `rule_id` | R-DEP-04（相邻层抽象重复） |
| `severity` | 🔵 Review |
| `location` | 08 §1 分层 / §2.1 BaseChannel |
| `evidence` | Tool（`browse_headless`）与 Channel（`HeadlessChannel.interact`）的参数模型可能高度重叠（都收 url/action/selectors/...）。 |
| `why` | **different layer different abstraction**（01）：相邻两层方法签名/参数雷同 >60% = 下层只是透传，没有自己的抽象职责，模块深度趋 0。 |
| `suggestion` | 明确两层职责差异：Tool 层 = MCP 协议翻译 + 参数校验 + 返回格式化（写磁盘指针）；Channel 层 = 后端交互 + 健康检查 + 子进程管理。两层**参数模型应不同**：Tool 收 `InteractTask`（CC 友好），Channel 收具体的后端请求对象（含 session/timeout/SSRF 通过标记）。 |
| `confidence` | medium |

## 2. 总体简单性健康度

| 刻度 | 状态 | 说明 |
|---|---|---|
| **分层方向（R-FF-01）** | ✅ 达标 | 4 层（Tool/Handler/Channel/Subprocess）方向正确，无层次泄漏 |
| **循环依赖（R-FF-02）** | ✅ 达标 | 设计上无循环（分层 + Channel 注册表） |
| **穿堂式（R-FF-04/R-DEP-03）** | ✅ 达标 | Channel 非纯转发——有增值逻辑（SSRF 校验/状态写盘/fallback 编排/健康检查） |
| **交织度（R-INT）** | 🟡 1 处 | F1 接口过胖（11 参数） |
| **模块深度（R-DEP）** | 🟡 1 处 | F1 同（接口过胖稀释 depth）；F2 双 Channel 相似 |
| **变更放大（R-CHG）** | 🟡 1 处 | F3 provider 矩阵加源改多处 |
| **概念完整性（R-CI）** | 🔵 2 处 | F4 降级三套 / F5 双层抽象重复 |
| **抽象成本（R-ABS）** | 🔵 命中 | F1 参数蔓延 / F2 错误抽象风险 |
| **起步最小集（§1 六条）** | ✅ 大部分 | 设计阶段无法跑 R-FF 适应度函数，但 R-DEP-03（穿堂=0）设计上达标 |

**裁决**：架构**整体合理**（分层清晰 + 复用 media-gen-mcp 验证过的范式 + 边界明确）。主要简单性风险集中在 **3 个 🟡（F1 接口过胖 / F2 双 Channel 相似 / F3 provider 变更放大）**，其中 **F1 是 MVP 就该改的硬伤**。无 🔴（设计上不违反硬不变量）。
