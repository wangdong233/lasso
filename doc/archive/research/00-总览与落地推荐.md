## 一句话结论

**控制浏览器**：首选 **chrome-devtools-mcp**（外部 CDP 驱动，原生 `--headless` 无头、`--slim` 降 token、`--browser-url` 复用已登录 Chrome、Claude Code 一等集成），或 **browser-use**（`skill install` 桥接 CC，自报 Odysseys 榜 87.4% 第一）。两者本质都是「外部代码驱动」，不是「寄生在浏览器进程内」。

**控制计算机**：CC Desktop **内置 computer-use MCP**（macOS，默认关，**不能后台无头**，是兜底工具）；要真正无人值守无头桌面控制，走独立的 **Anthropic Computer Use API + Docker（Xvfb 虚拟显示）**，但官方承认延迟慢、会幻觉坐标、小众/多应用不可靠——把它当「兜底」而非主力。

## 一个重要修正：所谓「寄生 agent 更高效」的真相

你的直觉是「浏览器内寄生 agent 离浏览器更近，效率和性能应该更好」。调研结论是 **部分成立、部分需要纠偏**：

1. **真正同进程寄生的成熟方案，本轮没找到可验证的代表**。WebLLM / Chrome 内置 Gemini Nano / Service Worker agent 这类「在浏览器进程内跑 agent + 本地模型」的方案，目前都没有达到生产可用的成熟度（这是 synthesize 报告的诚实结论，见 caveats #4）。
2. **主流高绩效方案（chrome-devtools-mcp、browser-use、Stagehand v3）本质都是「外部驱动」**——通过 CDP / Playwright 从浏览器外面控制，并不是寄生在浏览器进程里。
3. **它们高效的真正原因不是「寄生 vs 外部」，而是「代码驱动 vs 视觉截图驱动」**。关键证据：在主流视觉桌面 agent 中，**LLM 规划与反思占总延迟的 75%–94%**，截图/定位/执行占比极小（[arXiv 2506.16042](https://arxiv.org/html/2506.16042v1)）。所以 browser-use 这类把规划转成确定性 Playwright 代码的方案，在 web 任务上反超了截图派 CUA。
4. **真正算「寄生形态」的官方方案是 Claude in Chrome 扩展**——扩展确实运行在浏览器里、共享真实登录态，CC 自动优先用它。它是方向 A 里最接近你直觉的落地形态。

**落地含义**：追求效率时，**优先选「代码/结构化驱动 + 把页面状态写磁盘而非灌进上下文」的方案**（见下方 token 对比），而不是执着于「寄生」这个架构标签。

## 必须知道的限制（caveats 精简，完整版见各方案文档）

1. **来源偏向厂商一手文档**：chrome-devtools-mcp / CC / Computer Use / OmniParser / UFO 的核心证据都来自各家官方文档，存在自我宣传偏向；**反而负面限制（CU 的延迟/幻觉、CC desktop 不能无头）更可信**，因为厂商有动机淡化缺陷。
2. **benchmark 方法论不对称**：browser-use 的 Odysseys 87.4% 是 self-submitted，而被比较的 OpenAI/Anthropic/Google CUA 是作者评测，口径不统一；且夺冠条目底层用的就是 Anthropic Opus 4.7，**不是纯架构优势**。
3. **时间敏感性高**：GUI/CUA 领域 2025–2026 月级迭代，模型名（Sonnet 5 / Opus 4.8）与 beta header（`computer-use-2025-11-24`）都属较新版本，6 个月后部分数字（75–94% 延迟占比、OmniParser 60% 提速）可能过时。
4. **「寄生 agent」框架被部分误用**：browser-use 实为外部 Playwright 驱动，并非真正寄生；真正同进程方案（WebLLM / Gemini Nano / Service Worker）本轮未找到成熟代表。
5. **CC desktop 能力有平台/套餐门禁**：Pro/Max 套餐、macOS（CLI）/ Windows（仅 Desktop app）、claude.ai 鉴权（非 Bedrock/Vertex），且仅交互式会话（不支持 `-p`）。落地前**务必核对许可**。
6. **CC 内置 computer-use 无法后台无头**：默认关闭、macOS 需 Accessibility + Screen Recording 权限、运行时隐藏其它窗口、仅与已批准前台 app 交互、不支持 `-p`。
7. **chrome-devtools-mcp 默认工具数约 28–29**，要拿到完整 ~52 需开启多个非默认 flag（`--memoryDebugging` / `--category-extensions` / `--experimentalVision` 等）。
8. **个别 claim 的搜索配额耗尽**（OmniParser 部分无独立第三方佐证），证据强度主要靠一手源撑起。

## 4 个开放问题（值得后续深挖）

1. 是否存在真正「寄生」在浏览器进程内（同进程、共享 DOM/网络/登录态、无 CDP/IPC 往返）且用本地模型（WebLLM / Gemini Nano / Service Worker）的成熟方案？——本轮没找到。
2. CC Desktop 的内置 computer use 能否用虚拟显示器（Xvfb）+ 远程桌面强行无头化，还是「隐藏其它窗口 + 仅前台已批准 app」是产品硬约束？——对无人值守桌面部署是关键。
3. 「Claude in Chrome」扩展与 CC 之间的具体通信通道（native messaging / stdio / MCP / WebSocket）未被本轮证据明确验证，而它直接决定登录态复用的稳定性和跨域能力。
4. 在真实美元成本（dollars/task）维度上，代码驱动（browser-use + Playwright）与视觉驱动（CU API + 截图 loop）在同类长程任务上的量化对比缺失——这对选型比延迟数字更决策性。
