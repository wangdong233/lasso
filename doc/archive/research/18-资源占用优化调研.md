# 18 - 资源占用优化调研（白盒 + 本机实测）

- 日期：2026-08-15
- 基线：lasso-mcp v1.9.0（`npm run build` ✓ / `npm test` 1767 passed ✓ / `npm run check-invariants` 77 INV ✓，本调研期间真实复跑）
- 范围：只调研不改代码（红线遵守）。所有数字来自本机（MacBookPro11,4 / Darwin 21.6.0 / 16GB）真实运行，非引用推测。
- 方法：用 lasso **真实代码路径**（`dist/subprocess/SubprocessManager.js` + `dist/channels/HeadlessChannel.js`）驱动，`ps`/`pgrep -P` 递归采样进程树 RSS/CPU。采样脚本存 `/tmp/lasso-meter.mjs`、`/tmp/lasso-flags-test.zsh`（附录 A 可复现）。

## 1. 现状量化（本机实测）

### 1.1 单个 headless 实例的完整生命周期解剖

起 1 个 headless spec（= 1 个 CC 会话里的 lasso browse_headless），采样进程树：

| 阶段 | 进程树 | ps-sum RSS | 说明 |
|---|---|---|---|
| spawn 后 idle（未浏览） | 2 procs（npx shim + node MCP server） | **459MB** | **Chrome 尚未拉起**——chrome-devtools-mcp 0.3.0 首次需要浏览器的 tool call 才 `puppeteer.launch`（白盒：`browser.js` `ensureBrowserLaunched` 懒调用） |
| idle 持续 100s | 2 procs | 459MB | 稳定不释放（v1.8 默认挂 1h） |
| 首次 navigate example.com 后 | **8 procs**（+ 系统 Chrome 主进程 + 5 个 Chrome Framework 子进程） | **685MB** | Chrome 树增量 ~226MB；启动瞬间 Chrome 主进程 cpu=35%、子进程 2.9–14% |
| `subproc.shutdown()` 后 | 0 procs | 0 | v1.9 G5 树杀干净（`post-shutdown tree=1 RSS 0`） |

关键结构性发现：**idle 成本（2 个 node 进程）与负载成本（+整棵 Chrome 树）是两笔账**。Chrome 只在第一次真实浏览时才拉起。

### 1.2 idle watchdog 生效前后（v1.8 → v1.9 对比实测）

用 `startZombieReaper(2000, 5000)` 模拟 v1.9 默认 5min 语义（等比缩小）：

- 未导航场景：idle 6.1s 触发 `zombie_reaped`，进程树清零（杀的是 2 个 node 进程，~460MB ps-sum）。
- **导航后场景（Chrome 树存活）**：navigate 后树 = 8 procs / 721MB；idle 6.8s 同样整树回收清零。**watchdog 对「Chrome 树 + MCP 层」两层都有效**（G5 `_kill` 带 `_killTreeSync` 的效果实证）。

结论：v1.9 默认 `LASSO_HEADLESS_IDLE_MS=300000`（config.ts:197）把「工作流结束后浏览器继续与用户日常浏览器争资源」的暴露窗口从 v1.8 的 1h 压到 5min。**窗口内仍是满占用**——这是本调研 §2 要压的对象。

### 1.3 复用 vs 每调用（路线 d 量化）

| 模式 | 每调用开销 |
|---|---|
| 每调用起+杀（3 轮实测） | **4026 ms/调用**（npx 解析 + MCP initialize 握手） |
| 懒启动后跨调用复用（v1.9 现状） | 首次 3565ms，之后 **0 ms/调用** |

即现有「每 server 一实例 + 跨调用复用」已是最优基线（确认，无需改）。每调用一实例还会每次重付整棵 Chrome 拉起（本实验未导航故未含 Chrome 启动 ~1–2s，实际差距更大）。

### 1.4 并发累积（52 进程事故的机制还原）

模拟 5 个并发 CC 会话（各 1 个 lasso server → 各 1 个 headless spec，仅 idle 态、Chrome 未拉起）：

> **5 实例 = 10 procs，ps-sum RSS 1615MB（均摊 323MB/实例）**

事故日 52 个 chrome-devtools-mcp 进程 ≈ 20+ 个 server 对，再叠加多个 Chrome 实例/窗口（每个导航后 +~500–700MB ps-sum、启动期多进程吃 CPU），16GB 本机（还有 Docker VM 2GB + CC 会话）直接进入内存压力/swap → 用户日常浏览器卡顿。**时间相关性定性成立**：卡顿窗口 = 实例积留窗口；v1.9 的 5min watchdog 把该窗口从 1h 级压到分钟级，但多并发场景仍是 N×323MB 起步。

### 1.5 度量口径告诚（诚实性）

`ps rss` 逐进程求和会把 node/Chrome 共享库页**重复计数**，物理占用低于 ps-sum（方向性对比不受影响：同一口径下比较）。精确物理占用需 `footprint`（需 root），本调研未采。

## 2. 替代路线评估

### 2a. Chrome 资源削减 flags —— **裁决：WATCH（收益边缘 + 需版本升级才可用）**

**上游白盒（npx 缓存真实源码，非文档猜测）**：

- **0.3.0（当前 LOCKED）无透传**：`build/src/cli.js` 只文档化 7 个自有 flag（browserUrl/headless/executablePath/isolated/customDevtools/channel/logFile）；`build/src/browser.js:56` Chromium args **硬编码** `['--hide-crash-restore-bubble']`（仅追加 customDevTools）。
- **顺带发现一个既有 bug**：HeadlessChannel.ts:63 传的 `--disable-blink-features=AutomationControlled` 是 unknown flag，yargs 不报错但 **0.3.0 从不转发给 Chromium——该 flag 实际是死的**（源码可证，比 parse13 当时标记的「L3 待验证」更糟：白盒即可否定）。JS evasion 路径仍有效，故无功能回归，但注释语义失真。
- **1.7.0 有 `--chrome-arg`（可重复）+ `--ignore-default-chrome-arg` + `--proxy-server`**；npm pack 二分实锤：**0.8.0（2025-10-10）引入**，0.7.1 及以前无。
- 版本升级契约面：0.3.0 ↔ 0.8.0 **工具名集合实测完全一致**（各 26 个，本机 listTools diff：removed=[] added=[]）——升级到 0.8.0 的 BrowseChannel.actionDispatch 风险低（schema 细节仍需 Phase F 契约快照重跑）。

**flags 本身收益实测**（受控对照，同一 URL 同一等待，附录 A2）：

| 形态 | procs | ps-sum RSS |
|---|---|---|
| 系统 Chrome headless 基线 | 9 | 579MB |
| + `--disable-gpu --renderer-process-limit=1 --js-flags=--max-old-space-size=256` | 8 | 533MB（**−8%**） |

puppeteer 默认 args 已含 `--disable-background-networking/--disable-sync/--disable-component-extensions-with-background-pages` 等大头（ChromeLauncher.js 实测），剩余可省空间很小。

**`--single-process`：NO-GO**。上游证据：Chromium 官方讨论弃用且 **macOS 上启动即 CHECK 失败**（[chromium-dev](https://groups.google.com/a/chromium.org/g/chromium-dev/c/9Nmw91P45wM)）；new headless 下直接崩溃（[puppeteer-sharp #2512](https://github.com/hardkoded/puppeteer-sharp/issues/2512)）；本质是 test-only flag。

**迁移代价**：锁版本 0.3.0→0.8.0（package-lock + LOCKED_CDP_MCP_VERSION + 契约快照），半天级。**收益 −8%**——性价比低于 2c，故只 WATCH；若为修死 flag 而升级则顺带获得透传（见 §3 P2）。

### 2b. browse_headless 共享用户浏览器（`--browser-url` 复用） —— **裁决：NO-GO（默认路径）**

- 机制可行：0.3.0 即支持 `-u/--browser-url`（cli.js 实证；LoggedInChannel 已用此机制连 9222）。省整棵独立 Chrome 树（每实例导航后 ~500–700MB ps-sum + 启动 CPU 尖峰）。
- 风险（压倒收益）：
  1. **语义自毁**：headless 通道的存在意义 = 干净隔离 + stealth 反检测（HeadlessChannel 类注释自述）。连用户 profile = 与 logged_in 通道同质化，且用户日常 Chrome 的扩展/字体/状态直接污染指纹一致性。
  2. tab 卫生依赖机制三（TabSession 快照/恢复），任何崩溃路径泄漏 tab 即直接伤害用户浏览器；52 进程事故同级信任度不足。
  3. CPU 争用**并未消失**：渲染工作转进用户浏览器进程树，renderer 竞争依旧，只是省了 browser/GPU/utility 进程开销（~200–300MB 量级）；且崩溃耦合（我方页面 OOM 可能拖垮用户整个浏览器）。
- 保留 niche：logged_in 通道已是这条路的受控形态。headless 默认不走。

### 2c. 更轻的渲染引擎 —— **裁决：GO（headless-shell，v1.9.x 首选增量）；direct-CDP 去 mcp 层 WATCH**

**chrome-headless-shell（旧 headless 独立二进制）**：

| 形态（同口径受控实测） | procs | ps-sum RSS |
|---|---|---|
| 系统 Chrome headless | 9 | 579MB |
| **chrome-headless-shell 148**（~/.cache/puppeteer 已有） | 4 | **110MB（−81%）** |
| shell + 削减 flags | 4 | 140MB（flags 反而略差，不叠加） |

- **L3 验证通过**：`chrome-devtools-mcp@0.3.0 --headless --isolated --executable-path=<chrome-headless-shell>` 经 lasso SubprocessManager 真跑，listTools 26 个、navigate example.com **599ms** 正常。**锁版本 0.3.0 不用动**（`-e` 0.3.0 就有）。
- 上游定位背书：官方文档明确 chrome-headless-shell 为自动化场景专用、更小更快；new headless 是完整浏览器故更重（[Chrome for Developers](https://developer.chrome.com/docs/automation-and-testing/headless-chrome-shell)、[chromote 对比](https://rstudio.github.io/chromote/articles/which-chrome.html)）。
- 风险与缓解：
  - 指纹差异（shell 的 UA 含 HeadlessChrome）→ lasso StealthEngine 本就覆写 UA（windows_chrome_120 profile），主要检测点已覆盖；剩余差异（CDP 特性面）需 sannysoft 类实测一道再转默认。
  - 二进制管理：本机已被 media-gen-mcp 的 puppeteer 下载至 `~/.cache/puppeteer/chrome-headless-shell/`（582MB，多版本）；lasso 不引新 dep 的路线 = doctor 探测 + `LASSO_HEADLESS_EXECUTABLE` 环境变量 opt-in，用户/兄弟工具已下载则零成本复用。
  - 迁移代价：**极小**（HeadlessChannel spec args 追加一个 `-e` + config 一项 + INV 一条 + doctor 一项）。

**Puppeteer 直连 CDP（去 chrome-devtools-mcp 中间层）**：省 npx shim + node MCP server（idle 态 ~323MB ps-sum/实例）+ ~3.5s 首启延迟。但 BrowseChannel 整个 actionDispatch 建立在 MCP tool 协议上，等于重写浏览通道核心（LoggedInChannel 的 CdpClient 仅 200 行、只服务 cookie/tab 语义）。在 headless-shell 落地前收益无法叠加评估 → **WATCH**，先拿 −81% 的浏览器层收益。

### 2d. 单实例复用加强 —— **裁决：已是最优基线（确认，无动作）**

见 §1.3：懒启动 + 跨调用复用 = 首次 3.5s、后续 0ms；每调用一实例 = 4s+/调用且重付 Chrome 树。剩余问题不在「复用不够」而在「**多 server 各一实例**」（§1.4）——根治要跨进程共享（daemon 化），属架构级改动：**WATCH**（与 direct-CDP 同批评估；daemon 引入生命周期/权限边界新面，违背当前「每 CC 会话独立 stdio server」的简单性）。

## 3. 推荐组合与 roadmap

| 优先级 | 项 | 动作 | 依据 |
|---|---|---|---|
| **P0（已随 v1.9.0 落地，本次复核有效）** | idle watchdog 默认 5min + touchKeepalive；chrome-stop 台账收尾；TabSession 恢复 | 无新增 | §1.2 双场景实测树清零 |
| **P1（建议 v1.9.x 下一个增量）** | headless-shell opt-in：`LASSO_HEADLESS_EXECUTABLE` → HeadlessChannel spec 追加 `--executable-path`；doctor 加探测项；INV 加守护 | 半天级，零新 dep | §2c：−81% 浏览器层占用，0.3.0 原生支持，L3 已通 |
| **P2（小修，随 P1 顺手）** | 处理死 flag：升 LOCKED 0.3.0→0.8.0 拿 `--chrome-arg` 真透传（工具面实测不变，契约快照重跑），把 `--disable-blink-features` 改为 `--chrome-arg=--disable-blink-features=...`；或暂不升级则修正 HeadlessChannel 注释诚实化 | 半天级 | §2a 白盒：现 flag 从未到过 Chromium |
| **WATCH** | LOCKED 升 1.7.x（更多 flag/安全面）；direct-CDP 去 mcp 层；daemon 多会话共享单实例 | 观察 headless-shell 落地后的剩余占用再决策 | §2c/§2d |
| **NO-GO** | `--single-process`（macOS 崩溃）；browse_headless 默认连用户浏览器（语义自毁+污染+崩溃耦合）；本轮做 direct-CDP 全量重写 | — | §2a/§2b |

**组合后量化预期**（单实例、导航后）：685MB → ~110MB（shell）+ 323MB（mcp 层不变）≈ 433MB ps-sum；叠加 5min idle watchdog 的窗口压缩，多并发场景（§1.4 的 323MB/实例 idle 部分）需 WATCH 项（daemon/direct-CDP）才能进一步压。
