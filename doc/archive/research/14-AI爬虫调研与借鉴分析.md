## 0. TL;DR

1. **结论：Lasso 应该「借鉴轻量模式」而非「做爬虫」**——纯交互抓手的定位不变，但要从爬虫生态抄 2-3 件能解决真实痛点的具体能力（不是抄架构）。

2. **唯一值得抄的"硬缺口"是 LLM 友好抽取**：当前 `browse_*/fetch_url` 抓回原始 HTML 直接喂下游是 token 浪费，应集成 **Trafilatura（Apache-2.0，纯 Python 子依赖）** 做默认 markdown 精炼管线，并 opt-in 引入 **Crawl4AI fit_markdown 模式（citation `⟨N⟩` 角标 + BM25/Pruning 内容过滤）**。其余爬虫能力（frontier/调度/去重/批量/反封禁/持久化队列）**全部是上层编排者职责，不是 Lasso 的活**。

3. **基座可能性成立但不推荐追求**：Lasso 的四通道原语 + fallback + forest 确实适合做"爬虫编排层之下的基座"，但 ① 直接用 Crawl4AI（Apache-2.0，Python，已成熟）比自己造基座更省事；② 把 Lasso 当基座会诱导第二套范式（frontier/调度），直接撞 R-CI-02 红线。**保持 Lasso = 原语层，爬虫层由用户/上层框架（Crawl4AI/Crawlee）自行选择**。

4. **三条路线推荐 ②**：① 不做爬虫保持纯交互抓手（cleanest，但留着 token 浪费债）→ ② **借鉴轻量模式增强 browse/fetch_url 抽取**（sweet spot，v1.1+ 小增量）→ ③ 做完整爬虫层/基座（违反非目标，违反 R-CI-02，不推荐）。

5. **协议陷阱必须避坑**：Firecrawl（AGPL-3.0）/ Skyvern（AGPL-3.0）/ AgentQL（闭源 SaaS）**不可作代码依赖**，只作竞品/对比对象。可深度借鉴/集成的只有 **Apache/BSD/MIT 许可**：Crawl4AI（Apache）/ Crawlee（Apache）/ Scrapy（BSD）/ Trafilatura（Apache）/ Spider（MIT）/ Lightpanda（开源）/ AutoCrawler（学术，需查 LICENSE）。

## 1. Lasso 现状定位

**一句话**：Lasso 是 CC 的**全交互**对外抓手 MCP（npm `lasso-mcp`）——通过这唯一一个 MCP，让 CC 高效和**浏览器 + 桌面**交互。与 media-gen-mcp（图像抓手）双子星。

**四通道**（[08 §0](08-media-interact-功能架构.md)）：

| 通道 | 后端 | 职责 |
|---|---|---|
| `search` | 智谱 web-search-prime + Brave/Bing 多源（v0.2/v0.9） | 结构化搜索 API |
| `browse_headless` | chrome-devtools-mcp `--headless --isolated` | 干净无头抓取 / SERP 兜底 |
| `browse_logged_in` | chrome-devtools-mcp `--browser-url :9222` | 复用本机已登录 Chrome（不解 2FA） |
| `desktop` | macOS AXAPI（Rust helper，v0.3.5+） | 原生 app 操控（Finder/Mail/Safari/Xcode） |

**架构红线**（[08 §0.7 R-CI-02](08-media-interact-功能架构.md)）：四通道**共享同一套** fallback 范式（isFallbackWorthy/getFallbackProvider/activeProvider/60s+60min 熔断）/ 状态模型（InteractTask/stateId/expect/StateStore LRU）/ 工具描述风格 / 熔断策略。**任一独立即违例**。

**当前能力边界**（关键判断）：
- ✅ **单次抓取 / 单次会话交互**：search→browse_headless→browse_logged_in 单链；browse 多步链式（steps）；desktop AX tree 操控
- ✅ **跨模态 fallback**：search→browse_headless 实搜；desktop ax→appleScript→cgEvent→screenshotVlm
- ✅ **multi-root forest**（v0.4+）：@pN（browse CDP page）+ @wN（desktop AX window）双空间
- ❌ **批量爬取**：无 URL frontier / 调度 / 去重 / 递归广度遍历（非目标 [08 §7.1](08-media-interact-功能架构.md)）
- ❌ **corpus 持久化**：明确不做（非目标）
- ❌ **LLM 友好抽取**：fetch_url（v0.5）抓回原始 HTML，**未做 markdown 精炼/内容过滤/citation 压缩** ← 这是真实痛点

**当前版本**：[09](09-media-interact-实施排期.md) 显示 v0.1-v0.9 已交付（含 v0.3.5 DesktopChannel + v0.4 forest + v0.8 cookie AES-256-GCM + v0.9 多引擎兜底），**v1.0 是稳定发布目标**（跨平台 + 全量测试 + 文档）。本报告推荐的增强落在 **v1.x post-stable**，不进 v1.0 范围（防范围蔓延）。

### 2.2 三条关键观察（决定后续判断）

**观察 A：LLM-as-router 在开源界仍是空白**。调研范围内**没有任何一个开源项目做到「LLM 逐 URL 决定 frontier 下一步」**。所有"AI 爬虫"的 LLM 参与都在：① 规则生成（AutoCrawler）② 页面抽取/描述（ScrapeGraphAI DescriptionNode）③ 查询扩展/语义打分（Crawl4AI AdaptiveCrawler embedding）④ 饱和度判定（Crawl4AI 三指标）。**URL 选择一律是启发式（BFS/DFS/keyword/BM25/embedding 相似度）**。这意味着：① 真正的"LLM 逐 step 选 URL"是开源机会窗口，但 ② **这不是 Lasso 的机会**——Lasso 是原语层，不是上层编排者。

**观察 B：HTML→LLM-friendly markdown 是工业事实标准**。Crawl4AI fit_markdown、Firecrawl 默认 markdown 输出、Trafilatura（被 HuggingFace/IBM/Microsoft Research 依赖）、Spider HTML→MD、Lightpanda `markdown` MCP 工具——**所有抓取栈都在做这件事**。Lasso 的 fetch_url **没做**，是真实的、可量化（token 浪费 30-70%）的痛点。

**观察 C：反封禁作为商业模式切片已成行业共识**。Firecrawl 云独占 Fire-engine stealth / Skyvern Cloud 闭源反爬 / AgentQL 全闭源 / Agent-E 企业版闭源——**OSS 自托管的反封能力普遍缩水**。Lasso 走 OSS 自托管 + 真实 Chrome（browse_logged_in 天然反检测）路线，与行业切片不撞，**这是 Lasso 的差异化护城河**。

## 3. 差距分析：Lasso 缺什么 vs 爬虫有什么

| 能力 | Lasso 现状 | 爬虫生态成熟度 | 是否 Lasso 该补？ | 理由 |
|---|---|---|---|---|
| **LLM 友好抽取（HTML→markdown）** | ❌ 缺（fetch_url 返原始 HTML） | ✅ 工业事实标准（Trafilatura/Crawl4AI fit_markdown） | **✅ 该补** | 真实 token 浪费 30-70%，下游 LLM 决策质量受损；单点集成零架构冲击 |
| **内容过滤（去掉导航/广告/评论噪音）** | ❌ 缺 | ✅ Pruning/BM25 ContentFilter（Crawl4AI） | **✅ 该补（opt-in）** | 与上一项同根，opt-in 给 power user |
| **citation 压缩（`⟨N⟩` 角标 + References）** | ❌ 缺 | ✅ Crawl4AI `convert_links_to_citations` | 🟡 可选 | RAG 上下文预算优化，但 Lasso 不做 RAG（非目标） |
| **URL frontier / 调度 / 去重** | ❌ 缺 | ✅ Crawlee RequestQueueV2 / Scrapy 双队列 / Spider SQLite | **❌ 不补** | 上层编排者职责；补了违反 [08 §7.1 非目标](08-media-interact-功能架构.md)（"不做 corpus 持久化"） |
| **递归广度遍历（BFS/DFS/BestFirst）** | ❌ 缺 | ✅ Crawl4AI `deep_crawling/` + FilterChain + URLScorer | **❌ 不补** | 同上；Lasso 是单次/链式交互，不是整站爬取 |
| **批量并发（arun_many / AutoscaledPool）** | ❌ 缺 | ✅ MemoryAdaptiveDispatcher / AutoscaledPool | **❌ 不补** | 同上；批量是上层 |
| **反封禁（stealth/proxy 轮换/fingerprint）** | 🟡 部分（v0.4 stealth + 真实 Chrome） | ✅ 完整栈（Patchright/playwright-stealth/Fire-engine） | **❌ 不补** | browse_logged_in 用真实 Chrome 是天然反检测；继续堆 stealth 是军备竞赛（[08 §7.2 已识别为债](08-media-interact-功能架构.md)），与 Lasso"不解 2FA"边界一致 |
| **持久化队列（断点续爬）** | ❌ 缺 | ✅ Scrapy JOBDIR / Crawl4AI Redis / nuq-postgres | **❌ 不补** | 明确非目标（"不做 corpus 持久化"） |
| **LLM 抽取（schema-driven structured data）** | ❌ 缺 | ✅ Crawl4AI LLMExtractionStrategy / scrapy-llm / Skyvern page.extract | 🟡 暂不补 | LLM 抽取是上层职责；Lasso 提供"干净 markdown"即可，结构化抽取让 CC 自己用 tool calling 做 |
| **饱和度检测（Coverage/Consistency/Saturation）** | ❌ 缺 | ✅ Crawl4AI AdaptiveCrawler 三指标 | **❌ 不补** | 这是"何时停爬"的决策，是上层编排者的问题；Lasso 单次交互不需要 |
| **跨页规则合成（AutoCrawler rule_synthesis）** | ❌ 缺 | ✅ AutoCrawler StepbackCrawler | **❌ 不补** | 学术路线，泛化性未证实；与 Lasso 范式无关 |
| **稳定元素定位（无 unique id 的页面）** | 🟡 部分（@eN ref + stateId scope） | ✅ Agent-E `mmid` 自注入 + Skyvern persistent sessions | 🟡 可选 | 与 multi-root forest 设计同向，可借 `mmid` 思路增强 browse OutlineNode 稳定性 |

**判断**：爬虫生态的 8 项核心能力里，**只有 2 项是 Lasso 真正该补的**——LLM 友好抽取 + opt-in 内容过滤。其余 6 项要么是明确非目标，要么是上层编排者职责。**Lasso 的"差距"被高估了——Lasso 不是爬虫，本来就不该有 frontier/调度/批量**。

## 4. 借鉴分析：哪些爬虫模式可直接抄进 Lasso

> **评判标准**：① 解决真实痛点（非自我实现预言）② 不引大依赖（缠绕成本可控）③ 守简单性（02 清单 + R-CI-02）④ 协议安全（Apache/BSD/MIT only）

### 4.1 ✅ 强烈推荐借鉴（必抄）

#### (a) Trafilatura 集成作 fetch_url / browse extract 的默认 markdown 精炼

> **🔴 v1.1 已落地（2026-07-22）—— 引擎选型被推翻**：用户硬约束 + parse12 §4 决策表选定 **JS 原生 defuddle 0.19.1 + turndown 7.2.4**（均 MIT），**非 Trafilatura Python 子进程**。理由：守 R-CI-02 第三运行时红线（Node+Rust 已两套，Python 是第三套）；defuddle 近零 dep（避 jsdom ~10MB 重依赖）。另：用户纠正本文「默认 markdown」为「**默认 raw**」（保留网页元素原始结构有独立语义价值，不强制 AI 适配优化）；markdown / markdown_cited 是 opt-in。详见 [parse12.md](parse/parse12.md) + [parse12-acceptance.md](parse/parse12-acceptance.md)。MarkdownExtractor 已实装于 `src/browse/markdown-extractor.ts` + `content-filter-cite.ts`；69 invariants + 1411 TS tests 全绿。

- **借鉴什么**：把 [Trafilatura](https://github.com/adbar/trafilatura)（Apache-2.0，纯 Python，无浏览器依赖，被 HuggingFace/IBM/Microsoft Research 依赖）作为子依赖，接入 `fetch_url` 和 `browse_headless/browse_logged_in` 的 `action=extract` 后端。
- **落到 Lasso 哪个模块**：`src/channels/browse/`（BaseBrowseChannel 的 extract action）+ `src/tools/fetch_url.ts`。新增 `MarkdownExtractor` 类（封装 Trafilatura 子进程调用，类似 Rust helper 的 stdin/stdout JSON-lines 模式）。
- **代价**：+1 Python 子依赖（~3MB，lxml + trafilatura），需在 `lasso doctor` 加一项检测；**或者** 纯 TS 实现简化版（readability + turndown），但效果不如 Trafilatura。
- **风险**：Trafilatura 本身是单进程库（不是并发引擎），与 Lasso 单次交互语义一致，无并发冲突；作者呼吁赞助但 1.8 之后 Apache-2.0 商业友好。
- **是否守简单性**：✅ 守。**不引第二套范式**——MarkdownExtractor 是 BrowseChannel 的内部子组件，不是新 channel；fallback/state/tool description 全不变。
- **证据**：Crawl4AI `markdown_generation_strategy.py` L155-280 同思路；Trafilatura 是该细分品类的事实最优解（ScrapingHub benchmark 评其为最佳单工具）。

#### (b) Crawl4AI `convert_links_to_citations` 的 `⟨N⟩` 角标模式（opt-in）

- **借鉴什么**：长 markdown 输出时把所有 inline URL 替换成 `⟨N⟩` 角标 + 末尾去重 References 段，节省 RAG 上下文预算。
- **落到 Lasso 哪个模块**：`src/channels/browse/output.ts`（与 bounded output 48KiB + @oN 续页同模块），新增 `citations?: "inline" | "footnote" | "off"` opt-in 参数。
- **代价**：~50 行代码（URL 正则 + 去重 Map + 末尾拼接）；零依赖。
- **风险**：默认 off，不破坏既有调用方；对 RAG-heavy 用户显著省 token。
- **是否守简单性**：✅ 守。是既有 output 模块的功能扩展，非新范式。

### 4.2 🟡 推荐借鉴（可选，v1.2+）

#### (c) Crawl4AI `PruningContentFilter` / `BM25ContentFilter` 模式（opt-in）

- **借鉴什么**：在 markdown 输出前用内容过滤（Pruning 算法或 BM25 相似度）筛掉导航/广告/评论噪音。fit_markdown 模式。
- **落到 Lasso 哪个模块**：同 (a) 的 `MarkdownExtractor`，加 `content_filter?: "pruning" | "bm25" | "off"` opt-in 参数。
- **代价**：Pruning 算法 ~200 行 TS（lxml 实现 port 到 TS 工作量大，建议接 Trafilatura 的 `prune_xpath` API）；BM25 相似度 ~100 行 TS。
- **风险**：内容过滤是启发式，过度过滤可能丢信息——必须 opt-in 默认 off。
- **是否守简单性**：🟡 边缘。Pruning 算法本身复杂，TS port 有维护负担；**建议直接走 Trafilatura 的 `prune_xpath` 参数**，不在 Lasso 里重写。

#### (d) Lightpanda MCP 工具签名规范（semantic_tree / nodeDetails / interactiveElements）

- **借鉴什么**：Lightpanda 的 MCP 工具设计比"裸 DOM dump"更 LLM 友好——`semantic_tree`（带 maxDepth/backendNodeId）、`nodeDetails`（按 ID 查节点详情）、`interactiveElements`（只抽可交互元素）。
- **落到 Lasso 哪个模块**：影响 `browse_headless` 和 `desktop` 的 outline 输出 schema。Lasso 现有 `OutlineNode{role,label,ref,rect,children,pictureOnly?}` 已接近 Lightpanda 思路，**无需重写**，但可以加 `maxDepth` 参数（与 desktop `maxDepth` 对齐）和 `interactiveOnly?: boolean` opt-in。
- **代价**：~30 行（maxDepth 截断 + interactiveOnly 过滤）。
- **风险**：零——是既有 OutlineNode 的可选行为。
- **是否守简单性**：✅ 守。**与 multi-root forest 设计同向**，强化既有抽象。
- **证据**：[Lightpanda `src/mcp/tools.zig`](https://github.com/lightpanda-io/browser) 的 `tool_list`。

### 4.3 🟡 边缘借鉴（视需求，不强制）

#### (e) Firecrawl Multi-Engine Fallback Pipeline 模式（不抄代码）

- **借鉴什么**：Firecrawl 的引擎注册表按 quality tier 排序自动回退（fetch 5 → fire-engine 10 → playwright 20 → chrome-cdp 50）+ Feature Flag 决定引擎选择。
- **落到 Lasso 哪个模块**：**Lasso 已经有**（[08 §3.4](08-media-interact-功能架构.md) 的 isFallbackWorthy/getFallbackChannel + CapabilityBag priority + activeProvider）。**无需借鉴**——Lasso 的 fallback 范式已经覆盖这个模式。
- **代价**：零。
- **风险**：Firecrawl AGPL-3.0，**代码不可抄**；只学模式。
- **是否守简单性**：✅ 守。Lasso 的 fallback 是单一引擎，已经比 Firecrawl 的多 worker 拓扑更简洁。

#### (f) Spider `cache_openai`（moka）思路

- **借鉴什么**：LLM 响应缓存（moka LRU）省成本——`cache_openai` flag。
- **落到 Lasso 哪个模块**：仅当 Lasso 未来引入 LLM 抽取（如 screenshotVlm 档）时才适用；当前 Lasso 不直接调 LLM，**暂不需要**。
- **是否守简单性**：✅ 守。但当前不适用，推迟到 Lasso 真有 LLM 调用层时。

### 4.4 ❌ 不借鉴（明确否决）

| 模式 | 否决理由 |
|---|---|
| Crawl4AI AdaptiveCrawler 三指标饱和检测 | 是"何时停爬"的决策，属上层编排者；Lasso 单次交互不需要 |
| Crawlee RequestQueueV2 / Scrapy 双队列 | frontier 持久化是上层职责，违反非目标 |
| Scrapy 中间件 priority chain | Lasso 已有 fallback 引擎 + QualityGate，无需引入第二套中间件链（违反 R-CI-02） |
| Skyvern `page.act/extract/validate/prompt` 四命令 | 与 Lasso `browse(action, options)` action-enum 折叠语义重叠；AGPL-3.0 不可抄代码 |
| AgentQL Query-as-schema DSL | LLM 抽取是上层职责；Lasso 提供 markdown 即可，结构化让 CC 用 tool calling |
| AutoCrawler Reflexion 循环 | Lasso 已有 `expect` 后置 + tri-state outcome（worked/didnt/unknown），已是同源思想 |
| ScrapeGraphAI LangChain DAG 抽象 | Lasso 是 MCP server，不是 LangChain graph；引入会破第二套范式 |
| Stagehand `act/extract/observe/agent` 四原语 | v0.4 已预留 `browse_cloud/stagehand` 通道（[08 §3.11](08-media-interact-功能架构.md)），作 provider 接入即可，无需借范式 |
| Lightpanda 作为 browse_headless 默认后端 | Beta 阶段（"many websites now work... you may still encounter errors"），稳定性未到 Chrome 水平；**作可选后端 v2.0+ 评估** |

## 5. 基座可能性：Lasso 作为基座，爬虫层在上

### 5.1 架构图（理论上成立）

```
┌─────────────────────────────────────────────────────────────┐
│  上层爬虫编排层（用户/第三方框架自选）                          │
│  Crawl4AI / Crawlee / Scrapy / Firecrawl / 自写 LLM router   │
└──────────────────────────┬──────────────────────────────────┘
                           │ 调用 Lasso 工具（fetch/browse/extract）
┌──────────────────────────▼──────────────────────────────────┐
│  Lasso（MCP server，原语层基座）                               │
│  - browse_headless / browse_logged_in / fetch_url / desktop  │
│  - 单一 fallback 引擎 + tri-state outcome + StateStore LRU   │
│  - multi-root forest（@pN browse / @wN desktop）             │
│  - 跨模态 fallback（search→browse / ax→appleScript→cgEvent→VLM）│
│  - markdown 精炼（Trafilatura） + opt-in citation/filter      │
└─────────────────────────────────────────────────────────────┘
```

### 5.2 为什么 Lasso 理论上适合做基座

1. **可靠原语**：四通道跨模态 fallback + 诚实三态交付（worked/didnt/unknown）——爬虫层最怕"假成功"，Lasso 的 tri-state 直接解
2. **登录态**：browse_logged_in 复用本机已登录 Chrome（Crawl4AI/Firecrawl 自托管版本都没这能力）——绕开 2FA 难题
3. **桌面通道**：desktop 通道（macOS AXAPI）是**爬虫生态完全空白的蓝海**（Crawl4AI/Firecrawl/Crawlee/Scrapy/Skyvern 全部浏览器中心）
4. **forest 统一**：browse CDP page + desktop AX window 统一入口（v0.4+），爬虫层可不区分 surface
5. **状态写磁盘**：4× token 效率，爬虫层调 Lasso 不会爆上下文

### 5.3 反方观点：直接用 Crawl4AI 更省事（诚实不自卖自夸）

| 维度 | Lasso 作基座 + 自写/接爬虫层 | 直接用 Crawl4AI |
|---|---|---|
| **首日可用** | ❌ 需用户自己写爬虫编排 | ✅ `pip install crawl4ai` 即用 |
| **frontier/调度/去重** | ❌ 需自建或接 Crawlee | ✅ 内置（MemoryAdaptiveDispatcher + FilterChain + deep_crawling） |
| **markdown 抽取** | 🟡 需自己接 Trafilatura | ✅ fit_markdown 默认开 |
| **登录态/桌面** | ✅ **独家** | ❌ 无（Crawl4AI 不解 2FA，无桌面） |
| **协议** | ✅ MIT | ✅ Apache-2.0 |
| **语言** | TypeScript | Python |
| **集成成本** | 用户需自己粘合 | 开箱即用 |

**结论**：**如果用户的需求是"整站批量爬取"，直接用 Crawl4AI（Python）比让 Lasso 当基座更省事**。Lasso 当基座只在两类场景有附加价值：① 需要登录态的爬取（Crawl4AI 解不了 2FA）② 需要桌面数据源（Crawl4AI 完全空白）。**这两类场景是否频繁到值得 Lasso 主动做爬虫基座？答案大概率是否定的**——保持 Lasso = 原语层，让爬虫层由用户自行选择，是更诚实的定位。

### 5.4 推荐立场（保守）

**Lasso 不主动做爬虫基座**，但**保证可被爬虫层调用**：
- ✅ 暴露干净的 fetch/browse/extract 原语（已有）
- ✅ 提供 markdown 精炼输出（推荐 4.1a）
- ✅ 文档化"如何用 Crawl4AI 调 Lasso 工具"示例（v1.x 文档增量）
- ❌ 不内建 frontier/调度/批量（守非目标）
- ❌ 不营销"Lasso 是爬虫基座"（避免定位漂移）

## 6. 三条路线对比

| 维度 | ① 不做爬虫，保持纯交互抓手 | ② **借鉴轻量模式增强 browse/fetch_url 抽取**（推荐） | ③ 做完整爬虫层/基座 |
|---|---|---|---|
| **核心动作** | 维持现状 | 集成 Trafilatura + opt-in citation/BM25 filter + Lightpanda-inspired maxDepth | 自建 frontier/调度/去重/批量/持久化队列 |
| **工作量** | 0 | ~2-3 周（v1.1 增量）：MarkdownExtractor 类 + opt-in 参数 + doctor 检测 + 测试 | ~3-6 月（v2.0 新方向）：完整 frontier + 调度 + 去重 + 与 fallback 范式融合 |
| **收益** | 现状不变 | ✅ fetch_url/browse extract 下游 token 省 30-70%<br>✅ RAG 场景 citation 压缩<br>✅ 与 OutlineNode 设计同向（maxDepth） | 假性收益：用户大概率仍用 Crawl4AI 而非 Lasso |
| **风险** | 🟡 留 token 浪费债（可控） | 🟢 低（opt-in 默认 off，不破现有调用） | 🔴 高（违反非目标 / 违反 R-CI-02 / 引第二套范式 / 文档震荡） |
| **守简单性** | ✅ 完美 | ✅ 守（MarkdownExtractor 是内部子组件，不是新 channel） | ❌ 破（frontier 是第二套范式，CI 不变量 F3.9.8 须重写） |
| **适合场景** | 当前 v0.9 → v1.0 稳定 | **v1.1+ post-stable 增强**（推荐） | ❌ 不推荐（被 Crawl4AI 全面碾压） |
| **与 v1.0 关系** | 无影响 | v1.x 增强，不进 v1.0 范围 | v2.0 新方向，**会推迟 v1.0 稳定** |
| **协议风险** | 无 | 无（Trafilatura Apache-2.0） | 无（不抄 AGPL 代码） |

**关键判断**：**路线 ③ 是"自我实现预言"陷阱**——为了证明 Lasso 有价值而推荐做爬虫，但实际上 Lasso 在爬虫领域不可能比 Crawl4AI（61k star，3 年迭代）更优。**Lasso 的差异化护城河是"全交互（浏览器+桌面）+ 登录态 + 本地优先"，不是爬虫**。守住这个差异化比扩展到爬虫更重要。

### 8.3 开放问题

1. **Trafilatura Python 子依赖 vs 纯 TS 实现 trade-off**：Python 路线效果好但跨平台打包复杂（Windows lxml）；TS 路线打包干净但效果不如 Trafilatura。**v1.1 MVP 建议先走 TS 简化版**，v1.2 评估 Trafilatura Python 子进程（参考 Rust helper 的 stdin/stdout 模式）。
2. **`⟨N⟩` citation 默认值**：默认 on 还是 off？RAG-heavy 用户受益，普通用户可能困惑。倾向 default off + tool description 推荐。
3. **OutlineNode `interactiveOnly` 与既有 `pictureOnly` 关系**：是正交（可叠加）还是互斥？倾向正交——`pictureOnly` 是节点标记，`interactiveOnly` 是查询过滤。
4. **Lightpanda 长期跟踪**：是否在 v2.0+ 把 Lightpanda 作为 browse_headless 的高性能可选后端（16x 省内存，9x 快）？需监控其 Beta → Stable 进度 + Web API 覆盖率（CORS/部分 API 未完成）。
5. **ScrapeGraphAI MCP server 竞品应对**：[Smithery `@ScrapeGraphAI/scrapegraph-mcp`](https://smithery.ai/server/@ScrapeGraphAI/scrapegraph-mcp) 已存在，与 Lasso 同生态位。Lasso 文档应明确"原语层（Lasso）vs 编排层（ScrapeGraphAI/Crawl4AI）"的分工差异。
6. **真正的 LLM-as-router 是否值得做**：调研确认开源界尚无"LLM 逐 step 选 URL"实现。**这是 Crawl4AI 上层编排的机会窗口，不是 Lasso 的机会**——若用户有此类需求，应在 Crawl4AI/自写编排层之上做，而非塞进 Lasso。
7. **Agent-E `mmid` 注入是否值得借**：提升 browse OutlineNode 在"无 unique id 页面"的稳定性。但 Lasso 已有 stateId scope + @eN ref，是否过度设计？**v1.2+ 评估**，若实测试到稳定性问题再引入。

### 8.4 红线重申

- **R-CI-02 第二套做法红线**：MarkdownExtractor 必须是 BrowseChannel 的内部子组件，不引第二套 fallback / 状态模型 / 工具描述风格。架构不变量 F3.9.8/F3.9.9 全部守住。
- **非目标守住**：不做 corpus 持久化 / 不做 RRF 融合 / 不做自动登录解 2FA / 不做坐标 grounding。
- **诚实定位**：Lasso 是**全交互抓手 MCP**（浏览器+桌面），不是爬虫。借鉴爬虫的 markdown 精炼是为了**让下游 LLM 更高效地消费 Lasso 的抓取结果**，不是为了把 Lasso 变成爬虫。
