## 1. 漏报机制（结构性的，不是偶然）

### 1.1 检索目标函数里根本没有「商业状态」这个变量

五轮审计对外部世界的检索面，逐份核实如下：

| 轮次 | 声明的调研方法 | 实际拉的外部数据 | 商业状态（pricing/存续） |
|---|---|---|---|
| round1-search:5 | 「配合 web 搜索确认**热度与版本动向**」 | GitHub star、npm 周下载、版本号、aimultiple 基准**分数** | 零次 |
| round2-search:7 | 「GitHub API / npm registry 拉热度数据」 | 同上 + Brave 官方博客（增长/Snowflake 集成） | 零次（摸到边了，见 1.4） |
| round3-search:21 | 「热度与版本动向实拉（GitHub API + npm/PyPI registry）」 | star/pushed/版本 | 零次 |
| round4-search:22 | 同上 +「recency=oneWeek 过滤检索 + MCP 生态清单」 | 新项目扫描 | 零次 |
| round5-search:86 | 「两类检索：英文 MCP 生态 + 内容抽取库，均 recency=oneMonth」 | 新项目/媒体面 | 零次 |

检索目标函数只有三个变量：**热度（star）、版本（npm/PyPI）、机制（源码范式）**。Brave 免费档取消、Bing 退役不命中任何一个变量——不是检索不充分，是**检索维度定义里没有这个轴**。

### 1.2 五门槛结构性排除了运营事实类问题的立项通道

五轮 verdict 的调优项门槛逐字一致（round1-verdict:67 / round2-verdict:38 / round3-verdict:47 / round4-verdict:41-46 / round5-verdict:51-56）：

> ①白盒证据差距（有对标锚点）②愿景内既有能力优化 ③代价≤中（单轮可完成）④收益可验证 ⑤不破 INV/tri-state/简单架构

逐条检验「KEY-GUIDE 声称的免费额度已失实」这一候选：

- **门槛①「白盒证据」**：「白盒」= 源码锚点（Lasso 代码 vs 对标代码）。Brave 涨价不是代码差距，**没有源码锚点可引**——它的证据形态是 pricing 页/官方公告，在「白盒」定义之外。round4-verdict:42 把门槛①操作化为「五处全部亲读证实」——亲读的对象永远是**本仓库源码**。
- **门槛②「既有能力范畴」**：优化对象被定义为「能力」（机制/参数/接线）。文档事实核查不被视为能力项。
- **门槛④「收益可验证」**：round4-verdict:45 展示了典型验收形态——「grep 零命中 + 门禁基线不减」。修正免费额度声明的收益是「用户不被误导」，写不成机械断言（其实可以——grep 旧文案零命中——但审计框架从未把文档外部声明当作需要 grep 的对象；1.7 维度只 grep **仓库内部引用**）。
- **结果**：即使某轮审计员偶然看到 Brave 涨价消息，这个问题也**无法通过五门槛进入立项流程**——它会在「这不是白盒证据差距」的第一关被自己过滤掉。

### 1.3 对标范式把「生态共同依赖」变成不可见

审计方法论是「找更强的对标项目」（firecrawl/crawl4ai/open-webSearch/Kindly）。问题被框架为「Lasso vs 对标，谁的机制更好」。而 **Brave/Bing 的商业状态变化对全部对标项目同样生效**（firecrawl 也接 Brave，open-webSearch 引擎列表也有 bing/brave）——在「机制对比」的范式里，所有项目站在同一边，**没有项目能在这个维度上暴露差距**。范式内不可见 = 对标法的方法论盲区：它只能发现「别人有我没有」和「别人比我好」，不能发现「我们共同依赖的地基塌了」。

### 1.4 离事实最近的四次擦肩（证据：不是没有机会，是没有反射）

这是本次取证最有说服力的部分——五轮审计至少四次接近真相，每次都因「问题意识缺失」错过：

1. **round1-search:21**：把 Brave 列入对标表（aimultiple 2026 基准 Brave 97.x），结论「基准结论支持 Lasso『Brave 做英文艺主力』现状」。引用了 Brave 的**评测生态**，没引 Brave 的**定价页**。同表把 Brave 归类「商业付费层（Lasso L4）」——归类的正确反而强化了「我们知道它的商业形态」的错觉。
2. **round2-search:23**（最近一次）：实读 **Brave 官方博客**并写下「新端点属付费层扩张，Lasso 不动」——审计员已经摸到「付费层」三个字，关注点却是「T6 透传的参数面保持兼容，无回归风险」。差一问之遥：「付费层在扩张，那免费层还在吗？」没有问出。
3. **round2-5 全程**：给 **BingChannel 的 freshness 透传**做了 10 处调用点枚举（round4-search:46「10/10 全透传，零静默丢参残余」）+ 6 针 mutation kill（round3/4/5 M 系列）。即：**对一个已退役 12 个月的 API，审计做了全链路最精致的机制验证**——freshness Day/Week/Month 映射、「year 档诚实不传」的降级语义、cache key 纳入，全部白盒钉死。技术验证的精致度与运营感知的归零形成本次事故的最大反差：**验证的是参数怎么传，从没验证请求发过去还有没有人接**。
4. **round5-search:91**：Reddit「I Built a Free Web Search MCP」列 DDG/**Bing**/**Brave**/Tavily 为免费引擎，审计结论「open-webSearch 同族…无新机制面」。如果对第三方「免费」声明有核查反射（「2026 年了，Bing 还能免费？去官方核实一下」），这里就是现成入口。round4-search:35 同样把 brave 列入「2026 盘点老面孔」。

### 1.5 「无新证据不翻案」纪律 + surveillance 锚点全部技术化，监控面越收越窄

round3 起复审纪律是「无新证据不翻案」，round4-verdict:76 把 surveillance 重启条件定义为「**除非 registry/上游 issue 面出现版本级变动**」，round5-verdict:77 静默 surveillance 锚点 =「issue 状态 REST 直验 / curl 原始 HTML / npm 同名异包防误引 / cargo 全路径」。全部监控锚点是 **npm registry、GitHub issue、PyPI**——没有任何一个锚点是 pricing 页、lifecycle 公告页、服务商博客的 changelog。收敛纪律本身正确（防翻案噪音），但它把「什么算新证据」也一并锁死在技术 Registry 里——**循环越收敛，监控面离商业现实越远**。

### 1.6 文档同步机制忠实放大失实，「活文档」反受保护

1.7 冗余与废弃审查（03 清单）检查的是**死文档**（零引用 → 删）。KEY-GUIDE 是**活文档**——被 README×8 七语言引用、每轮全量同步（doc/20-文档同步审计）、doctor 消费。同步机制的语义是「多语言/多页面与源文档一致」，**忠实 ≠ 正确**：它把「2000 次/月」复制到 8 个 README 的 14 处（d3d1b24 --stat 证实修改面），失实覆盖面反而被机制性放大。而 1.7 维度看活文档高引用 = 健康，从不问「它引用的**外部世界**还对不对」。

### 1.7 read-only 验证手段 vs read-write 事实：为什么只有用户能发现

五轮审计的全部验证手段是**旁观式**：读源码、读 star 数、读 registry、读官方博客。而「Brave 免费档已取消」这一事实在 2026-02~08 期间**最可靠的公开探测方式就是走一遍注册漏斗**（read-write、参与者视角）——用户亲自注册、走到绑卡一步，才发现没有 Free 计划。深层问题：**五轮审计从未扮演「按 KEY-GUIDE 从零配置的用户」**。审计自我定位是「架构对标者」；只要有一轮按 KEY-GUIDE §2 的四步指引实际走一遍，第一轮就会撞上付费墙。用户撞墙是系统里唯一的运营事实探测器，而审计循环的输入端**不消费任何用户反馈信号**。

### 1.8 证据阶梯没有运营事实的合法形态

03_审查测试清单 §0.3 定义 L0-L3 四级证据，全部是技术证据（producer 源码 / 真实流量 / 运行时复现）。§0.3 判定准则「证据必须能追溯到 producer 代码或真实流量捕获，不能追溯到另一份断言」——讽刺的是 KEY-GUIDE 的「2000 次/月」正是典型 L0（另一份断言，且源头是 Brave 官网过时营销文案），**五轮审查从未对它做过证据升级**。但清单也确实没有哪一条要求「对文档中的外部世界声明核实」：1.2 项 1 的「producer 契约验证」覆盖外部 API 的**字段形状**（freshness 参数映射确实被白盒验证了），1.2 项 8 把 producer 扩到宿主平台——**唯独没有把 producer 扩到「服务商的商业生命周期」**。外部服务的「存在性/计划层级」和「字段形状」同属契约，前者却无任何条目覆盖。

**结论**：这不是五次独立的偶然疏忽。检索维度定义（1.1）、立项门槛（1.2）、对标范式（1.3）、翻案纪律（1.5）、同步机制（1.6）、验证手段（1.7）、证据阶梯（1.8）——**七层结构层层都在放行同一类失实**。任何一层有拦截，事故都不会发生到第五轮。用户不是比审计员更聪明，而是用户走了审计体系七层结构都不覆盖的唯一路径。

## 3. 修复建议

### a) 03 审查清单新增「运营事实核查」维度

**落点建议：两处联动改**（单独加一节不如嵌进既有骨架有效）：

**① §0.3 证据阶梯追加一行**（位置：`架构想法/03_审查测试清单.md` §0.3 表格末尾）：

> | L-OP | 运营事实（外部服务存续/定价/配额）：官方 pricing 或 lifecycle **公告页**（带日期+URL）、API 控制台亲历截图 | ✅（限时） | 唯一允许「官方页面」作证据的例外；**marketing/产品页 = 仍属 L0**（Brave 官网在免费档取消后仍长期挂 "free tier 2,000/month" 旧文案——openclaw #16629 实证）。定价类 L-OP 有效期 ≤90 天，超期复用前必须重核 |

**② §1.2 数据逻辑追加项 9**（位置：§1.2 项 8 之后，与项 8「宿主平台也是 producer」形成递进）：

> 9. 🔴 **外部服务运营契约（producer 的商业存在性）**：代码或文档依赖的外部 API（一切 key 类集成），其「存续状态 / 计划层级 / 免费额度 / 定价」的每一处**明示或暗示声明**（「免费 2000 次/月」「F0 免费层」「≈永不失败」），必须能追溯到 L-OP 证据（官方公告页或控制台亲历），并标注**核实日期**。声明无法溯源 → 按失实处理（阻断）；溯源对象是 marketing 页 → 仍算 L0（阻断）。**机理**：字段形状契约（项 1）验证「producer 怎么说」，本项验证「producer 还在不在、按什么条件在」——两者同为契约，缺一不可（Lasso 案例：Bing API 2025-08-11 退役后 12 个月，审计仍在其上做 freshness 参数透传的全链路白盒验证，机制验证精致度与存续感知为零并存）。

不建议新开独立的 §1.8 维度：运营事实核查天然是「数据逻辑（对外契约）」的延伸，独立成节会在审查预算里被降权（03 §0.2 审查预算 200-400 LOC 的纪律下，六维已经接近预算上限）。

### b) KEY-GUIDE 时效标注制度

**最小可行形态**（一次 PR 可完成）：

1. **总表加一列「最后核实」**：`doc/KEY-GUIDE.md` §总表（现 :20-28）每个 key 行加日期戳（本轮全部补 2026-08-17，与 d3d1b24 修正对齐）。
2. **每节头部加时效声明**：Brave 节（:84）/Bing 节（:115）/智谱节各加一行「> 本节数额事实最后核实：2026-08-17（核实方式：官网 pricing 页 + 控制台注册亲历）」。
3. **重核触发条件**（写进 KEY-GUIDE 头部「维护规则」段，同时挂进审查 surveillance 锚点）：
   - 距最后核实 **>90 天** 且该节将被引用作决策（新版本发布、README 同步、审查轮引用该数额）；
   - **doctor active probe**（见 c）探测到该 key 计划级异常（403/计划不存在）；
   - 上游发 **lifecycle/pricing 公告**（挂 Brave blog changelog、Microsoft lifecycle RSS 进 round5-verdict:77 的静默 surveillance 锚点清单——这是对 D-5 的直接修补）。
4. **顺手补一个数字**：KEY-GUIDE 明示「智谱按 token 计费，具体数值以平台公示为准」（:68）——智谱侧同样应标核实日期（它是唯一免费主力，失效后果最重）。

### c) doctor 探测 key 的计划级失效——可行性评估

**现状**（白盒核实）：
- `doctor.ts:1095-1107 checkBraveKeys` 是**纯静态检查**：只看 `BRAVE_API_KEYS` env 有没有值（无 → warn「退化为单源 zhipu」），**从不发请求**。
- 运行时分类已存在且够用：`BraveChannel.ts:26-27`「429/5xx → unknown (transient) + markExhausted；**4xx 非 429 → didnt (definitive negative)**」——即 401/403 在搜索链路上已诚实降级，用户只是不知道**为什么**失败。
- Bing：`FallbackChain.ts:25`「key=[] 时 ProviderRegistry 跳过 bing」——没人能再申请到 key，永远空、永远被过滤，是「语法活着的死代码」。

**结论：可行且代价小（S），但不是全新机制——是把既有运行时分类前移到 doctor 观测面**：

1. **Brave active probe（新增 doctor 可选检查）**：doctor 发一次最小真实请求（`GET /res/v1/web/search?q=test&count=1`，单次计费 ≤$0.005，在 $5 月度赠送额度内）。按状态码四分类输出：
   - `200` → pass「key 有效」；
   - `401` → fail「key 无效（被撤销/填错）」；
   - `403` / 响应体含 plan/subscription 类错误 → fail **「计划层级异常——Brave 2026-02 起已无免费档，核查 [pricing](https://brave.com/search/api/)」**（这正是「401 key 错」与「计划不存在」的区分点：401 是凭证问题，403+plan 语义是商业层问题，doctor 把 body 关键词翻译成人话并指向 KEY-GUIDE 时效标注）；
   - `429` → warn「限流（key 本身有效），quota ledger 已短期熔断」。
   - 守红线：probe 必须**显式开关**（如 `--deep` 或配置项）且默认关——doctor 现有检查零网络副作用，不能默默引入「跑 doctor 就花钱」的语义变化（违 tri-state 精神里的「无隐藏成本」）；doctor 输出里明示本次 probe 消耗 1 次额度。
2. **Bing 静态即可全覆盖**：对「配置了 `BING_API_KEYS`」直接输出 fail/info——「Bing Search APIs 已于 2025-08-11 全量退役（微软 lifecycle 公告），该配置永远不可用，建议删除；主链已自动跳过，无功能影响」。无需 probe（服务不存在，probe 必 404/DNS 级失败，反而浪费一次误导性输出）。
3. **不做的事**（守宁缺毋滥）：不自动改写 KEY-GUIDE、不自动禁用 channel——doctor 的职责是把「用户撞墙才发现」变成「doctor 一跑就知道」，**决策留给用户**；也不为「计划层级」建新配置面（403 人话文案已够，无需 Lasso 侧持久化 Brave 计划状态——那是第二套 state，违 R-INT 简单性）。

**三者关系**：b（时效标注）是**制度层**——让每条 key 声明自带保质期；c（doctor probe）是**探测层**——让计划级失效在用户撞墙前可见；a（03 新维度）是**方法层**——让下一轮审查对这类问题有立项通道和证据形态。三层各自独立可实施，合起来封掉 §1 七层结构中的 1.2/1.5/1.6/1.8 四层（D-2/D-5/D-11/D-8）；1.1/1.3/1.4/1.7（检索轴/范式/形状vs存续/活文档）随 a 的 L-OP 证据形态进入审查动作自然覆盖；D-9/D-10（用户路径/反馈回流）超出本次修复范围，记为 watch：下轮审查可加一个「按 KEY-GUIDE 从零走一遍注册漏斗」的手测节（成本一次 ≤30 分钟，与既有手测清单 A-G 并列）。
