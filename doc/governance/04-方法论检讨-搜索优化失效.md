# 方法论检讨：为什么多轮搜索优化没有产生本质改进

> 2026-08-17。触发事件：用户两问揭穿两代工作流的盲区——①「Brave/Bing 不免费这么重大的信息为什么没搜到」②「API 全挂为什么直接上无头浏览器而不是先 curl 快探」。两个问题都是**方案层**的，都由用户提出，都不是任何一轮 agent 生成的。本文档检讨原因并落地制度修复，防止第三类盲区再次由用户买单。
>
> 检讨人：主循环（工作流设计者本人）——检讨对象是自己设计的审计方法论，外包给 agent 检讨等于重复同一错误。

## 一、事实清单（先摆证据，再谈原因）

| 轮次 | 产出 | 实际漏掉什么 |
|---|---|---|
| 五轮最优性审查（doc/governance/01） | 38 项调优、四维「全最优」结论 | Brave 免费档取消（2026-02）、Bing 退役（2025-08）、serp_http 快探层缺失——三项全部方案级 |
| v1.14 搜索方案重审（doc/governance/02） | 修了运营事实 + 级联，**裁决再次认定「机制面超过全部对标项目」** | serp_http 快探层——直到用户第二天再问才补上 |
| 两次真改进的来源 | — | 都是用户的经验性质疑（撞上付费墙；注意到降级直接上浏览器），零个来自 agent 对标 |

**定性**：不是某次执行不认真——是审计的**问题定义**让这类发现结构性不可能出现。

## 二、五个根因

### 1. 对标框架的引力锁定（最核心）
所有调研的问题都是「**Lasso 与对标项目比，谁的做法好**」。这个框架天然验证既有选择：对比维度=我们已经选定的维度（stealth 范式、抽取引擎、聚合策略），自己选的维度上自己当然不差。**没有人问「如果今天从零设计搜索链，它长什么样」**——serp_http 在零基视角下是显而易见的（成本排序：1s 探针先于 11s 冷启动+整棵 Chromium 树），在「评估现有链」视角下永远隐形。

### 2. 调研问题定义错误：问「他们有什么我们没有」而不是「用户在什么场景付出什么代价」
开源对标还有一个幸存者偏差：**多数开源搜索工具也不做 HTTP 快探层**（它们要么纯 API 要么纯浏览器），于是「大家都这样」成了最优的证据。用户的两个问题都来自**体验侧**（真金白银撞墙、等待时间直观感受）——体验侧信号在方法论里没有入口。

### 3. 成本模型全程缺席
五轮裁决文档中「时延」唯一出现是 T14 的 metrics 接线问题（观测），**从未有过任何一层 的延迟/资源/金钱成本表**。没有成本表就看不见成本排序错误——11s 排在 1s 前面这种事，只有把两个数字放在一起才会刺眼。resource-meter（v1.9）造出来了，但只用于**事后验证**，从未进入**事前设计审查**。

### 4. 收敛偏好 + 我亲手写下的「不得翻案」
循环的终止条件是「零调优轮」，制度性地奖励宣布收敛；我给第 2+ 轮复审 agent 的指令原文是「上轮 NO-GO/watch 是否有**新证据**翻案（**无新证据不得翻**）」——**亲手压制了对既有方案的重新质疑**。裁决链形成棘轮：一旦宣布最优，后续轮以先前裁决为锚（「维持已最优」），每多一轮反而更难推翻。

### 5. 用户提问没有被制度化为一等信号
两次教训的模式完全一致：用户问「为什么 X」→ 答案揭示一个方案级缺陷 → 修复缺陷 → **但不追问「为什么我们的流程生成不了这个问题」**。本次检讨即补上这一环：用户的每个 why 类提问，都应触发一次方法论回溯（是流程盲区还是随机意外），盲区类要落成清单维度。

## 三、制度修复（落成可执行项，不是表态）

| # | 修复 | 落点 | 形态 |
|---|---|---|---|
| 1 | **零基重设计练习（L-ZB）**：审查任何子系统前，先不看现状写「从零设计的方案」，再与现状 diff，每个 diff 要么补上要么给保留理由 | 03 清单新维度（建议补丁） | 每次大版本审查必做 |
| 2 | **成本模型前置（L-COST）**：方案审计必须附每层成本表（延迟 p50/p95 / 资源 / 金钱），**故障路径与正常路径分开列**——UX 活在故障路径里 | 03 清单新维度 + parse 模板 | 表格模板 |
| 3 | **红队翻案权**：迭代收敛类工作流必须含一个专职红队 agent，唯一任务是论证现行设计是错的，且**明确豁免「无新证据不得翻案」约束** | 工作流脚本模板 | 结构性 |
| 4 | **用户 why 触发方法论回溯**：用户每个方案级提问 → 判定（流程盲区 / 随机意外）→ 盲区类必须产出清单维度或流程补丁 | 维护者手册/CLAUDE 纪律 | 事件驱动 |
| 5 | 调研问题改写：从「对标项目有什么」改为双问——「零基会怎么做」+「用户故障路径的每一秒花在哪」 | 工作流 prompt 模板 | 结构性 |

## 四、诚实边界

- L-ZB/L-COST 能抓住「这一类」（成本序、分层、运营事实）盲区，**抓不住 Nobody-asked 类盲区**——总有第一个问题只有用户会问。制度 4（why 回溯）是把这类损失转化为改机的最快回路，不是消灭它。
- 红队 agent 有噪声（会产出错误推翻），需要与严格证据门槛并用：红队负责生成候选，门槛负责过滤——而不是用门槛过滤掉生成本身（本轮教训：门槛把生成权也过滤没了）。
- 多轮调研并非全无价值（38 项实施改进多数真实）——失效的是**方案层**的发现力。检讨针对后者，不推翻前者。

## 建议维度七：L-ZB 零基重设计（Zero-Based Redesign）

**审查动作**：对被审子系统，先**不看现有实现**，从问题本质（用户要什么、约束是什么）独立写出「从零设计的方案」；然后与现状 diff；每个差异要么成为改进项，要么给出明确的保留理由（写进档案）。

**判定要点**：
- 审查记录中必须存在「零基方案」段落——缺失即该项不过
- 零基方案与现状的 diff 清单（编号、每条处置：采纳/保留理由/记 roadmap）
- 特别检查**成本排序**：各层/各步骤的执行顺序是否按「便宜先试、昂贵兜底」排列

**为什么需要**：对标式审查（与开源项目比机制）天然验证既有选择——对比维度就是我们已经选的维度。零基练习是唯一能暴露「评估现有方案时不可见」的结构性问题的方法（实证：搜索降级链五轮审查全过，但「API 全挂直接上 11s 无头浏览器而不是 1s curl 快探」的成本序错误，零基视角下显而易见）。

## 建议维度八：L-COST 成本模型（Cost Model on Both Paths）

**审查动作**：方案/子系统审计必须附**每层成本表**，正常路径与故障路径分开：

| 层 | 延迟 p50/p95 | 资源占用 | 金钱成本 | 故障路径额外代价 |
|---|---|---|---|---|

**判定要点**：
- 故障路径（降级链走到最后一层）的总延迟与每层增量必须有实测或推算数字
- 任何「高成本低成本」相邻层倒挂（贵的排在便宜的前面且无理由）即改进项
- 用户可感知的等待/花费集中在哪一层必须能指出

**为什么需要**：没有数字就看不见倒挂。UX 活在故障路径里——正常路径人人都审，故障路径五轮没人算过延迟。

## 配套流程修订（迭代收敛类工作流）

1. **红队豁免条款**：多轮收敛工作流必须含专职红队 agent（任务=论证现行设计错误），其 prompt 明确豁免「无新证据不得翻案」类约束；红队产出走正常证据门槛过滤，但不得在生成阶段被门槛拦截。
2. **用户 why 回溯**：用户每个方案级质疑，处置后追加一次「流程盲区判定」：是流程生成不了这个问题（→ 产出清单维度/流程补丁）还是随机意外（→ 记录即可）。
