## 1. 背景：那道「墙」是什么，不是什么

2026-09-17 下午实机报告判定 tm.aliyun.com 存在「输入保护层：程序化设值被瞬间清除」。bugs/11 白盒复析**证伪**该判定（§0 断言 7/8）：

1. 真实机理是**框架/引擎的状态完整性语义**——搜索框为 React 16/17 受控组件：只走脚本写入（`element.value=`）的值不触发 onChange → 受控状态仍空 → **blur/下次 commit 时框架把 DOM 回写成已提交状态**（值存活到 blur，不是毫秒级消失）。报告时间线步 6-7（设值成功 + 截图确认「喵虎」）与步 11（物理点击后读回空）之间的差正是 blur 回写。
2. 经**可信输入管道**（CDP `Input.dispatchKeyEvent` 逐字派发——浏览器协议公开标记 `isTrusted:true`，框架 onChange 正常触发）键入的值 blur 后**存活**；lasso 既有 uid 路 fill（短值逐字）当天在该站全链路完成真实搜索。
3. 「六路全败」实为观察面错误（submit 走 `window.open` 开新 tab，原页 URL 永不变 → wait 结构性失明——bugs/11 决议 D-1/§2.19）。

**边界判定的原问题**（用户裁决指令）：「站点输入保护层是 lasso 的责任面吗？处理到哪层——原语补齐 / 主动对抗 / 只给信号？」本文即该裁决的书面答案。

## 2. 边界声明本体

### 2.1 正当面（提供什么）

- **标准输入原语**：`type`/`press`（browse 通道，底层映射上游 `type_text`/`press_key` → CDP `Input.dispatchKeyEvent` 逐键派发）与 Playwright `page.keyboard.type()`、Puppeteer `keyboard.type()` 同级，是 click/fill/type 三输入原语的补齐，不是反检测增强。CDP Input 域事件被浏览器标记 `isTrusted:true` 是**协议的公开设计**（所有 DevTools 驱动自动化的基础）——提供它 = 能力对齐。
- **诚实信号**：`input_guard_suspected`（advisory 信号 + hint）把「脚本设值可能被框架回写吞掉」这堵墙**显式化**——失败模式此前不可见（fill 报 worked、值静默消失）是可观测性欠账。
- **信任阶梯文档**（决议 B.4）：哪条路是可信管道（逐字派发）、哪条是程序化 DOM 写入（会被受控组件/保护层回写吞掉），调用方可见。

### 2.2 拒绝面（永不提供什么——rejected-by-design，bugs/11 §8-1）

以下能力**任何人未来提需求也拒绝**，除非用户显式推翻本节（见 §5）：

1. **键入节奏随机化 / 人类拟态延迟**——欺骗站点行为检测，不是输入能力；
2. **`_valueTracker` 欺骗**（伪装用户输入骗过框架状态追踪，作为 fill 策略）；
3. **accessor 反劫持**（拆除站点对 value setter 的包装）；
4. **`isTrusted` 伪造**及任何形式的事件信任级伪造；
5. **「让 fill 看起来像人输入」的一切包装**。

共同判据：这些不是「把键敲进去」，是**欺骗站点侧机制**。伦理红线 + 无必要（可信原语正门是开的）+ 脆性（与站点实现版本强耦合，维护成本无上限）三重否决。

### 2.3 立场：墙在那里，我们告诉你

lasso 对「输入墙」的全部责任 = **提供诚实原语 + 如实信号**。穿墙方式只有两种合法形态，且都**交给调用方决定**：

1. **换可信原语**——`type`（逐字派发进框架输入管道）；hint 里的换路指引是指令不是行动；
2. **请用户物理输入**——headed/visible 窗口场景下 hint 指引交还人类。

**绝不替用户决定攻墙**。信号路径零副作用、零自动改道、零自动重试（驱逐哨兵同款红线：检测到保护层不得自动换 type/自动重试/自动换通道——惊吓面与归因权交给知道真相的调用方）；探测探针纯读 + 页内 sleep，**明确禁止为探测合成 blur**（blur 会触发提交/校验）。

## 3. 未来需求的判定准绳

新输入面能力请求，过三问：

| # | 问 | 答 |
|---|---|---|
| Q1 | 它是 Playwright/Puppeteer/上游 chrome-devtools-mcp 已有的**标准输入原语**吗？ | 是 → 正当面候选（§2.1） |
| Q2 | 它的存在理由是**欺骗站点侧机制**（行为检测/状态追踪/事件信任级）吗？ | 是 → §2.2 拒绝面，无豁免 |
| Q3 | 它让失败**更可见**还是更隐蔽？ | 更隐蔽 → 与「消灭静默失败」血脉相悖，拒绝 |

Q2 是一票否决；Q1+Q3 同时成立才进正面面。

## 4. 与既有红线的关系

- **bugs/10 合成输入红线**（「只做检测与诚实报告，不绕过用户输入监控」）：本文是其输入原语面的展开——投递回执/物理竞争归因（bugs/10）管**输出侧**可见性，信任阶梯/`input_guard_suspected`（bugs/11）管**输入侧**可见性。
- **驱逐哨兵范式**（bugs/09 WT4）：「只供信号绝不自动升级」——§2.3 的信号纪律逐字沿用该范式。
- **永不 kill 用户浏览器**（bugs/03，行为红线 + hook 强制层）：不同轴线（浏览器主权 vs 输入伦理），同源精神——lasso 不替用户做主权/伦理决定。
- **禁绕过上游直连 CDP**（INV-6 + 上游锁定纪律）：即便在正面面内，实现路径也必须映射已锁定的上游工具，不自建协议客户端。

## 5. 推翻程序

本声明可被推翻的唯一形态：**用户显式书面裁决**针对 §2.2 具体条目（逐条点名，不接受「放开对抗能力」这类集合式授权）。agent（含任何自动化流程）无权提议以自身名义推翻、无权以「调用方需要」为由软化 Q2 判定。推翻后须回写本文 §2.2 并在 bugs/ 留裁决记录。
